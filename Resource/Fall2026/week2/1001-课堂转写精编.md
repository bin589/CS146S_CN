## 为什么需要 MCP

今天的主题是 MCP、工具调用以及更远的东西。会先讲 MCP 的基础：它在理论上怎么设计、协议是什么；然后再往上一层，讲人们实际在用的现代做法。

MCP 到今天已经存在接近两年，作为一个社区，我们已经学到了很多关于什么有效、什么无效的经验。它仍然是 LLM 总体——尤其对编码 agent 而言——最重要的基础构件之一。接下来会讲 MCP 是什么、它对做工具调用的 LLM 意味着什么，以及基于过去两年积攒的伤疤总结出的现代最佳实践。

核心观点是：今天的 LLM 是预训练系统，在海量数据上训练，包括网页数据和更定制的数据集。它们在参数里学到的东西，很大程度上是静态信息——训练数据在某个时间点的快照。作为静态系统，它们已经很有用、很强大；但当要在现代语境中使用它们、要对世界上正在发生的事情和最更新的系统版本做出反应时，就需要在预训练权重之外扩展其能力。为此我们发展出了工具，以及 MCP 这样的协议，让 LLM 获得更动态的能力。

## MCP 是什么

MCP 是 Model Context Protocol，由 Anthropic 大约两年前开发的开放协议。它让各类系统——例如 API 的包装层——以某种在底层系统或 API 之间可泛化的方式，向 AI 模型（通常是 LLM）提供相关上下文。

用最简单的话说，MCP 提供了把工具暴露给 LLM 的标准格式与协议。这些工具不只是本地开发的，也包括来自第三方服务或系统的工具。如果要与 Gmail 或 DoorDash 交互，你并不想自己搭一遍集成再暴露给 LLM；理想情况是「那件事已经由一支拿高薪的优秀团队做好了，我直接接入 DoorDash 的功能，让我的 LLM 用上」。MCP 就是实现这件事的格式与协议。

从历史背景看：传统上要把编码 agent 或 LLM 接到第三方服务，必须为每一个点对点方案搭连接器。如果一侧有 M 个 LLM 或编码 agent，另一侧有 N 个服务，就需要 M × N 个连接器。MCP 提供了更高效的方式：连接器之间共通的标准化部分——鉴权、错误处理、限流，以及搭 API 连接器时本来都得考虑的那些东西——不必重复实现。只要 LLM 一侧会说 MCP、连接器一侧说协议的另一端，就不必重新造这些轮子，只需实现一次。Gmail 可以把自己暴露给所有 LLM 编码 agent，每个编码 agent 也都能与 Gmail 对话。

输出格式也标准化了：底层基本上全是 JSON，LLM 与连接器之间说 JSON，这是社区共同约定的通用格式，结构化且可查看。价值就是从 M × N 变成 M + N。

图示里，旧世界一侧是 LLM（不同颜色代表不同模型、agent 或平台），另一侧是想交互的第三方服务，比如 Twitter API、Facebook，以及底部的 SOAP（把第三方服务暴露给其他系统的一种更老的遗留方式）。如果想让一个 LLM 连上 Twitter、一个 SOAP 系统和 Facebook，就得为每一个搭双向连接：第一个 LLM 需要三条，第二个三条，第三个三条，也就是 3 × 3 = 9 条连接（若把每个方向分开算则是 18 条，尽管每对之间也可以只有一条边）。

用 MCP 就能去掉中间那些过多的交叉边：LLM 一侧实现协议的接收端，第三方服务一侧实现自己的一端，MCP 定义了这些连接器的标准语言。连接从九条变成六条：agent 或 LLM 一侧三条，服务一侧三条。看起来提升不大，但在规模上差别巨大——可能有几百甚至更多编码 agent 和模型，服务则更多。考虑一下你想集成或暴露给编码 agent 的所有第三方 API，两侧都很大时结果是巨大的乘积，而 MCP 把它变成加法。

需要澄清的是，这张图简化得有点过头：中间是讲者用来概括 MCP 协议的总称，那个符号代表共同语言，而不是某个 server 本身。实践中每个 API 都有对应的 server——Twitter 一个 MCP server、Facebook 一个，等等。

## 术语：host、client、server、tool

host 指的是 Cursor 或 Claude Desktop 这类东西。MCP client 实际上是坐在 host 里的一个库，协议定义了 client，client 为每个 server 维护一个有状态会话。

server 是对第三方或第一方工具的包装。对第三方工具，通常通过网络、用 HTTP 这类协议交互。如果自己搭 MCP server——这会是本周或下周某次作业的练习——通常会把它放在本地，编码 agent 通过 stdio（标准输入输出）与它对话。如果要接 Gmail，可能是通过 HTTP 与本机之外托管的 MCP server 通信。server 可以是本地也可以是远程；通常那些不是自己搭的第三方服务都用在远程场景。

最后一个词是「tool」。前面把工具讲成把能力暴露给 LLM 的方式。在 MCP 里，可以把 tool 大致看成一个 API（这个说法要加引号）：它不是严格的 API，但确实是一个暴露给协议客户端的可调用函数。

## 客户端流程

典型的客户端流程大约四到五步，协议本身还有更多复杂度，规范是公开开源的，可以去读。在高层次上，与 MCP server 交互时，client 通常从发现（discovery）开始：把 Cursor 看成 host，里面跑着一个 client；client 向一个或一组 MCP server 询问「有哪些工具可用」。也就是第一行里 client 调用 `tools/list`，发出请求去发现可用内容。

server 返回描述每个工具的 JSON：名字、摘要、JSON schema。回想上一节课拆 Claude Code 的 harness 时看到的结构，完全一样。这就是 LLM 使用工具、判断何时使用工具所需的信息。

随后 host 把这些信息注入模型上下文。用户请求（比如向 Cursor 提的要求）触发模型；如果模型判断应当使用某个 MCP 工具，它就依据收到的定义发出结构化的 tool call；本地或远程的 MCP server 执行调用、返回响应，对话继续。前几次课已经见过这个流程的若干版本，包括自己实现工具调用的时候。

## 端到端示意：总结邮件

上一个部分是文字描述，这里给一张示意图。设想用户在与 LLM 或 ChatGPT 这类聊天机器人对话——这并不特指编码场景——请求是「总结 Jack 发来的邮件」。

用户查询由 host 接收，MCP client 就在 host 里；host 包括 Claude、Cursor、Windsurf。第二步是发现：LLM 有哪些能力可用？MCP server 提供这些信息。这个玩具例子里通过 MCP server 连了三个第三方服务：Gmail、S3 和 DoorDash。这三个 server 向 LLM 暴露不同的工具。关键在于这些工具不是我们实现的——本可以自己实现，但在这个例子里它们是别处的开发者定义的第三方 server，比如 Amazon 团队暴露 AWS 工具。我们只是想集成它们。

我们已经通过 OAuth 完成了对这些 server 的鉴权，发现阶段返回了可用的工具。第三步是智能层，也就是 LLM：把查询与可用工具合在一起，问「针对这个关于邮件的请求，该用哪个工具」。LLM 判断 Gmail 相关，返回一个结构化的 tool call。MCP server 执行它——既然是总结邮件，大概是 Gmail 的 list 工具。底层上，server 通常会去调真实 API，这也是把它描述成 API 包装层的原因。它执行操作、拿到响应、返回结果，流程继续。

**问：** MCP 是只给 API 用的吗，还是也能暴露其他东西、被别的系统使用？

**答：** 通常谈的是 agent，但只要能按协议定义交互，任何系统都能对接。它不是只给 agent 用的；如果两个系统想交换信息并遵守这些定义，任意一方都可以处在接收端或提供端。只是我们习惯把接收端想成 LLM。协议是围绕「我们认为对 LLM 重要的事」优化的，server 通常是 API 的包装层；这不必然，但实践中常见。

**问：** client 和 host 的区别是什么？

**答：** 实践中人们不太谈 host，更多谈 client 库。把 Cursor 里那个底层 Python 或 JavaScript SDK 想成 client；Cursor 是运行这个 SDK 的东西，SDK 定义了如何暴露和连接 MCP server。也可以说 VS Code 就是 host。在我们搭的那个精简 harness 里，根本没有定义协议或额外的层；可以把 VS Code 或 Cursor 看成 host，而「工具应当如何定义」的约定就是 client 一侧——我们以某种方式定义工具签名，遵守这些定义就能让各部分配合起来。

## 工具膨胀

关于工具膨胀的一个关键问题：是不是所有工具都被暴露出来？默认情况下是的，全都在。回想展示过的 Claude harness trace，大约 1 万行 JSONL，而真正的对话（包括提示词）可能只有 600 到 700 行，其余是全部可用工具的漂亮打印版本：schema、期望参数、名字。当然当时跑的那个 Claude Code harness 本身有点臃肿，但默认就是全量暴露。

这是 MCP 的一个显著局限。朴素版本下很快就会撞上工具问题：一部分是占满上下文，另一部分是让 LLM 困惑。前几节课讲过「dumb zone」与「smart zone」——超过一定 token 数之后，很难对那么多工具做推理；工具越多，混淆的可能性也越大。

有一些方法和论文在 MCP 之前做 RAG：用中间层索引所有工具，做语义搜索取出最相关的，把结果限制在十个左右，只把这些暴露进上下文。这是其中一种版本；后面会讲一种工业界更常见的绕开工具膨胀的做法。在你无法控制所对接 server 的情况下，这个问题尤其明显：我们控制不了 Gmail 或整个 G Suite 的 MCP server、AWS S3 的 server，也控制不了 DoorDash 的 server。

早期人们朴素地按 API 端点与 MCP 工具一对一来搭 server。接入 GitHub 的 MCP server 时有大约 150 个工具，用一个 server 差不多就到极限了，没有空间放别的。这种做法效率很低。现在好一些了，但限制仍然存在。

**问：** 接入第三方 server 的鉴权怎么做？

**答：** 通常通过 OAuth 或其他鉴权方式。在 Codex 或 Claude 里跑一条命令添加 server，给出名字或它的位置，然后鉴权。如果是第三方服务，必须建立安全连接；一旦鉴权完成，工具就对 client 可用。鉴权 token 有时效（TTL），过期后需要重新鉴权。实践中通常鉴权一次，在 token 生命周期内一直可用。

**问：** 直接调 API、把 API token 放进上下文让模型调用，或者用 CLI，和 MCP server 相比如何？

**答：** 基线问题仍然是「怎么把工具暴露给 LLM」。这些方式都能用，后面会讨论它们与 MCP server 之间的取舍。MCP 是我们为「把工具暴露给 LLM」优化出来的协议，好处包括标准化、安全性和版本管理。MCP 早期人们把 API 端点和 MCP 工具当成一对一，是赶热潮的做法。

## MCP server 设计最佳实践

前面都是理论，偏枯燥但重要。实践中意味着什么？先说不要做什么：把每个 API 端点映射成一个 MCP 工具这种朴素做法不必再花时间。2024 年与 2025 年初，server 设计的前三四个月试过，效果不好——工具膨胀、上下文膨胀、LLM 困惑；那些更早的模型在区分工具上更差。还记得 Cursor 一度只允许 IDE 里加载 88 个工具，有些 server 根本无法完整加载；光是 GitHub 就给出 120 到 150 个工具。

不要把 MCP server 只当成 REST API 的包装。LLM 是对你提供的上下文做推理的；API 端点是为人类使用而设计的，有时连对人类都不算友好，那未必是 LLM 消费信息的最佳方式，一对一映射会浪费潜力。有大量能工作但让 LLM 难以推理的 API，因为粒度太细：拿 UID、拿资源，等等。如果每种可能的资源都有一个 get-X 工具，光 API 定义就可能占满上下文窗口。这会造出巨大而复杂的上下文，也意味着 agent 要花大量时间编排简单的逻辑。

**按结果设计，而不是按操作设计。** 假设你说「我比一对一映射更强，我上过 146S，能做得更好」，建议的做法是围绕结果而非单个操作来设计工具定义。比较同一件事的两种做法。选项一是「给这个用户的邮箱付款」：提供邮箱，发出付款，结束。选项二沿用传统的 API 到工具映射：API 可能从未定义「按邮箱付款」，只定义了「按账户付款」。那怎么拿到账户 ID？先列出与该用户邮箱关联的账户。但也许从鉴权 token 里只拿到 user ID，于是还得先从 ID 取到邮箱。取到邮箱、列出它的账户、再用账户 ID 付款——这是必须连续做对的三次工具调用，每一次都是独立的 LLM 请求-响应往返，而且你希望它别出错。第一种做法只有一次调用：把结果操作化，而不是把达成结果的每一步都暴露出来。

这种改进方向关注的是我们希望 LLM 做什么的语义。传统 API 未必围绕语义设计，它们的设计目标是暴露或修改每一份数据。

**参数要显式。** 回想第一节课的工具：读文件、编辑文件、列出文件，参数都是显式标注类型的。类型标注、docstring、函数名都会成为 LLM 推理「该做什么」的上下文。Python 里一种偷懒做法是到处用 `*args` 和 `**kwargs`：写起来容易，也能工作，但让 LLM 难以推理里面该放什么。早期搭 MCP server 时最先出问题的地方之一，就是参数与工具调用不匹配——模型选对了工具，却提供了错误的参数。原因之一就是我们没有严格说明函数调用需要满足什么。避免巨大的无类型字典：可以用字典，但要用 Pydantic 或类型标注来描述它，这给 LLM 的提示比任意输入更有意义。

指令是上下文，docstring 是上下文，每一条标注都是上下文。设计 MCP server 时，写下的一切都同时供你和 LLM 消费，要按这个标准对待。

**错误信息也要具体。** 即便像「抛一个裸 `Exception` 而不是 `ValueError`、`NameError` 或自定义错误类型」这样的小事也有影响。优先使用具体的或自定义的错误类型，它们提供的提示能帮 LLM 解释错误并调试。

**工具命名服务于可发现性。** 看 Claude harness 时，本地工具有一套独立的命名方案；你自己的工具命名方案同样重要。

**问：** 在第一个最佳实践里，是信任 LLM 自己搞清如何从用户邮箱拿到账户 ID，还是把它编程实现？

**答：** 实践中很难预测对 LLM 而言最优的语义。你不知道它会以哪些方式使用工具，也不知道最终会提供哪些工具。常见的路径是：一开始对工具设计并不深思，为了覆盖率有点失控，把能想到的每种情况都支持上；然后发现有 100 个工具，需要减少，于是开始整合——看 LLM 的 trace，找出常见模式。比如分别有搜索会议、搜索转录、搜索 Slack 线程的工具，本来可以搜所有频道，但现在有三个工具定义；一种整合方式是做一个 `search_resource` 工具，把要搜的资源作为参数。设计第一批工具时，你甚至可能还没支持 Slack 或邮件，怎么可能预见到需要一个跨频道的通用工具？通常就是先急着铺开、把东西往墙上扔看哪个粘住；等到 LLM 连简单任务都开始困惑，再整合。这就是重构，不必事先把所有东西想清楚。

**问：** 设计一个要分发给所有人使用的 harness，和只做本地用的 harness，有什么区别？

**答：** 取决于它将以何种方式提供——这听起来像推脱，但确实如此。讲者喜欢的一句话是：软件工程是「给编程加上时间和人」之后发生的事情。当很多人长期参与同一个东西，它才成为一门工程学科。如果知道它会被广泛使用，就要认真考虑设计、消费者以及不同类别的消费者；如果只是自己用，可以少一些严格的做法。

**问：** 什么时候该路由到更强的模型？

**答：** 这本身可以讲半小时，没法给死规定，因为取决于任务复杂度、成本、是否已有微调模型等诸多因素。回到前面的例子：实践里模型多半能自己搞清那三步顺序，但那样是在浪费潜力——即便它正确地执行了三步，也会更贵、更慢、出错概率更高。这些因素都指向应该优化。针对具体用例和不同模型的取舍可以另外讨论，路由是另一个话题。

## Code mode：meta MCP server

另一种做法与现代 MCP server 设计实践相关，也接上前面的 RAG 思路：与其把每个 server 的每个工具都放进上下文，不如让某个东西在需要时把正确的工具拉进来。基本做法是在你和其他 server 之间建一个 meta MCP server，只暴露两个工具：search 和 execute。search 找出相关的 server、工具和定义；execute 在搜索缩小候选范围之后执行操作。说具体一点：agent 调用 search 找出相关工具及其定义；execute 这一步用生成的确定性代码完成操作。这个中间层动态生成代码，把工具或函数串起来；不必让 LLM 逐个走完每一次工具调用，这两个 meta 工具支撑起生成操作所需代码的能力。

好处有两点。第一，大幅减少上下文，因为不再把全部可用工具一次性载入上下文窗口。第二，因为交互是通过 search 和 execute 进行的，接口与你有多少 server 无关——任意数量的 MCP server 都可以被索引以供搜索。有研究报告这种技术能削减 90% 以上的 token。它在工业界有不同叫法，值得记住的一个术语是「code mode」：通过代码生成工具调用并发出 server 请求。

具体例子：请求是「找一张 Jira ticket，并用 Google Drive 里的信息更新它」，这是软件工程团队请 LLM 做的一件相当标准的操作。底层会从该请求动态生成一段代码，搜索可用工具并按请求过滤。这里标出的东西与上一页的 search 工具并不完全等价，但它返回工具并做过滤。要点是这段代码是动态生成的，不是你事先写好的一块；LLM 看到「找 Jira ticket」的请求，知道自己有 code-mode SDK，于是生成代码去取回最相关的工具。

从这段代码出来的是相关工具定义。第二步是 execute：设想 search 返回了用 JQL 搜索 Jira、获取 Google Workspace Drive 内容、更新 Jira ticket 这三个工具，第二段代码被动态生成，把这些操作串起来。这段代码是作为进程执行的，不是由 LLM 亲自执行；我们从未把完整工具集载入模型上下文，代码被生成并运行（通常在虚拟机里），返回相关工具并传递结果。

**问：** 过滤必须按语义做吗？

**答：** 可以语义也可以词法。这里用的是词法：LLM 识别出请求里提到 Jira 和 Google Drive，生成基本的 JavaScript，用 `includes` 按这些关键词过滤。也可以扩展到语义搜索。
