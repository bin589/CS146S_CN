这门课的申请已在周日截止。如果到现在还没收到回复，大概率不在拿学分的名单里；旁听当然欢迎，这里对所有人开放。

本周需要记在日历上的是额度合作伙伴 Factory 的工作坊。课程的合作伙伴分几类：客座讲师、提供算力额度的公司，以及 OSS 合作伙伴。Factory 是提供额度的公司之一，也是当今编码 agent 领域最顶尖的初创公司之一，最近一轮融资后估值大约五十亿美元。比钱更重要的是人：他们的 CTO Eno 这学期晚些时候会来做讲座，是讲者在编码 agent 领域交流过的最聪明的人之一。

因为提供了额度，他们希望把大家接入 Factory 平台。团队的 Ashley 会在周四来做工作坊，演示怎么用 Factory 并正式开通账号。时间安排在正常上课之外，不强制参加：先上正常课程（可能会提前几分钟下课），再留出 20 到 25 分钟给她。她会做一点与斯坦福相关的演示来展示平台能力。

今天还要正式宣布 OSS 合作伙伴计划，这是这一轮课程里最令人兴奋的部分之一，筹备了几个月。很多合作伙伴在做很酷的软件，而为他们贡献代码是作业的一部分。当天是提交志愿的截止日期：有一个表单收集用于通信的邮箱，以及 Discord 和 Slack 信息。各合作伙伴与社区互动的方式不同，有的用 Slack，有的用邮件，有的用 GitHub issue，有的用 Discord，需要把这些汇总起来。

本学期的合作伙伴包括：Anyscale，在机器学习推理与训练领域；Arize，一个可观测性平台；Browserbase，浏览器 agent 以及「用浏览器为 agent 服务」方向上最热门的初创公司之一；cmux，一个很受欢迎的开发者工具；CopilotKit，AG-UI 背后的团队，那是用于构建前端系统的 agent 协议；CrewAI，被许多企业使用的 agent 编排平台；HeyGen，一个生成系统（转录原文写的是 “audio”，媒体类型不明）；Marimo，出自斯坦福，讲者本科时最亲密的朋友之一创立，实际上是下一代 Jupyter notebook；OpenHands，走开源路线的、比较受欢迎的编码 agent 之一；Pi，另一个受欢迎的编码 agent，OpenClaw 由它驱动；Unsloth，公司用来定制开放权重模型的微调平台；Vercel，一个 Web 应用平台。此外还有 Warp，他们卖「软件工厂」（software factory），并允许课程去构建他们的软件工厂；以及 Zilliz，做向量数据库。

## 规模化代码库下的上下文窗口

今天的主题是面向复杂代码库的高级提示与上下文工程。课程的目标之一，是把有扎实理论基础和学术背景的软件开发者训练成能在真实工作中成功的人，因此内容大量对应工业界的实际做法。

其中最重要的一课，是学会在远超「几个本地文件」的规模上操作编码 agent：几百到几千个文件、数百万行代码，接近 Google 那种量级。一旦到了这个规模，就会撞上编码 agent 固有的上下文窗口限制。有些智能体最多能到一百万 token，但 token 并不等价——在性能下降之前，真正能用于有意义工作的 token 大概不到一百万。

因此在复杂软件上工作时必须更有章法，因为大量代码与上下文都可能被 agent 吞进去。这就是今天的重点：vibe coding 和朴素提示（vanilla prompting）在某个点上都会失效。此外还会讲两件事——如何接入陌生的代码库（OSS 合作伙伴计划会逼着大家做这件事），以及如何解决特别复杂的编码任务。

## 从 vibe coding 到系统化流程

规格驱动（spec-driven）工程是工业界解决更难任务时事实上的做法。实现方式有很多，今天主要讲一套框架，再给出另外几个可以自行探索的名字。

这套框架是 RePPIT：research、propose、plan、implement、test，五步（转录中写作 REPIT）。今天会逐步展开每一步的含义，也会介绍思路相近的其他框架；核心原则大体相同，可以试过之后挑自己喜欢的。

「vibe coding」这个词出现得并不久，大概一年半。它来自 Andrej Karpathy 的一条推文——他是斯坦福校友，曾在 Fei-Fei 的实验室，后来做了很多了不起的事。按他自己的说法，那是洗澡时冒出的念头：如果做这件事时干脆不去想，直接「耶稣，你来掌方向盘」，会发生什么？这个想法很酷，也造就了一条热门推文，甚至能上维基百科词条。但要在困难代码库里解决困难问题，需要比 vibe coding 再高一层。有时人们把这门课叫成 vibe coding 课，讲者不希望它被这么叫——这门课讲的是系统化使用编码 agent 的原则，而不是说完「耶稣，你来掌方向盘」之后看会发生什么。

一个思想实验：如何构建一个 Mint 的克隆？Mint 是一个消费级记账应用，可以录入预算、连接信用卡、追踪支出，看自己在各类目上花了多少钱；它是这类产品的早期版本，被 Intuit 收购。现在还有 Monarch 等玩家。再往前一步：假设已经有一个功能完整的 Mint 克隆，需要扩展它。要在生产规模上做到这一点，用编码 agent 写代码的方式必须有章法。

首先要理解一个陌生的代码库，尤其是一个自己没有参与、没有写过的代码库，要能在里面找到路，掌握到足以指挥 agent 的程度。然后是提出方案：如果在一个自己没写过、也一无所知的代码库里接到任务，会怎么着手？会提出若干方案，挑出最有希望的那个，实现它，再测试它。有人会说「我们做测试驱动开发，难道不是先写测试再反推方案？」这没问题，在这里同样成立。讲者并不规定顺序，核心部件是相同的，只是排列方式略有差别。

这套框架是讲者日常工作中大量使用的，认识的人也用类似原则，只是名字不同。接下来会把它应用到一个具体问题上。

演示对象是一个极简的 Mint 克隆，其现状是：能看到异常项、能上传 CSV 文件，没有信用卡集成、没有与第三方服务的连接；有基础图表、可以设预算上限、可以逐行查看各类目支出明细。界面里的数据是编造的，不是讲者真实的消费。要加的新特性是「按类别的支出随时间变化的趋势线」。

这个应用是 vibe coding 出来的：讲者不是前端开发者，知道自己懂得刚好够惹麻烦，但不够真正干活；当初只是问了一句「一个 Mint 克隆应该长什么样」，结果在功能上够用了。现在要在此基础上扩展，而扩展的动机正是要演示框架。

## RePPIT 五步框架

五步的定位各不相同。研究（research）负责把代码库蒸馏成一份能喂给 agent 的整合表征；提案（propose）基于这份表征提出候选方案；计划（plan）把选中的方案落成设计文档；实现（implement）按文档改代码；测试（test）验证行为。

后文会按顺序走一遍，每一步都给出背后的提示词。整个过程中，人类在两端介入最多：前端是意图与架构，后端是代码评审。这两处是当下人类仍然最有价值的位置。

## 研究阶段：research codebase

第一步是研究。这一步的目的是往 agent 的上下文里种下关于代码库的有用信息，而不是把原始代码全部倒进去。做法是把代码库蒸馏成一个整合表征，让编码 agent 有足够的信息开始提出方案。

讲者准备了一组 skill，第一个叫 `research codebase`。底层上，skill 绑定了一段提示词。研究阶段只负责记录代码库里现在有什么，不负责实现，也不负责提方案；它的职责是定义今天已经存在的那些行为契约。提示词写得很明确：只记录今天存在的东西，不要提改进建议。

它可能会读取被提到的文件、把请求拆解成若干研究领域、按清单逐项推进。最关键的是最终的产物：一份结构化的研究文档，描述 agent 对各个组件或代码区域的了解，可能带有对代码的引用；提示词也规定了输出格式。在它运行的过程中，它在聚合上下文；结束时得到一份包含这些上下文的文档。

这份文档有两个用途。其一是给编码 agent 打底，因为后续步骤都建立在它之上；其二是帮助讲者本人理解——不需要每个细节，但需要一个心智模型来分辨好坏。讲者坚持认为人仍然需要对代码现状有心智模型：不需要对 Terraform 了解得极其细致，但应该能看出这里有前端和 backend、前端涉及 Vue、backend 的模型是某种形态；真要进代码，也能去看。这份文档同时是讲者自己的参考。

**问：** 如果项目已有大量关于自身结构的 Markdown 文档，是否跳过研究阶段，直接让 agent 去读？

**答：** 取决于文档质量。如果维护得好、准确反映代码库，建议复用，并调整 skill 让它以这份文档为起点。演示里有些工作重复了，因为并没有摄入既有文档——文档常常维护不善。虽然有了编码 agent 之后情况有所改善，可以定时跑 agent 保持文档新鲜，但很多时候并没有这么做。在「喂坏文档」和「从零开始」之间，讲者会选从零开始：应该让 agent 建立自己的理解，而不是被过期信息搞糊涂。最好的做法是让那些过时文档要么不存在，要么被更新。

**问：** 这套 skill 与提示词是否做过 A/B 测试？

**答：** 「A/B 测试」这个词有点重，但它确实被测试过。讲者用大约一年到一年半的时间逐步构建，从一份文档开始逐行添加：看研究时发生了什么，看到不满意的地方就追加或修改。所以是定性意义上的 A/B 测试。另一方面，它被提交到团队共享的仓库，其他开发者也在用、在测；代表这套框架的代码是当前代码库里被审视得最多的部分之一。讲者不会每加一行都做正式对比，但会有人说「这里退化了，改一下」或「加上这一行」。

**问：** 那个 `Context7` 是什么？

**答：** 一个提供外部第三方文档的 MCP server。如果只关心本地代码，可以把那一行删掉；但如果需要查某个库或某个版本怎么用，Context7 能拉取最新文档。也有其他做同样事情的 MCP server。

**问：** 怎么让 skill 在一个全新仓库里可用？

**答：** 如果是克隆已有仓库、而 skill 已经提交进版本控制，那就自动可用。也可以把 skill 打包成插件，在整个组织内提供，或者使用封装了多个 skill 的全局插件。做法不止一种。

**问：** 研究产出需要验证吗？

**答：** 讲者在研究这一侧做的验证比以前少了，因为 agent 在阅读代码、把它蒸馏成整合表征这件事上已经很强。他更关心实现而不是研究。研究本质上是信息压缩，而 agent 很擅长压缩；不能说百分之百，但已经足够好到让人不太担心这一环。验证也会在之后发生，尤其是在测试阶段。

## 提案阶段：make proposals

到目前为止只有一份描述代码库状态的通用文档，它对新特性只字未提。接下来要变得更有主张。要做的特性是「按类别的支出随时间变化的趋势线」。

「make proposals」是另一个 skill。它的内容更多，但功能上很简单：给定代码库的整合表征，针对这个特性提出两个不同的方案。可以要三个或四个，但超过两个之后讲者看到的是收益递减。这些提案以既有研究文档为依据，可以把文档拉进来，或者显式种进上下文。

agent 会捕获用户请求、解析研究、生成方案、做一轮验证，最后按固定格式产出。这个产物不一定非要写进文件，但可以写。关键内容包括：每个方案的上下文、方案概述、关键改动、权衡、验证、开放问题。这一步和下一步，是人类作为用户和专家最该深度介入的地方。

演示里给出两个方案及其权衡。一个是服务端方案，上传响应支持多序列；讲者不确定是否要走这条路。另一个在客户端处理已上传的交易数据，感觉更轻量，是纯前端改动。对现场演示来说，越少碰 backend 越好，于是选了第二个。

在真实工作里，讲者会仔细看这两个方案：权衡是什么？自己在乎什么？作为理解产品需求、系统需求与系统限制的技术人员，在方案之间做选择，然后推进。这一步和下一步，是人类作为用户和专家最该深度介入的地方。

**问：** 是否应该单独做一个「选方案」的 skill？

**答：** 也许可以，但那样提案这一步就变成了 agent 自己决策的一部分。

**问：** 提案数量为什么是两个？

**答：** 大体上是经验法则，可以扩展到三个、四个甚至更多，但讲者发现了收益递减的拐点。类比机器学习里的 PCA：想要彼此正交的主成分，一个轴和另一个与它垂直的轴。可以扩展到更多维度，但主要目的是逼 agent 识别出解空间中两个不同的区域；按经验，这通常已经覆盖足够多的空间，同时给人留下发挥专业判断的余地。在更大的代码库里，这个假设可能需要重新审视。

**问：** 随着编码越来越强，人还在哪些地方有用？

**答：** 今天主要有两处：意图与架构，以及代码评审。人应当作为理解产品需求、系统需求和约束的专家插进去。讲者承认自己仍然要在流程早期决定 agent 怎么运作、怎么实现，要把规格、研究和实际计划说清楚——对他而言这是当下人类杠杆率最高的位置之一。两年后是否仍然如此很难说；可能存在一个编码好到任意程度、人们仍希望人参与早期阶段的世界。课在录像，两年后可以回来核对这个判断。

**问：** 内置的规划能力已经不错，为什么还要自己写提示词？

**答：** 随着 harness 越来越复杂，它们承担了更多这类责任，尤其是规划；Claude 和 Codex 内置的规划能力相当好，讲者自己有一份规划提示词但并不总是用。他仍然认为指导 agent 行为、标准化产物与输出是有价值的。不必照搬这种做法：提示词会公开，鼓励大家拆开看，删掉不喜欢的行、改掉不合适的地方。此前教这门课时，一位医疗行业的学员按自己的需要扩展了 RePPIT。这不是一套定死的流程，而是拆解复杂问题的起点。

## 计划阶段：设计文档模板

现在有了两个方案，认真评审过之后选定一个，接下来要形成计划。讲者强烈建议使用编码 agent 内置的规划能力。他自己的 skill 很直白：这里有一份设计文档模板，按选定的方案把它填满。

为什么用这个格式？因为它好读、好解析，包含做出判断所需的信息。别人不一定需要全部字段，但这份模板是讲者长期迭代出来的，用来评估 agent 将要实现的方案质量。

设计文档包含：代码库现状、功能与非功能需求、设计决策与权衡、技术设计。里面有一些代码级的细节，好让讲者能钻进细节里。这部分未来可能会变小，但他喜欢稍微动手：就像翻书，他不是 Kindle 派，喜欢纸质页；在这里他想看到哪些文件在改，几乎像看一份 diff。

模板里那些大写字母的字段是人工写的：讲者希望它包含行号。几个月前加上行号，是为了让方案落地、得到一份几乎到代码级别的计划；这个做法以后是否还有必要，要看发展。

模板还覆盖测试（跑哪些测试）、可观测性，以及未来考虑（future considerations）。其中最有价值的一点，是明确写出实现范围之外的东西：对这次特性来说，哪些事情不做。讲者把这些放进未来考虑，并注明「不要碰这些，只实现范围内的部分，其余一律推迟」。显式写出来有助于防止 agent 跑偏去做无关的事。模板里还有安全、发布等章节。

最后得到一份相当详细的文档。看这份文档的版式很有用：服务边界是否合理？代码库的模块化是否恰当？数据模型是什么？在研究文档之后，这份计划严格按提供的格式展开：现状、功能需求，等等。在这个阶段，讲者会非常深入地审查这里的内容。

## 实现与测试

接下来进入实现。讲者要展示那段「极其精巧」的实现提示词——它几乎不需要成为一段提示词；但如果要凑出 RePPIT 里的 I，就必须有这么一步，于是就有了它。抛开玩笑，它本质上只是告诉 agent 按计划实现。

与此同时，Cursor 正在按计划推进，并自行补齐需要的东西：它隐式地打开浏览器、与应用交互、生成合成数据，并试着通过 CSV 界面把数据传进去。也就是说，它把实现和测试合并成了一个步骤。这在六个月前还做不到，但现在足够好，可以在实现之后说一句「我大概应该自己测一下，验证生成的结果」，然后真的去做。

Cursor 和许多其他 agent 内置了这个能力。如果你的 agent 没有，可以加上 Playwright MCP 之类的东西：有若干 MCP server 能让 harness 获得打开浏览器并在其中操作的能力。本周晚些时候讲 MCP 时会展开，并给出几种选择。

这次浏览器交互本质上是一次行为检查：上传一个 CSV，就应该看到新特性被生成出来。做完之后可以离开内置浏览器，用普通浏览器打开应用，至少视觉上看起来是完整的。这就是对应用行为的一次检查。

**问：** 这一步在检查什么？

**答：** 检查行为契约。上传 CSV、看到新特性生成，这就是行为验证。而性能、质量、可读性等属于行为契约之外的关切，归入代码评审。

## 代码评审

行为契约之外的方面——性能、质量、可读性等等——属于代码评审。今天人们通常让 agent 来做，往往由不同的 agent 分别负责特定细节。

讲者展示了一个简单的代码评审 skill。他并不特别推荐这一个，只是用它来激发兴趣：它检查 diff，输出 `must fix`、`recommended fixes` 和 `consider` 三档，相当于红黄绿。这个 skill 把安全、性能、风格、一致性、边界情况合在一起。

在实践中，人们常拆成四到五个 agent，每个负责一个领域，比如安全或性能。在 GitHub 上开 PR 时，一个 action 会跑这些 agent，再由一个协调 agent 汇总它们的输出，得到一份报告，覆盖架构、风格、一致性等方面。演示里把所有内容放进一个 skill，只是为了更好消化；本学期晚些时候会再展开。

需要注意的是 skill 的命名有歧义：也存在一个内置的 skill。运行结束后会得到一份检查该特性各方面的输出。

**问：** 每一步都要写文档并新开会话吗？什么时候清空上下文重来？某些步骤是否需要更强的模型？

**答：** 这些选择有些更接近艺术而非科学，但已经越来越多人研究。关于压缩（compaction）——即压缩上下文的表征——有一篇扎实的博客文章研究了何时压缩、如何影响成本、累积多少 token 之后应当压缩。结论之一是区间大约在 25 万到 45 万 token 之间，具体取决于模型。很难一概而论，但基于他们自己的 trace 和编码 agent 使用情况，那大致是建议把上下文压缩成更整合表征的位置。他们也研究了更多上下文是否有用、编码 agent 实际使用超过那个量的频率有多高，结果并不高。这就是为什么说：虽然编码 agent 号称一百万 token 上下文，实际上并不是一百万 token 的有效上下文，按这项研究更接近 50 万。具体结论是：经常压缩。

关于清空上下文：演示里讲者做了一件他并不推荐的事。在提出并选定方案之后，正常情况下他会清空上下文；否则两个方案都还留在那里，尽管已经确定只做其中一个，这会让 agent 搞不清自己在实现哪个。虽然已经说了「用方案二」，上下文里仍带着那个被考虑过但没有采用的备选方案所对应的无用 token。他会在那里清空。总体而言他倾向于清空：一旦看到几十万 token，就尽量把相关信息写进文件，把这份压缩表征摄入一个全新上下文，再从那里继续。

关于模型质量：早期阶段用非常好的模型，后面的阶段不必那么强。实现、甚至测试可以用更轻量的模型；研究、提案和计划要用强模型，因为大部分思考发生在那里。

## 有效 token 与流程选择

前面提到过「smart token」：上下文里真正有用的部分，相对于未被使用或没有帮助的部分。粗略地说，有用部分可能在一半到最多四分之三之间；这更像是人们观察到事情开始出错时的直觉。

最重要的实践是审查你的规格，尤其在研究、提案和计划这三个环节保持高度参与。与此相关还有一个尚未回答的开放问题：五步走完、做了计划、评审、实现了特性，那么什么时候该用朴素提示，什么时候该切换到更重的流程？

可以简单提示：跟 ChatGPT 说「耶稣，你来掌方向盘」。可以直接进入 Claude 的 plan mode 做一份计划。可以先研究再计划，把更多时间花在计划前的上下文上。也可以把研究和计划重复几轮。这些选项之间如何取舍，取决于任务复杂度；这张图很有用，坐标轴的具体位置可能随模型质量变化，但方向是对的。

演示里的做法是重手笔：花 45 分钟讲提示词，只为给一个 Web 应用加上仪表盘功能。按任务复杂度看，改一段文案或做个小修复，直接跟 Claude 或 Codex 说就行。跨多个文件的小特性，就该开始考虑做计划；是否对所有相关文件都足够熟悉？也许熟悉也许不熟悉，为稳妥起见做个计划。复杂度上升到中型特性，以及确定要做的大重构或迁移，就需要多轮研究、提案和计划，配合独立会话和 subagent。讲者日常工作中的超大项目，会拆成多个 issue，每个 issue 用一个独立 agent，并把 issue 堆叠起来，让 agent 在彼此的工作之上继续推进；这时他会更认真地写 issue 描述。
