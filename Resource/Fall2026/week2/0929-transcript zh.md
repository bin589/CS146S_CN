今天的重点是面向复杂代码库的高级提示工程与上下文工程。我们的目标之一，是把理论功底扎实、学术背景很强的优秀软件开发者，培养成能在真实世界里成功的人。我们要讲的很多内容，都是你在业界工作中会经历或用到的。

你必须学会的最重要的事情之一，是如何在超出手头几个本地文件的范围之外操作编程智能体。我们说的是数百上千个文件、数百万行代码，接近 Google 那样的规模。一旦到了那个规模，你就会撞上编程智能体固有的上下文窗口限制。有些模型号称能到一百万 token，但并不是所有 token 都是平等的。在性能退化之前，你大概能用上不到一百万 token 来做有意义的工作。

这意味着，在处理复杂软件、有大量代码和上下文可能被智能体读入时，你必须更用心。这就是今天要讲的重点。我们都可以 vibe code，用最朴素的提示方式，但只能到某个程度为止。这是我的核心论点。

我还想讲如何接入不熟悉的代码库——你们会通过 OSS 合作伙伴计划来做这件事——以及如何解决特别复杂的编程任务。我们会讲一个规格驱动工程（spec-driven engineering）的框架。做法有很多，但今天大部分时间我会讲其中一个框架，然后给你们另外几个框架的名字去探索。规格驱动工程大概是业界解决较难任务的事实标准做法。

我们会聚焦 REPIT：研究（research）、提议（propose）、计划（plan）、实现（implement）、测试（test）。就是这五步。我们会逐个讲清它们的含义，我也会分享其他涉及类似思路的框架。你可以都试试，挑你喜欢的。很多核心原则是相通的。

有人记得“vibe coding”这个词是什么时候出现的吗？其实没多久。在现代世界里，一年半就是永恒了，但它出现也就差不多这么久。它来自 Andrej Karpathy 的一条推文，他是斯坦福校友，曾在 Fei-Fei 的实验室，后来做了很多了不起的事。

按他自己的说法，这真就是洗澡时的灵光一现。想法是：如果我们做这个叫 vibe coding 的东西，根本不去想它，直接说“耶稣，你来掌方向盘”会怎样。看看会发生什么。这很酷，也很容易成为一条热门推文。这么干你能上维基百科条目。但要在困难的代码库里解决难题，我们需要比 vibe coding 再高一个层次。

有时候人们把这门课叫作 vibe coding 课。那不是我希望它被叫的名字。这门课讲的是使用编程智能体的系统性原则。

这里有个思维练习：你会怎么做一个 Mint 的克隆？有些人可能记得 Mint。它是一款面向消费者的记账应用。你可以输入预算、绑定信用卡、追踪支出，看看自己在不同类别上花了多少钱。Mint 是这类产品的早期版本，后来被 Intuit 收购了。现在还有别的玩家，比如 Monarch。

我们再进一步。假设我们已经有一个功能完整的 Mint 克隆，现在需要扩展它。要在生产级别做这件事，我们必须对如何用编程智能体写代码保持有条不紊。

首先，你必须理解一个不熟悉的代码库，尤其是你既没贡献过、也没亲手写过的代码库。你要能在里面找到路，并且懂得足够多，才能指挥你的智能体。然后你需要提出方案。如果我给你一个任务，代码库不是你写的、你也完全不了解，你会怎么做？你会提出一些方案，找出最有希望的那个，实现它，再测试它。

有些人可能会说：“我们做测试驱动开发。不是应该先写测试，再倒推解决方案吗？”没问题，在这里也适用。我对顺序并不教条。核心环节是一样的，哪怕顺序稍有调整。

这是我在日常工作中大量使用的一个框架，我认识的人也用类似的原则，只是叫法不同。我想把 REPIT 讲一遍，并应用到一个问题上。

我会给你们看一个极简的 Mint 克隆和它的当前状态。然后我们用一个新功能来扩展它：一条按类别展示支出随时间变化的趋势线。

我说过这不是 vibe coding 课，但老实说，这个应用就是 vibe code 出来的。我不是前端开发者。我懂的那点东西足够惹祸，但不够真正干活。我问了“一个 Mint 克隆应该长什么样”，出来的东西在功能上就是我们要的。现在我们要扩展它。

你可以看到异常项，也可以上传 CSV 文件。没有信用卡集成，也没有连接第三方服务。你能看到基础图表、设置预算上限，还能逐行查看各类别支出的明细。

这不是我的消费数据，是编造的数据。我不知道这个“异常大额消费”是什么。可能是任何东西，随你想象。但按类别展示支出随时间变化的趋势线还没有。我们该怎么加上它？我们用这个框架。

大家能看到我的屏幕吗？好。我会按框架的每一步来做，加上这个功能，并展示每一步背后的提示词。

补充背景：我不知道这个应用是怎么写的。再说一次，我不是个有用的前端开发者。Vue？我完全不知道。这代码不是我写的，但我需要为它做贡献、扩展它，所以我会用这个框架。

第一步是研究。这是一个机会，把关于代码库的有用信息播种进智能体的上下文，而不是把全部原始代码都喂给它。我们是在把代码库蒸馏成一份整合过的表示，让编程智能体有足够信息开始提出方案。

我们从汇总代码库里正在发生的事情开始。我准备了一些 skill，第一个是“研究代码库”（research codebase）。在底层，这个 skill 绑定着一个提示词。趁它在思考——大部分 LLM 推理就发生在这里——我们来看看那个提示词。

研究阶段只负责记录代码库里现有的东西。它不负责实现，也不负责提出方案。它的职责是定义今天已经存在的行为契约。提示词写得很明确：只记录今天存在的东西，不要建议改进。

它可能会读取被提到的文件，把请求拆解成若干研究领域，并按清单逐项推进。重要的是最后产出的工件：一份结构化的研究文档，描述智能体对代码库各组件或区域学到了什么，可能还会引用代码。提示词也规定了输出格式。

在它处理的过程中，它在汇总上下文。最后我们会得到一份包含这些上下文的文档。到这儿有问题吗？

研究这一步第一次把对代码库的理解播种进智能体。如你所见，它生成了相当详尽的文档，说明代码目前是如何工作的。

这份文档有两个用途。一是给编程智能体打底，因为后续步骤都建立在它之上。二是帮助我自己理解。我想懂得足够多，才能有用。我不需要每个细节，但我需要一个心智模型，来分辨好坏。

在这一点上，我坚持认为我们仍然需要对现有代码有一个心智模型。这并不意味着要极其细致地理解 Terraform。但我应该能看出有一个前端和一个后端、涉及 Vue、后端模型以某种特定形式存在。如果我真要进代码里，我能去看。这份文档对我自己也是参考资料。

接下来是“提议”。到目前为止，我们有一份描述代码库状态的通用文档。它对我们要做的功能只字未提。现在我们要变得更有主见了。功能是：一条按类别展示支出随时间变化的趋势线。

我把这个放进去，让它跑。“提出方案”（make proposals）是另一个 skill。它的内容更多，但功能上很简单：给定代码库的整合表示，拿这个功能，提出两个不同的方案。

你可以要三个或四个，但我见过的边际收益在超过两个之后就递减了。这些方案建立在已有的研究文档之上。你可以把那份文档拉进来，或者显式地把它播种进上下文。

智能体捕获用户请求、解析研究、生成方案、做一些验证，并产出这种格式的东西。你不一定非要把这个工件写成文件，虽然也可以。

重要的部分是：每个方案的背景、方案概览、关键改动、权衡、验证，以及待解问题。这个阶段和下一个阶段，是你作为用户和专家最该投入的地方——决定智能体该怎么做事。

我在这里能看到两个方案及其权衡。我会读一遍。一个是服务端方案，上传响应支持多序列。我不确定我想走这条路。另一个是在客户端处理已上传的交易数据。那感觉更轻量，纯粹是前端改动。对于现场演示来说，我少碰点后端越好。我选方案二。

在现场演示之外，我会仔细看这个。权衡是什么？我在意什么？作为懂产品需求、系统需求和系统限制的技术人员，我在这些方案中做选择，然后继续。我先把下一步跑起来，然后停下来回答问题。

**[观众提问]** 如果项目已经有很多关于自身结构的 Markdown 文档，你会跳过研究阶段，直接让智能体去读那些文档吗？还是说，为了让上下文更靠得住，让智能体重做一遍更好？

好问题。如果有现成文档，你是直接吃进去、扔掉，还是找个折中？这完全取决于文档有多好。如果它维护得好、准确反映了代码库，我建议复用它，并调整 skill 让它以文档为起点。

在我的例子里之所以有一些工作重复，是因为我没有吃现成文档。这是因为文档往往维护得不好。有了编程智能体之后情况有所改善，你可以定时跑它们来保持文档最新，但很多时候并没有这么做。

在吃进糟糕文档和从零开始之间做选择，我会选从零开始。你希望智能体建立自己的理解，而不被过时信息搞糊涂。最佳实践是确保那些过时文档要么不存在，要么被更新到最新。这个我们后面再讲。

这主要是启发式的。你可以扩展到三个、四个甚至更多。我发现有一个边际收益递减的点。如果你熟悉机器学习里的 PCA，我想要的是彼此正交的主成分：一个轴，和另一条垂直的轴。

你可以把它扩展到更多维度，但我主要想迫使智能体去识别解空间里两个不同的区域。以我的经验，这通常足以覆盖足够大的空间，同时给我的专业判断留出余地。在更大的代码库里，你可能想重新审视这个假设。

是不是应该有一个单独的 skill 来选择方案？也许吧。那样的话，提议这一步就会被封装进智能体自己的决策里。

我们会谈到，随着编程能力越来越强，人类在哪里仍然有用。今天有两个主要位置：意图与架构，以及代码审查。我们应该作为懂产品需求、系统需求和约束的专家参与进去。

这是我承认：我仍然应该在流程早期就决定智能体将如何运作、如何实现某个东西。我要把规格、研究和实际计划说清楚。对我来说，这是今天人类杠杆率最高的位置之一。

两年后这还成立吗？很难说。我认为存在这样一种世界：编程变得任意地好，而我们仍然希望人类参与这些早期阶段。我们在录像，所以两年后你们可以来核查我说的话。再提一个问题，然后我们继续。

随着编程智能体的 harness 越来越复杂，它们承担了更多这类责任，尤其是计划。我有自己的计划提示词，但我并不总是用它。Claude 和 Codex 内置的计划能力相当不错。

我仍然觉得，指导智能体行为、把工件和输出标准化是有价值的。你不必这么做。我会把提示词发出来，也鼓励你们把它们拆开看。删掉你不喜欢的行，改一改。我以前教这门课的时候，有一位医疗行业的学生按适合他自己的方式扩展了 REPIT。这不是一套板上钉钉的流程，而是一个用来拆解复杂问题的起点。

我们现在到了计划阶段。我们提出了两个方案，当然也认真审阅过，并选定了一个。现在我们开始制定计划。

大家用过内置的计划 skill 或能力吗？我非常鼓励你们在编程智能体里用。这是我的 skill。它基本上是说：这里有一个设计文档模板，根据方案把它填好。

为什么是这个格式？因为这是我喜欢、也容易解析的格式。它包含我做判断所需的信息。你可能不需要全部内容，但这个模板是我长期打磨出来的，帮我评估智能体将要实现的方案质量。

设计文档包括代码库的当前状态、功能性与非功能性需求、设计决策与权衡，以及技术设计。里面有一些代码级细节，让我能钻进细节里。

你可能会说，这个部分以后会越来越小，但我喜欢稍微亲手一点。这就像翻书。我不是 Kindle 派，我喜欢纸质页。这是我在代码里的那一页。我想看到哪些文件在改，几乎像看 diff 一样。

从大写字母你能看出这是人写的：我要它包含行号。这是我几个月前加的，用来让方案落地，得到一份几乎到代码级别的计划。我们看看这一点以后还有多必要。

模板还覆盖测试——跑哪些测试、可观测性，以及未来考虑。最有价值的一点之一，是明确写出哪些不在实现范围内。对于这个功能，这些是不会做的。我把这些放在“未来考虑”下面，并说：“不要碰这些。只实现在范围内的部分。其他一律推迟。”

把这一点写明确，有助于防止智能体跑偏去做无关的事。文档里还有关于安全、发布（rollout）和其他考虑的部分。

最后我们得到一份相当详尽的文档。看它的排版很有帮助。服务边界合理吗？我们在恰当地把代码库模块化吗？数据模型是什么？

那是研究文档。哎呀，这才是计划。它遵循了我给的格式：当前上下文、功能需求，等等。在这个阶段，我会非常投入地审阅这里的内容。

[观众提问：关于如何验证研究的输出；具体措辞不清晰。]

我在研究这一侧的验证比以前少了，因为智能体在阅读代码、把它蒸馏成整合表示方面已经非常擅长。我更关心实现，而不是研究。研究本质上是对信息的压缩，而我认为智能体非常擅长这个。我不能说百分之百，但好到我不那么担心验证那个阶段。

验证也会在之后发生，尤其是在测试中。既然我们在实现，你会看到一种我没有显式提示过的验证形式，这值得一提。

单元测试、集成测试和冒烟测试，是验证方案最有价值的方式之一。如果我们相信编程正变得任意地好、实现细节可能没那么重要，那么我们在意的就是输入和输出。我们必须严格检查输出。

作为现代开发者，我们很大一部分时间会花在给输出设定要求上：它应该怎么工作、应该具备什么行为。

在它实现的同时，我想展示这个极其复杂的实现提示词。它几乎都不需要是个提示词。但如果你想凑一个缩写词，你需要一个 I，于是就有了这个。开个玩笑，它基本上就是告诉智能体去实现这份计划。

与此同时，Cursor 正在按计划推进，并添加它需要的东西。它在隐式地打开浏览器、与应用交互、造合成数据，并试着通过 CSV 界面上传。它把实现和测试合并成了一步。

六个月前还不是这样，但现在它已经好到可以在实现完某个东西之后说：“我大概应该自己测一下，验证生成的东西。”所以它正在这么做。

Cursor 和许多其他智能体都内置了这个能力。如果你的智能体没有，你可以加类似 Playwright MCP 的东西。有好几个 MCP server 能让你给 harness 增加打开浏览器并在其中操作的能力。这周晚些时候我们会更多聊 MCP，我也会给你们一些做法选项。

这个问题非常好。我们在这里检查的是行为契约。这个浏览器交互实际上是一次行为检查：我上传一个 CSV，然后我应该看到新功能被生成出来。

看起来做完了。我可以离开内置浏览器，用普通浏览器打开这个应用。至少从视觉上看，它似乎是完整的。那是对应用行为的一次检查。

还有另一类关注点：性能、质量、可读性等等。这些超出行为契约的方面属于代码审查。我们会讨论代码审查，以及今天人们怎么做。它常常是智能体驱动的，由不同的智能体负责特定细节。

我会给你们看一个简单的代码审查 skill。我并不一定推荐这个具体的 skill；我分享它是为了激发一些好奇心。它检查 diff，并输出“必须修复”“建议修复”和“考虑”，类似红、黄、绿。

这个特定的 skill 把安全、性能、风格、一致性和边界情况合在一起。在实践中，人们常用四五个智能体，每个负责一个方面，比如安全或性能。你在 GitHub 上开 PR 时，一个 action 会跑这些智能体，再由一个协调智能体合并它们的输出。你会得到一份报告，包含对架构、风格、一致性等的检查。

我这里把它们都放在一个 skill 里，因为这样更好消化。这学期后面我们会更多聊这个。

这些 skill 的名字有点含糊；另外还有一个内置 skill。它现在在跑，最后我们会得到这种格式的输出，检查已实现功能的各个方面。

**[观众提问]** 每一步你都会写一份文档、开一个新会话吗？你什么时候决定刷新上下文、从零开始？另外，某些步骤是不是需要更强的模型？

非常好的问题。人类处在什么位置？你要不要写工件？什么时候清空上下文？你没提压缩（compaction），但我也一起讲。什么时候用更强的模型？

这其中有艺术成分多于科学成分，但人们越来越多地在研究这些选择。这里有一项研究，我会发给你们。上节课我们讨论过压缩：压缩上下文的表示。

这是一篇很扎实的博客文章，研究了压缩、什么时候做、它如何影响成本，以及在压缩之前应该累积多少 token。我不会把整篇总结一遍，但一个要点是大约在 25 万到 45 万 token 之间，取决于模型。

很难一概而论。基于他们自己的 trace 和编程智能体的使用情况，那大概就是他们建议把上下文压缩成更整合表示的位置。他们还研究了拥有更多上下文是否有用，以及编程智能体实际使用超过那个量的频率有多高。结果是不太常用到。

这就是为什么我说，虽然编程智能体宣称有一百万 token 的上下文，但实践中那并不总是一百万 token 的有用上下文。根据这项研究，真正有用的可能更接近五十万 token。具体的结论就是：经常压缩。

至于清空上下文：我在这个演示里做了一件我不推荐的事。在提出并选定方案之后，我通常会清空上下文。否则两个方案都留在那里，哪怕你已经选定了一个。这会让智能体困惑它到底在实现哪个。是的，你告诉它用方案二，但上下文里仍然留着那个你考虑过、但没选的替代方案的无用 token。

我会在那里清空上下文。总的来说，我倾向于清空。一旦我看到几十万 token，我会试着把相关信息写进文件，把那份压缩后的表示导入一个全新的上下文，再从那里继续。

最后一个问题是关于模型质量。早期阶段用一个非常好的模型。后期阶段不需要那么强。实现乃至测试可以用更轻量的模型。研究、提议和计划要用强模型，因为大部分思考发生在那里。

我们时间快到了。我还有几页幻灯片很重要，讲完就结束。

我们已经提到过“聪明 token”：上下文中真正有用的部分，相对于没用上或没帮助的部分。粗略地说，有用的部分可能在二分之一到最多四分之三之间。再说一次，这更多是人们注意到事情开始出错时的直觉。

最重要的最佳实践是：审阅你的规格。尤其要在研究、提议和计划上投入。

还有一个我们没回答的开放问题。我们刚刚走完了五步，做了计划，审阅了它们，实现了一个功能。但你什么时候该用朴素提示，什么时候该切换到更重的流程？

你可以用简单提示：跟 ChatGPT 说“耶稣，你来掌方向盘”。你可以直接进 Claude 的 plan mode，做一个单一计划。你可以先研究再计划，在计划之前花更多时间在上下文上。或者你可以把研究和计划重复好几轮。

我们处在这些选项之间的什么位置？这张图很有用。坐标轴可能会随模型质量移动，但方向上是正确的思考方式。有些任务适合更简单的方式，有些则需要更繁复的流程。

我展示的做法是偏重的。我花了 45 分钟讲提示词，只为在一个 Web 应用里做一个仪表盘功能。看任务复杂度，像改个文案或者小修复，跟 Claude 或 Codex 聊聊就能搞定。没问题的。

对于跨多个文件的小功能，就该开始考虑做计划了。你对所有文件都足够了解吗？也许，也许不。稳妥起见，做个计划。

当复杂度上升到中等规模的功能，更不用说大重构或迁移，你会想要多轮研究、提议和计划，配合独立会话和子智能体。在我的日常工作里，对于非常大的项目，我会把它们拆成多个 issue，每个 issue 用单独的智能体，再把 issue 堆叠起来，让智能体在彼此的工作之上继续。到那时，我会更用心地写 issue 描述。
