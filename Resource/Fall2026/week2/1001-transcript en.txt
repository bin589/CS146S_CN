MCP stands for Model Context Protocol. It's an open protocol developed by Anthropic, I believe about two years ago. I'll explain what that means, what existed before, and why MCP was developed.

In the simplest terms, MCP provides a standard format and protocol for exposing tools to LLMs. These aren't just tools we develop locally, but tools from third-party services or systems. If you're interacting with Gmail or DoorDash, you don't want to build the integration yourself and expose it to your LLM. A little terminology and background: traditionally, when we wanted to connect coding agents or LLMs to third-party services, we had to build connectors for every point-to-point solution. If you had M LLMs or coding agents on one side and N services on the other, you needed M × N connectors between the hosts or agents and the underlying tools.

MCP provides a more efficient way to do this. We don't have to reimplement the standard pieces common across connectors, including authentication, error handling, rate limiting, and many of the things we'd otherwise have to think about when building an API connector.

As long as the LLM side knows how to speak MCP and the connector side speaks the other side of the protocol, you don't have to recreate all those aspects. You handle those pieces once. Gmail can expose itself to every LLM coding agent, and each coding agent can speak to Gmail. That's the main value proposition.

The output format is standardized too. It's pretty much all JSON under the hood: LLMs talking JSON to underlying connectors. That's the common format we've agreed on as a community. It's structured and viewable.

The value is going from M × N to M + N. I'll show how that happens in the next diagrams.

This approach to improved MCP servers focuses on the semantics of what we want LLMs to do. Traditional APIs weren't necessarily designed around semantics; they were designed to expose or modify each piece of data.

Another practice is being explicit about arguments. Remember the tools from the first class: read file, edit file, and list files? We explicitly typed the arguments. Type annotations, docstrings, and function names are all part of the context the LLM uses to reason about what to do.

A lazy approach in Python might be to use *args and **kwargs everywhere. It's easy and it works, but it's confusing for an LLM to reason about what belongs in those arguments. I want to get through option two because it reflects modern practice in MCP server design. It's related to the RAG point: instead of putting every tool from every server into the context at once, what if something could pull in the right tools when needed?

The basic approach is to create a meta MCP server between you and the other servers. It exposes just two tools: search and execute. Search finds relevant servers, tools, and definitions. Execute performs the operation after you've searched and narrowed down the relevant candidates. That's high-level; let me make it more concrete.

The agent calls search to find relevant tools and their definitions. The execute step uses generated deterministic code to perform the operation. This middle layer dynamically generates code that strings tools or functions together. Instead of making the LLM work through each individual tool call, these two meta tools support generating the code needed for the operation.

I'll describe the benefits and then show an example. First, it massively reduces context because you no longer load every available tool into the context window at once. Second, because you interact through search and execute, the interface is agnostic to how many servers you have. An arbitrary number of MCP servers can be indexed for search.

Some studies of this technique report more than 90% token reduction. It has different names in industry, but one term to remember is “code mode”: generating tool calls and issuing server requests through code.
