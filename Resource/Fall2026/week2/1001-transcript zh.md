今天我们聚焦 MCP、工具调用（tool calling）以及更远的东西。我们会从理论层面讲 MCP 的基础：它是怎么设计的，协议是什么。然后我们再往上一层，讲人们实际在用的现代做法。

到这会儿，MCP 已经存在快两年了，所以作为一个社区，我们对什么有效、什么无效已经学了很多。我认为它仍然是 LLM 总体上最重要的基础构件之一，尤其是对编程 agent 而言。我们会讲 MCP、它对做工具调用的 LLM 意味着什么，以及基于过去两年积攒的伤疤总结出的现代最佳实践。

高层的要点是：今天的 LLM 是预训练系统。它们在大量数据上训练，包括网页数据和更定制化的数据集。在很大程度上，它们参数中学到的是静态信息：训练数据在某一时间点的快照。

作为静态系统，它们有用且强大。但当我们要在现代场景中使用它们、让它们对世界上正在发生的事情和最最新版本的系统作出反应时，就需要把功能扩展到预训练权重之外。我们开发了工具等东西，以及 MCP 这样的协议，来赋予 LLM 更多动态能力。

先问一下，有人用过 MCP 吗？熟悉这个概念吗？我看到有几个人摇头，也有几个人没反应。这挺正常的。

MCP 是 Model Context Protocol（模型上下文协议）的缩写。它是由 Anthropic 开发的开放协议，我记得是大约两年前。它允许系统（例如 API 的封装层）向 AI 模型（通常是 LLM）提供相关的上下文，并且这种提供方式能跨底层系统或 API 通用化。我会解释这是什么意思、在这之前有什么、以及为什么要开发 MCP。

最简单的说法是，MCP 提供了一种把工具暴露给 LLM 的标准格式和协议。这些工具不只是我们在本地开发的工具，还包括来自第三方服务或系统的工具。如果你要和 Gmail 或 DoorDash 交互，你不会想自己构建集成再暴露给 LLM。理想情况下，你可以说：“这已经由一支拿着高薪的优秀开发者团队处理好了。我要接入 DoorDash 的功能，让它对我的 LLM 可用。”MCP 就是实现这一点的格式和协议。

先讲一点术语和背景：传统上，当我们想把编程 agent 或 LLM 连接到第三方服务时，必须为每个点对点方案构建连接器。如果一边有 M 个 LLM 或编程 agent，另一边有 N 个服务，那么宿主或 agent 与底层工具之间就需要 M × N 个连接器。

MCP 提供了一种更高效的做法。我们不必重新实现连接器中共通的标准化部分，包括身份认证、错误处理、限流，以及构建 API 连接器时本来不得不考虑的其他许多事情。

只要 LLM 这边会说 MCP、连接器那边会说协议的另一端，你就不必重建所有这些方面。这些部分只需处理一次。Gmail 可以把自身暴露给每一个 LLM 编程 agent，而每个编程 agent 都能和 Gmail 对话。这就是主要的价值主张。

输出格式也被标准化了。底层基本上全是 JSON：LLM 用 JSON 和底层连接器对话。这是社区达成共识的通用格式。它是有结构的、可查看的。

价值就在于从 M × N 变成 M + N。我接下来用图说明这是怎么发生的。

在旧的世界里，一边是 LLM。在我这张花哨的图里，不同颜色代表不同的模型、agent，或者暴露 agent 的平台。另一边是你要交互的第三方服务：也许是 Twitter API、Facebook，或者最下面的 SOAP。SOAP 代表一种更老、更遗留的方式，用来把第三方服务暴露给其他系统。

如果你想让一个 LLM 连到 Twitter、一个 SOAP 系统和 Facebook，你就要为每一个建立双向连接。第一个 LLM 需要三条连接，第二个需要三条，第三个需要三条。也就是 3 × 3，九条连接。如果把每个方向分开算，我猜是 18 条，不过每对之间其实也可以只有一条边。

有了 MCP，我们可以去掉中间那些过度交叉的边。LLM 这边实现协议的接收端。第三方服务这边实现它自己那一端，也就是提供端。MCP 为这些连接器定义了标准化的语言。

我们从九条连接变成了六条：编程 agent 或 LLM 这边三条，服务那边三条。看起来提升不大，但在规模上差别巨大。你可能有几百个甚至更多编程 agent 和模型，服务则更多。想想所有你想集成、或想暴露给编程 agent 的第三方 API。两边集合一大，结果就是巨大的乘法效应。MCP 把它变成加法。有问题吗？

这张图简化得有点过头了。中间那个是我给 MCP 的总括桶，代表协议。实践中，每个 API 都有对应的服务器：Twitter 一个 MCP server、Facebook 一个，等等。中间那个符号代表共同语言，而不是某个服务器本身。这大概会让人有点困惑。

好问题，也正好引出术语。这些是谈论 MCP 时想显得专业就需要知道的术语。

host（宿主）就是我们说 Cursor 或 Claude Desktop 时所指的东西。MCP client 实际上是坐落在 host 上的一个库。协议定义了 client，而 client 对每个 server 维护一个有状态的会话。

server 是第三方或第一方工具的封装。对第三方工具，你通常通过网络、用 HTTP 之类的协议交互。如果你自己构建 MCP server（这会是本周或下周某次作业里的练习），你往往会把它放在本地。然后你的编程 agent 可以通过 stdio（标准输入输出）和它对话。

如果我要集成 Gmail，我可能是通过 HTTP 和我机器之外托管的 MCP server 对话。server 可以是本地的，也可以是远程的。通常，不是你构建的第三方服务都是在远程场景下使用的。

最后一个术语是“tool（工具）”。我们讲过，工具是把能力暴露给 LLM 的一种方式。在 MCP 里，可以把 tool 几乎当成 API 来理解——这里要打一个大大的引号。它不是严格的 API，但它是你暴露给协议客户端的一个可调用函数。

典型的 client 流程大致有四五步。协议里还有更多复杂性，欢迎你去读公开的开源规范。在高层次上，当你和一个 MCP server 交互时，client 通常从 discovery（发现）开始。

把 Cursor 想成你的 host，里面跑着一个 client。client 向一个 MCP server（或一组 server）问：“有哪些工具可用？”这就是这里的第一行：client 调用 tools/list。它发出请求来发现可用的东西。

server 返回描述每个工具的 JSON：名称、摘要和 JSON schema。还记得我们看 Claude Code 及其 harness 内部的时候吗？结构是一样的。这就是 LLM 使用工具、判断何时使用工具所需要知道的信息。

然后 host 把这些信息注入模型的上下文。用户的请求——比如我们向 Cursor 提的某个要求——会触发模型。如果模型决定应该使用某个 MCP 工具，它会根据收到的定义发出结构化的工具调用。本地或远程的 MCP server 执行调用、返回响应，然后对话继续。过去几节课我们见过这个流程的多个版本，包括我们自己实现工具调用的时候。

这里是一张可视化图。上一张幻灯片是口头描述，这一张是示意图。假设我们是用户，在和 ChatGPT 这样的 LLM 或聊天机器人对话。这不一定是编程场景。我们让系统总结 Jack 发来的邮件。Jack 是谁？我不知道。

用户的查询由 host 接收，MCP client 就在 host 里。host 包括 Claude、Cursor 和 Windsurf。然后是第二步：discovery。LLM 有哪些能力可用？MCP server 提供这些信息。

在这个玩具示例里，假设我们通过 MCP server 连接了三个第三方服务：Gmail、S3 和 DoorDash。那是 S3 吗？你是 Amazon 的人，应该知道 S3。我刚才看你，是想给你一个送分题。

这三个 server 向 LLM 暴露不同的工具。重点是这些不是我们实现的。我们本可以实现，但在本例中它们是别处开发者定义的第三方 server，比如 Amazon 团队暴露 AWS 工具的 server。我们只想和它们集成。

我们已经通过 OAuth 向这些 server 完成了认证，discovery 返回我们可以使用的工具。第三步是智能层：LLM。我们把查询和可用工具结合起来，问：“针对这个关于邮件的请求，应该用哪个工具？”LLM 判断 Gmail 相关，并返回一个结构化的工具调用。

MCP server 执行它。因为我们要总结邮件，所以大概是 Gmail 的 list 工具。底层上，server 通常会调用 API 交互，这也是我们把它描述为 API 封装的原因。它执行操作、拿到响应、返回响应，然后我们继续。

如果我理解错了请纠正我，问题是：MCP 是否只用于 API，还是也能暴露其他东西、被其他系统使用。

通常我们说的是 agent，但任何人都可以和这个协议交互，只要他们按协议定义自己的交互。它不只服务于 agent。如果两个独立系统想交换信息并遵守这些定义，任何一方都可以在接收端或提供端。

只是我们通常把接收端想成 LLM。协议是围绕我们认为对 LLM 重要的东西来优化的，而 server 通常是 API 的封装。这并非必然，但实践中通常如此。

关于 client 和 host 的区别：实践中人们不太常提 host。我们通常说 client 库。把 Cursor 内部那个底层的 Python 或 JavaScript SDK 想成 client。Cursor 是运行这个 SDK 的东西，SDK 定义了如何暴露和连接 MCP server。

回到第一部分：也许连整台机器都算 host。抱歉，VS Code 是 host。在我们构建的那个精简 harness 里，我们甚至没有定义协议或额外的一层。你可以把 VS Code 或 Cursor 想成 host，而把“工具应如何定义”的约定定义想成 client 侧。我们以某种方式定义了工具签名，遵守这些定义就能让各部分协同工作。

关于 tool bloat（工具膨胀）的好问题：所有工具都会暴露吗？默认情况下，你会拿到全部。如果你还记得我展示的 Claude harness trace，大约有 10,000 行 JSONL。真正的对话（包括提示词）也许只有 600 或 700 行。其余都是所有可用工具的格式化版本：schema、期望参数和名称。

诚然，我跑的那个 Claude Code harness 有点臃肿，但默认情况下这些工具全都会暴露。这是 MCP 一个相当大的局限，也正好引出我们后面要讨论的内容。用朴素版本的话，你很快会遇到工具相关的问题。

问题的一部分是把上下文塞满。另一部分是让 LLM 混淆。几节课前我讲过“笨区（dumb zone）”与“聪明区（smart zone）”。超过一定 token 数之后，要对那么多工具进行推理就很困难。工具越多，混淆的可能性也越大。

有一些方法和论文讲在 MCP 之前先跑 RAG。一个中间层给所有工具建索引，做语义搜索取出最相关的那些，把结果限制在比如 10 个，只在上下文里暴露这些。这是一种版本。我会展示另一种在业界更常见的、绕开 tool bloat 的做法。

你说得对，这确实是个问题，尤其是当你无法控制所交互的 server 时。我控制不了 Gmail 或通用 G Suite 的 MCP server、AWS S3 server，也控制不了 DoorDash server。

早期人们很朴素地构建 server，把 API 端点一比一映射成 MCP 工具。我们当时就是这么做的。现在人们一般不这么做了，但那是早期的做法。如果你连 GitHub MCP server，大概有 150 个工具。你用一个 server 就差不多到顶了，没多少空间给别的。效率很低。我们现在好一些了，但这仍是个局限。一个短问题被我答得很长。

通常你通过 OAuth 或其他认证方式连接。你在 Codex 或 Claude 里运行一条命令来添加 server，提供它的名字或它所在的位置，然后认证。如果是第三方服务，你需要建立安全连接。一旦认证完成，工具就对 client 可用了。

认证 token 有生存时间（TTL）。最终它会过期，你需要重新认证。实践中你认证一次，在 token 有效期内都有访问权限。

高层上说，是的，但微妙之处在于它在什么场景下有用。MCP 早期，人们把 API 端点和 MCP 工具当作一对一的等同物。他们是在赶 hype 的潮流。

根本问题仍然是：我们如何把工具暴露给 LLM？我们可以直接用 API，把 API token 放进上下文让模型调用。也可以用 CLI。我们会讨论这些做法与 MCP server 之间的取舍。MCP 是我们为了优化“向 LLM 暴露工具”而开发的协议，好处包括标准化、安全性和版本管理。

回到我们原定的节目。

我们来谈 MCP server 的设计。这之前都是理论：有点枯燥，但是重要的基础。实践中这意味着什么？

我不会花时间讲那种把每个 API 端点映射成 MCP 工具的原始、朴素做法。在 2024 年和 2025 年初，server 设计的最初三四个月里我们试过，效果不好。我们得到的是工具膨胀、上下文膨胀，以及被搞糊涂的 LLM。更早的模型在区分工具方面还要更差。

我记得 Cursor 的 IDE 里曾经只允许 88 个工具。有些 server 你甚至没法完整加载。光 GitHub 就给你 120 到 150 个工具左右。那不是个好系统。

我们来讨论朴素做法之后是什么。正如我提到的，你不该把 MCP server 只当成 REST API 的封装。LLM 会对你提供的上下文进行推理。API 端点是为人类消费设计的，有时候甚至对人类也不够友好。那未必是 LLM 消费信息的最佳方式。一比一映射会把一些潜力留在桌上。

有很多能用的烂 API 和端点，它们太细粒度，LLM 很难推理。一个副作用是产生大量小工具：获取一个 UID、获取一个资源等等。如果你为每种可能的资源都有一个 get-X 工具，光 API 定义就可能把上下文窗口塞满。

这会产生庞大而复杂的上下文。这也意味着 agent 要花很多时间来编排简单的逻辑片段。我会展示一个前后对比的例子。

对于第一种方案，假设你说：“我比一比一映射更强。我上过 146S，我能做得更好。”建议的做法是围绕结果（outcome）而不是单个操作来设计工具定义。

考虑做同一件事的两种方式。一种更冗长、更细粒度，出错机会更多。方案一是“向这个用户的邮箱付款”。你提供邮箱，发送付款，就完成了。

方案二遵循更传统的 API 到工具映射。也许 API 从来没定义过“向邮箱付款”，只定义了“向账户付款”。你怎么拿到账户 ID？你列出与该用户邮箱关联的账户。但也许你从认证 token 里只拿到了用户 ID，所以得先从这个 ID 拿到邮箱。

你拿到邮箱，列出它的账户，然后用账户 ID 付款。这是三次必须依次做对的工具调用。每一次都是独立的 LLM 请求—响应往返，你还得指望它成功。第一种方案只有一次调用。你是在把结果操作化，而不是暴露达成结果所需的每一步。

这种改进 MCP server 的做法聚焦于我们希望 LLM 做什么的语义。传统 API 未必是围绕语义设计的；它们是为了暴露或修改每一份数据而设计的。

另一个做法是显式声明参数。还记得第一节课的工具吗：read file、edit file、list files？我们给参数显式标注了类型。类型注解、docstring 和函数名，都是 LLM 用来推理该做什么的上下文的一部分。

在 Python 里，偷懒的做法可能是到处用 `*args` 和 `**kwargs`。这很简单也很有效，但 LLM 很难推理这些参数里该放什么。早期构建 MCP server 时，最先出问题的情况之一就是参数与工具调用不匹配。模型选对了工具，却给了错误的参数。原因之一是我们没有足够严格地告诉它函数调用需要满足什么条件。

避免庞大的无类型字典。你当然可以用字典，但要用 Pydantic 或类型注解来描述它。相比任意输入，这给 LLM 的是更有意义的提示。

这个点我已经讲过，就不多啰嗦了：指令是上下文，docstring 是上下文，每一个注解都是上下文。设计 MCP server 时，你写的一切都同时供你和 LLM 消费。请相应地对待它。

错误信息也包括在内。哪怕只是抛一个通用 Exception，而不是 ValueError、NameError 或自定义错误类型，这样看似无害的选择也很重要。优先使用具体的或自定义的错误类型。它们提供的提示能帮助 LLM 解读错误并进行调试。

这一点的延伸是：为发现（discovery）而给工具命名。我们看 Claude harness 时，我们暴露的本地工具有一套单独的命名方案。

我想把方案二讲完，因为它反映了 MCP server 设计的现代实践。这和 RAG 那一点相关：与其把所有 server 的所有工具一次性放进上下文，如果有什么东西能按需把正确的工具拉进来呢？

基本做法是在你和其他 server 之间创建一个 meta MCP server。它只暴露两个工具：search 和 execute。Search 查找相关的 server、工具和定义。Execute 在你搜索并缩小到相关候选之后执行操作。这是高层描述，我讲具体一点。

agent 调用 search 找到相关工具及其定义。execute 步骤使用生成的确定性代码来执行操作。这个中间层动态生成代码，把工具或函数串起来。与其让 LLM 逐个处理每一次工具调用，这两个元工具支持生成该操作所需的代码。

我先讲好处，再举例。第一，它极大减少上下文，因为你不再一次性把所有可用工具加载进上下文窗口。第二，因为你通过 search 和 execute 交互，接口与你拥有多少 server 无关。任意数量的 MCP server 都可以被索引以供搜索。

有些关于这项技术的研究报告称 token 减少超过 90%。它在业界有不同叫法，但有一个术语值得记住：“code mode（代码模式）”：通过代码生成工具调用并发出 server 请求。

举一个具体例子，假设请求是：“找一个 Jira ticket，并用 Google Drive 里的信息更新它。”对软件工程团队来说，让 LLM 做这件事相当标准。

底层上，会根据该请求动态生成一段代码。它搜索可用工具，并依据请求进行过滤。这里标注的东西并不完全等同于上一页的 search 工具，但它会返回工具并对它们做过滤。

重点在于这段代码是动态生成的，不是你提前写好的块。LLM 看到“找 Jira ticket”的请求，知道自己有 code-mode SDK，就生成代码来取回最相关的工具。

从这个块出来，你就得到了相关工具定义。第二步是 execute。假设 search 返回了用 JQL 搜索 Jira、获取 Google Workspace Drive 内容、更新 Jira ticket 的工具。第二段代码被动态生成，把这些操作串起来。

这个块作为进程执行，而不是由 LLM 本身执行。我们从未把完整工具集加载进模型的上下文。代码被生成并运行（通常在 VM 里），返回相关工具并把结果传递下去。
