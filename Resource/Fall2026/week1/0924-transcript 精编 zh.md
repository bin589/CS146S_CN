## 从 200 行代码到生产级 harness

上一次课在结尾做了一个演示：用大约 150 到 200 行代码搭出编码 agent 的骨架。它能理解用户请求、编辑代码和文件，并生成有一定复杂度的东西，从「Hello, world」起步。那次演示是一次概念验证，说明用 200 行代码可以做到什么程度。今天的课要把大家带到编码 agent 及其 harness 的现代状态，剖开一个最先进编码 agent 的解剖结构，看引擎盖下面发生了什么。

除了智能层——也就是模型——我们能看到一切。模型是私有的：一大批两万亿参数以上的模型分布在各地的服务器上，看不到内部。但围绕它的 harness 是可见的，接下来的内容就是关于这个 harness 意味着什么。

编码 agent 的核心执行循环此前已经讲过：用户与 harness 交互，harness 可以是 Claude、Windsurf 或 Devin；智能层是 LLM，是用复杂训练算法在海量数据上训练出来的一组参数；LLM 再与一组工具来回配合。工具把 LLM 锚定在现实世界中，让它能搜索网络或读写文件系统。用户发出提示词，底层走的就是这个循环：通过界面与 harness 对话，让它与 LLM 交互，再与工具集往返。

这个循环今天仍然成立，但今天关注的是循环周围的一切。循环周围堆着一圈被称为 harness 的部件，而 harness 设计大概是编码 agent——以及更广义的 agent——中最难也最重要的问题之一。课程聚焦编码与软件系统，但其中许多原则适用于任何垂直领域，无论是销售、法律还是客服。

由于要尽量站在最前沿，本次的解剖对象是 Claude Code 的 harness，具体是 Opus 5.5，这个版本大约两天前才发布。按 Anthropic 公布的基准，它是当前最先进的；而就在同一天，OpenAI 也发布了新模型——这两家公司习惯把发布安排在同一个日子。课件的组织方式是在高层原则与实际演示之间来回切换：先给出原则，再当场跑一遍 Claude Code，拦截请求，逐层拆开看。

## harness 的组成清单

有几类部件现在已相当标准：system prompt；自定义配置文件，例如 `AGENTS.md` 和 `CLAUDE.md`；以及工具清单，用来指定当前可用的工具。工具这一部分在上一节课里已经碰过——编辑、列出、读取文件——可以扩展到开箱即用的工具之外。

在此之上还有 plan mode 这类内置模式，让你在 harness 内做别的事情；可以启动 subagent；还有 skills、hooks 和 compaction。这些只是举例，实际塞进 harness 的东西相当多。

在核心循环内部，要考虑三样东西：上下文窗口（本季度会专门花时间讲）、模型（智能层）以及工具执行（上次课讲过）。今天的全部内容都是上一段列出的、循环之外的那些部件。

## 工具清单：约 40 个内置工具

工具是 LLM 在静态权重与训练之外访问真实世界的方式，无论是本地文件系统、计算机上的东西，还是网络上的东西。放进 harness 的工具为 LLM 增强搜索、shell 命令、agent 任务这类能力。这些与编码尤其相关，但同样的原则适用于编码之外的场景；事实上，编码之外的 agent 也越来越多地围绕编码能力来设计，这已经成为为其他领域设计 harness 的一条路径。

Claude Code 下载即用时大约带 40 个内置工具，这是 Anthropic 团队判定编码 agent 应当具备的能力集合。可以再往前推一步：模型本身已经被优化成会用这些工具，这通过后训练之类的过程实现。除原生工具外还有 MCP 工具，也就是把外部工具与资源集成进 harness 的途径；每一个加载过的 MCP server 都会往工具清单里加条目，这部分后面还会展开。

有一个要点在进入示例之前必须先说清楚：可以把一个工具看成函数，就像上次课演示的那样。工具定义里的一切——描述、注释、名字、完整签名——都会成为 prompt 的一部分，被注入上下文。因此，在写一个要暴露给编码 agent 的函数时，Python docstring 的清晰与一致极其重要，参数类型的清晰同样重要。这些内容都会呈现给 LLM，而 LLM 正是靠它们理解该做什么、什么时候该用这个工具。这一点对设计 MCP server、以及为 agent 设计工具都成立。

从截获的请求里可以看到，工具块位于 user 与 assistant 消息之后，`tools` 是一个列表，每个条目是一个字典。以 agent 工具为例：它用来启动一个新的 agent 处理复杂的多步任务，描述里解释了该 agent 的能力，另有一个 schema 可以理解为这个工具的函数签名，其中 `properties` 是调用时可以指定的参数。工具被调用时，这些属性会带上具体的值。定义可以相当繁复，取决于底层工具的复杂度。

把这些原生工具与额外工具（例如 MCP 工具）分开看，约 40 个内置工具大致覆盖这些方面：文件访问；通过 Bash 与 shell 交互；以类似 cron 的方式做定时监控；搜索网络；用 LSP（Language Server Protocol）检索当前语言；agent 专用工具；规划与隔离；调度，包括一个专门的 cron 工具；创建 artifact；列出 MCP 资源（与 MCP 工具不是一回事）；以及与用户交互、调用 skill、提问、推送通知、发送反馈。

关于工具清单还有一个历史观察，如果已经自己搭过 harness 或者准备搭，值得记住。Claude Code 在去年 12 月前后开始流行，原因之一就是它的 harness 极简：很长一段时间里，它只有一组很克制的工具，却几乎能做所有事。40 个在这个语境下并不算多。真正强大的工具例子是 Bash 和 SQL——把文件系统和一个 CLI 交给 LLM，就能完成复杂操作，Bash 本身就是一门完整的语言。

这套设计是在给此前已经膨胀的东西瘦身。早期（2024 年底 MCP 刚出现的时候），GitHub 的 server 开箱就有 110 个左右的工具：列出 issue、创建 issue、给 issue 评论，等等。这些都有用，但占用大量上下文；上下文越膨胀，LLM 在任务上的表现越差。Claude 的贡献在于整合：保持简单，从三到五个能成大事的工具起步，再向外扩展。行业趋势是降低复杂度——用更少的工具做更多的事，寻找那种「瑞士军刀」式的强力工具，SQL 和 Bash 就是两个例子。

MCP 先出现，skills 后引入，引入 skills 的动机之一就是渐进披露：在信息与任务相关时才把它带进上下文。工具清单是把所有工具一次性塞进去，每一个加载过的 MCP server（包括第三方 server）都出现在这个块里，每次发请求都会带上这一整套。skills 初始只带一小段元数据描述它做什么，系统再根据这段元数据和它与任务的相关性，在需要时把 skill 的其余内容拉进来。所以要谨慎选择引入哪些 MCP 工具和 server，因为它们可能把上下文撑爆；无关材料越多，编码 agent 在任务上表现越差。有研究专门看过性能开始下降的拐点出现在多少 token。

**问：** 一次请求里就包含了这全部工具吗？

**答：** 是，全都包含，量确实很大。这也是要花时间讲上下文工程的原因之一。

**问：** 为什么启动 agent 时用自然语言而不是向量？

**答：** 具体细节不清楚，但训练在很大程度上基于自然语言文本，代码和指令都以文本片段表示——无论用于训练的网页语料，还是人工标注的定制数据都是如此。让人用向量或其他非人类可读的格式来沟通会非常困难。

**问：** 截获到的这份 JSON 就是送进模型的形式吗？

**答：** 几乎肯定不是。这是能解析出的、最接近人类可读的形式；被摄取时很可能还有折叠或压缩处理，某些材料会被剥离或转换。想再往下追，就得站在托管 LLM 的服务器上，看 token 化输入送出前的最后一步，那大概率看不到，其中一部分是他们的秘密配方。

**问：** 工具定义里是否带校验和、hash、UID 之类的元数据？

**答：** 有，各类对象上都有 checksum、hash 和 UID。缺少这类东西会造成安全漏洞。

**问：** MCP 工具和 skill 的区别是什么？

**答：** MCP 是一个原语，可以把 MCP 工具几乎看成一个 API 调用，一种输入输出机制。skill 编码的是流程：多个步骤、多次工具调用，以及调用之间的提示词。MCP 工具是与底层第三方资源交互的最小单元；skill 把工具、函数、脚本和其他资源包装成多步操作。这种粒度上的区分是有用的。

MCP 工具靠名字前缀识别：以 `mcp__` 开头（例如 `mcp__claude_ai` 下的 Claude Docs 工具）就是外部工具的标记。Mintlify（文档托管）、Notion、Slack 等等也都有对应的工具，同样会注入到工具清单里。

## 解剖一次请求：trace 演示

演示用一个代理工具拦截 Claude Code 的请求与响应，全班都能拿到。类比对象是 Wireshark：抓网络包，看协议层发生了什么；这里是抓请求与响应并解包。另一个类比是 Chrome 或其他浏览器的调试台。这个工具的好处是能把信息拆开看。

演示对象是一个命令行 to-do 工具，可以添加任务、列出任务、标记完成、添加子任务等等，是讲者 vibe coding 出来之后又主动扩展的。屏幕下方是 CLI 本身，上方是凌晨与 Claude Code 的对话；一堆提示词发出后被捕获，请求被记录成文件。

trace 是一个 JSON 文件，结构清晰、便于解析。里面有模型名，其后是一组 `messages`。上一节课里有过一个随请求不断追加的对话列表，`messages` 对象就是那个列表。角色概念也一样：`user` 角色后面跟着消息内容，有的 user 消息是讲者发出的，也包括工具调用的响应；`system` 级别的消息是 harness 在背后注入的；`assistant` 消息是 Claude 在做事情，例如发出工具调用。每个块都是一条消息，有些被额外充实过，以帮助 Claude 完成工作——这些信息平时看不到，这正是要拦截请求的原因。

演示里的第一条用户消息是「这个 to-do 应用的核心组件有哪些」，因为讲者想重新熟悉一个自己 vibe coding 出来的仓库。它之上还有内容，但那些不是讲者输入的——他没有打过「system reminder」之类的东西，是 harness 加进去的。这门课的第一次作业就是让每个人做类似的事：起一个 Claude Code 实例，发出调用，拦截请求与响应，解包看清背后发生了什么。

## system prompt

system prompt 是 LLM 行为的蓝图，是一段文本，定义 harness 及其行为的若干方面，包括护栏和环境信息。harness 在你什么都没说的时候就注入这段静态文本；你控制不了它，是 harness 设定的；它还会出现在 Claude 发出的每一次请求里。

trace 里与 system prompt 相关的是两个块。第一块只有一句话：`You are Claude Code, Anthropic's CLI for Claude.`——harness 用自然语言告诉 LLM，它作为一个系统是什么。第二块才是实质指令所在，这是 Claude Opus 5.5 的 system prompt，大约 50 行，比之前的版本短不少。

这份蓝图规定的内容包括：你是一个帮助用户完成软件工程任务的交互式 agent；有哪些需要小心的地方，包括与安全有关的指令；harness 是什么、如何与之交互；与会话有关的信息。还有一块相当长的 memory 内容，这是相对较新的机制：一个隐式记忆系统，从用户行为中学习。

memory 存放在文件系统里的特定路径下，每次 LLM 判断应当写入记忆时，prompt 规定了要使用的格式。打开那个路径会看到 Claude 提取出的记忆的元数据块，以及大量关于如何写入和操作这些记忆的指令。此外还有环境信息（哪些 Claude 模型可用）和一点关于上下文管理的内容。

值得强调的是这份 prompt 变短了：直到一两个月前它还有 200 到 250 行，其中很多在解释怎么用 Git、怎么发任务这类内容。那些曾被认为必须显式告诉模型，现在似乎不那么必要了。讲者的推测是，训练过程已经把其中大部分信息吸收进模型参数。这与减少 MCP 工具以避免上下文膨胀是同一个道理：同样要减少超长 system prompt 带来的膨胀。大约一个月前他们把 system prompt 砍掉了约 8%，会尽量往下剥——因为这些东西不是用户写的，却每次请求都占着上下文窗口，第一次请求时可能已经有数万 token 被用户控制之外的材料消耗掉。

**问：** 能不能通过 prompt injection 把 system prompt 套出来？

**答：** 基本做不到，肯定有人试过，简单的尝试应该已经被处理，而且他们有一整个团队专门防这类情况。但这个攻击面没有想象中严重：抓取请求与响应并不难，有开源工具；而且半年前整个系统已经泄露过一次，所以这也不完全是他们的选择。讲者用的是普通的、Wireshark 式的检查，在泄露之前就能做到。泄露发生时大家说「现在我们知道 Claude 怎么工作了」，其实之前就知道。Codex 也可以同样处理，它的 harness 直接放在 GitHub 上。所以 harness 的可见性并没有那么大的攻击价值。

**问：** memory 是每个 Claude Code 执行实例本地的，还是别的形式？

**答：** 从路径定义看是项目级的，可以看到代码所在路径，其他项目会有类似的布置。

**问：** memory 会追加到 system prompt 里吗？

**答：** 「追加」这个词太重。它们是各自独立的块，会被拼接进请求里发出的 prompt。它是 prompt 的一部分，但仍应当看作与 system prompt 本身不同的对象。

**问：** 检索记忆时用 RAG 或 GraphRAG 拉相关记忆，还是别的做法？

**答：** 这些设计取舍是基准驱动的。结论是这类系统增加的复杂度并不总能带来多少优势，不如让系统直接解析平文本。研究和基准都看过这个问题，具体取决于任务，所以不下笼统结论。讲者所在公司自建了 harness 和 agent，做的是销售而不是编码，最终也用平文件存记忆。

## 配置文件：CLAUDE.md 与 AGENTS.md

这类文件是 agent 配置文件。`CLAUDE.md` 是 Claude 专用的，`AGENTS.md` 是更通用的标准。此前看起来所有人都已经同意用 `AGENTS.md`，只有 Anthropic 想另搞一套；几周前他们也开始加入。可以把 `CLAUDE.md` 软链接到 `AGENTS.md`，试图与众不同在这个例子里并没有带来好处。两者在功能上相同，运行方式相同，目的相同，只是名字不同；在 Codex 和 Anthropic 之间切换时会带来一点摩擦，算是一堵非常薄的花园围墙。

与 system prompt 相比，这是用户可控的对应物：system prompt 是静态的、由 harness 设定、在背后注入；`CLAUDE.md` 同样被注入，但由用户控制，因此改它就是改 agent 的行为。在演示的 to-do 应用里有一个 `CLAUDE.md`，高层描述了项目结构，是讲者和 Claude 一起写的。它被注入的位置在用户消息块之上：那个块的开头说这些指令会覆盖默认行为、必须严格照写执行，然后给出 `CLAUDE.md` 的路径，再把内容贴进来。这里就是用户对 LLM 或编码 agent 行为有控制权的地方。

关于 `CLAUDE.md` 或 `AGENTS.md` 的共识是：写一些运行代码的指引——怎么跑测试、怎么起服务——但不要太多。这是一条细线，写多了会过度约束系统，几乎把系统过拟合到你的指令上。通常不会把整块代码放进去，最多放一两条命令：跑单元测试的那条、起服务的那条。演示里那块内容并不是 trace 中独立存在的 Markdown 文件，而是从 JSON 里抽出来存进一个空文件的，做成 `.md` 只是为了比纯文本好看一些。

## plan mode

plan mode 是与这类 agent 对话时可用的一种模式，专门用来设计规格、推进较难的任务。大约九个月甚至更早之前，多数编码 agent harness 都引入了 plan mode，用来与用户来回澄清需求与架构。

Claude Code 里进入该模式有一个工具，harness 会注入一段文本说明该做什么；结束时另有一个工具退出该模式。这段 plan-mode prompt 就是一段文本，但思路可以推广到几乎所有现代 harness，包括 Codex。它的流程是分阶段的：第一阶段理解用户需求，harness 说明了该怎么做，其中甚至包括启动 agent 去探索代码库；第二阶段是设计；之后是评审阶段、最终计划，以及完成时退出 plan mode 的指令。最后产出的 artifact 是 plan 文件，即走完规划步骤后的产物。

演示里想给 to-do 应用加上定时任务或周期性提醒，比如「每周给植物浇水」。进入 plan mode，来回沟通，生成了一份计划；整个过程从注入那段 prompt 开始，LLM 照它执行，双方一起把计划推出来。

## skills

skills 的核心是写下来的流程，可以包含多次工具调用、脚本，以及把它们串起来的提示词，从而完成更精细的任务。skill 可以由上下文主动触发，也可以由用户显式调用：可以让它评审代码，也可以让它检测到任务完成后自行调用代码评审 skill。

结构上是定义一个 `SKILL.md` 文件。讲者为这门课写了一个叫 `check code quality` 的 skill，里面描述了要做什么、好的代码质量与差的代码质量分别是什么样。

在 trace 里可以看到调用过程：在对话的某一处显式调用该 skill——「检查我的代码质量，用这个 skill」——底层注入了一个带有 `check code quality` 命令的文本块，告诉 LLM 现在该检查代码质量了；随后 harness 定位到 skill 文件，把内容插入上下文。这也是 skill 与普通提示词的区别所在：提示词随用户输入进入上下文，而 skill 的正文是由 harness 在触发时按需加载的。

## subagent

subagent 用来把任务的一部分委派出去。有一个主控 agent，也就是 Claude Code 的主控制循环，可以调用带独立、全新上下文窗口的助手或 worker。这样可以并行，也可以为不同任务定义不同行为。worker 完成后把输出交回主 agent。好处是每个 subagent 从干净上下文开始，而不是继承父级的全部上下文；它的探索发生在主控制流之外，结果在完成时被带回，是一种更有效地管理上下文的方式。

演示的 trace 里调用过一次 subagent，能看到对应的工具调用：一个 agent 通过工具调用被派生出来，做完工作，返回结果。父会话里留下的是这次调用的请求与结果，子 agent 自己的探索过程不在主控制流里展开。

## hooks 与 compaction

hooks 只简要提及，不展开。最后一个大主题是 compaction：当上下文越来越长，compaction 把它整合、摘要，降低上下文膨胀。它像 plan mode 一样是一种模式，触发方式有两种：自动——即将超出上下文窗口时（也许是接近一百万 token 或该模型的上限）；手动——自己调用。有整套 prompt 规定如何生成摘要，摘要随后替换它所摘要的那段上下文。例如把 50 万 token 压成 15 万，此后 LLM 看到的就是压缩后的版本。

## 收尾：模型与 harness 的跷跷板

以上大致展示了更复杂的 harness 里都有些什么：核心循环周围有大量附加部件，但趋势是走向简单，仍然希望工具更少、更强。没有前后对比很难直接演示这一点，但 Claude 的约 40 个原生工具，相比过去版本的 harness 已经是一个更小的集合。harness 设计者越来越依赖底层模型的能力，而不是让 harness 替困难任务扛起重活。

这是 agent 设计里的大问题：投资模型还是投资 harness？行业在这两端之间反复摇摆。有时人们说价值和公司的护城河在 harness 里；随后又指向训练 LLM 花掉的数十亿美元，主张投资应该投向模型。眼下所处的时点，是希望 harness 尽量简单、精炼；在里面仍然可以做有意思的事，只要小心别把上下文撑爆。

还会讲到所谓的「dumb zone」——这不是正式术语，只是一个非正式叫法，指 LLM 开始变得不那么有效的区间。如何避开它，会牵出很多上下文工程的原则。

关于 harness 简单性的最后一点：prompt 长度是来回变化的，有时长有时短。目前倾向于更短的 prompt，因为要避免上下文膨胀、要照顾上下文窗口，短 prompt 也更容易针对任务调整。下节课会继续深入。
