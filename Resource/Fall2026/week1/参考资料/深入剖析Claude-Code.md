Claude Code 是一个代理式（agentic）编程工具，可以代替用户运行 shell 命令、编辑文件并调用外部服务。本研究通过分析公开可用的 TypeScript 源代码ᵃ，并将其与两个独立的开源 AI 代理系统 OpenClaw 与 Hermes Agent 进一步比较，来描述其完整架构；这两个系统从不同的部署情境出发，回答了诸多相似甚至相同的设计问题。我们的分析识别出驱动这一架构的五种人类价值、哲学与需求：人类决策权，安全、保障与隐私，可靠执行，能力放大，以及情境适应性。随后，我们沿十三条设计原则将它们追溯至具体的实现选择。系统的核心是一个简单的 while 循环：调用模型、运行工具，然后重复。然而，大部分代码存在于这个循环周围的各个系统之中：一个具有七种模式和基于机器学习的分类器的权限系统，一条用于上下文管理的五层上下文压缩（compaction）流水线，四种可扩展机制（MCP、插件、技能与钩子），一种子代理（subagent）委派与编排机制，以及面向追加（append-oriented）的会话存储。与 OpenClaw（一个多通道个人助理网关）和 Hermes Agent（一个单进程、多界面的助理）的比较表明，相同的设计问题在三种部署情境下会产生不同的答案。Claude Code 强调逐操作的安全性，OpenClaw 强调边界级访问控制，而 Hermes 则在众多界面上呈现逐操作审批。在运行时层，Claude Code 使用单一的 CLI 循环，OpenClaw 将运行时嵌入网关控制平面，Hermes 则使用一个由其入口点设定角色的进程。在上下文与扩展层，Claude Code 扩展上下文窗口，OpenClaw 注册网关级能力，Hermes 提供可插拔的记忆与模型后端。最后，我们以近期的实证、架构与政策文献为基础，提出未来代理系统的六个开放设计方向。我们的 GitHub 地址为：https://github.com/VILA-Lab/Dive-into-Claude-Code。

## 1 引言

AI 辅助软件开发已从 GitHub Copilot (Chen et al., 2021) 这类自动补全式工具，经由 Cursor (Cursor, 2026) 这类 IDE 集成助手，演进为能够自主规划多步修改、执行 shell 命令、读写文件并迭代自身输出的完全代理式系统。Claude Code (Anthropic, 2026a) 是 Anthropic (Anthropic, 2026g) 发布的代理式编程工具。其官方文档描述了一个“代理循环（agentic loop）”，它规划并执行朝向目标完成的动作，可以调用工具、评估结果，并持续进行直到任务完成¹。这种从建议到自主行动的转变引入了基于补全的工具所没有对应物的架构需求。这些需求定义了一个设计空间（design space），即一组反复出现的问题，涵盖安全性、上下文管理、可扩展性与委派等主题，每一个编程代理都必须应对。本研究利用对 Claude Code 的源代码级分析，展示一个生产系统如何回答这些问题。

尽管采用率不断增长，Anthropic 只为 Claude Code 发布了面向用户的文档，而没有详细的架构描述。本研究使用源代码分析来描述架构设计决策。Anthropic 对 132 名工程师与研究人员所做的内部调查 (Huang et al., 2025) 报告称，约 27% 的 Claude Code 辅助任务是在没有该工具的情况下根本不会被尝试的工作，这表明该架构促成了性质上全新的工作流，而不只是加速了现有的工作流。

在本工作中，我们首先识别出驱动这一架构的五种人类价值/哲学与十三条设计原则（第 2 节），然后将分析组织为三个部分：

1. 设计空间分析。我们识别反复出现的设计问题（推理发生在何处、迭代循环如何组织、采取何种安全姿态、扩展面如何划分、上下文如何管理、工作如何在子代理之间委派，以及会话如何持久化），并通过一个 7 组件的高层结构和 5 层子系统架构来分析 Claude Code 的答案，将每一项选择追溯到具体的源文件（第 3 节）。该分析旨在建立对系统机制的深入理解，目标是为更好、更强大的代理系统的设计提供参考。
2. 与 OpenClaw 和 Hermes Agent 的架构对比。除了分析 Claude Code 本身，我们还在六个设计维度上将其设计哲学与两个开源代理系统的设计哲学进行比较：OpenClaw (Steinberger and OpenClaw Contributors, 2026)（一个多通道个人助理网关）与 Hermes Agent (Nous Research, 2026)（一个单进程、多界面的助理），以展示相同的反复出现的问题在不同部署情境下如何产生不同的答案（第 10 节），从而既突显共同原则，也突显商业软件与开源软件之间的关键差异。这一比较有助于揭示部署环境、产品目标、安全要求与用户假设如何以不同方式塑造架构选择。通过考察这些系统在何处趋同、在何处分歧，本研究旨在为未来更强大的代理系统的设计提供有用的指导与实践洞见。
3. 未来代理系统的开放方向。在设计空间分析以及 OpenClaw 与 Hermes 对比的基础上，第 13 节识别出六个开放方向，涵盖可观测性—评估鸿沟、跨会话持久化、执行框架（harness）边界演化、时间跨度扩展（horizon scaling）、治理，以及长期开发者能力，每一个方向都借鉴了实证、架构与政策文献。长期能力问题还揭示出一个尚未解决的关切：虽然 Claude Code 代理系统放大了程序员与最终用户的短期能力，但它所提供的、明确支持人类长期提升、更深入理解与代码库持续一致性的机制却很有限。

核心代理循环是一个带有状态管理的 while-true 循环。围绕它的、用于安全性、可扩展性、上下文管理、委派与持久化的各个子系统构成了实现的主体。源代码级分析²使我们能够直接从系统本身识别设计选择、子系统边界与实现权衡，而不是仅从产品描述中推断它们。

**贯穿案例（Running example）。** 为使架构保持具体，我们在第 3 节至第 9 节中贯穿追踪任务“修复 `auth.test.ts` 中失败的测试”。这个例子说明了看似简单的用户请求如何激活多个架构层，包括工具调用、权限检查、上下文选择、迭代修复、委派与会话持久化。

**论文组织。** 第 2 节识别驱动该架构的人类价值与设计原则。第 3 节介绍高层架构及其所回答的设计问题。第 4 节至第 9 节各自分析一个主要子系统的设计选择。第 10 节将分析与 OpenClaw 和 Hermes Agent 进行对比，第 11 节将本工作置于先前的代理与软件工程文献之中，第 12 节提供讨论，第 13 节综述未来代理系统的开放问题，第 14 节作结。附录描述了证据基础与方法、包结构说明、社区重新实现，以及一份从新的代理系统信号到本文设计空间问题的对照映射。

## 2 设计哲学、设计原则与架构动机

生产级编程代理由人类构建、为人类服务，它们所嵌入的架构决策反映了其创造者认为重要的事物。本节识别驱动 Claude Code 设计的人类价值，沿反复出现的设计原则将其追溯，并框定组织第 3 节至第 9 节分析的设计空间问题。

Anthropic 关于安全代理的框架陈述了一个核心张力：“代理必须能够自主工作；正是其独立运作使其具有价值。但人类应当保留对目标如何被追求的控制权” (Anthropic, 2025a)。Claude 的宪法（Constitution）并非通过僵化的决策程序，而是通过培养“能够在具体情境中运用的良好判断力与健全价值观”来解决这一问题 (Anthropic, 2026b)。这些承诺，连同关于开发者实际如何使用该工具的实证发现 (Huang et al., 2025; McCain et al., 2026)，指向五种塑造该架构的人类价值。

### 2.1 五个价值观与哲学

**人类决策权（Human Decision Authority）。** 人类对系统所做之事保留最终决策权，这种权力通过一个主体层级（principal hierarchy，即 Anthropic、然后是运营者、然后是用户）来组织，从而形式化谁对什么拥有权力 (Anthropic, 2026b)。系统的设计使人类能够行使知情控制：他们可以实时观察动作、批准或拒绝提议的操作、中断兼容的进行中操作，并在事后进行审计。当 Anthropic 发现用户批准了 93% 的权限提示 (Hughes, 2026) 时，其回应不是增加更多警告，而是重构问题本身：划定明确的边界（沙箱、自动模式分类器），代理可以在其中自由工作，而不是依赖用户在习惯化之后便不再审阅的逐操作审批 (Dworken and Weller-Davies, 2025)。

**安全、保障与隐私（Safety, Security, and Privacy）。** 系统保护人类、其代码、其数据及其基础设施免受伤害，即使人类注意力不集中或犯了错误。这与人类决策权不同：权力关乎人类进行选择的能力，而安全关乎系统即使在该能力失效时仍负有保护的义务。Anthropic 的安全代理框架将保障代理交互的安全，以及在长期交互中保护隐私，分别列为核心承诺 (Anthropic, 2025a)。自动模式威胁模型 (Hughes, 2026) 明确针对四类风险：过度急切的行为、诚实的错误、提示注入（prompt injection）与模型失准（model misalignment）。

**可靠执行（Reliable Execution）。** 代理做人类真正想做的事，随时间保持连贯，并支持在宣称成功之前验证其工作。这一价值既涵盖单轮正确性（它是否忠实地理解了请求？），也涵盖长时程可靠性（它是否在上下文窗口边界、会话恢复与多代理委派之间保持连贯？）。Anthropic 的产品文档 (Anthropic, 2026h) 描述了一个三阶段循环，代理重复该循环直到任务完成：收集上下文、采取行动、验证结果。代理设计指南 (Schluntz and Zhang, 2024) 进一步强调，每一步都“从环境中获取基准事实（ground truth）”以评估进展。执行框架设计指南 (Rajasekaran, 2026) 同样指出，“代理倾向于以自信的态度称赞工作”，即使质量平平，这促使人们将生成与评估分离。

**能力放大（Capability Amplification）。** 系统实质性地提高人类在单位努力与单位成本下所能完成的事情。第 1 节中讨论的 Anthropic 内部调查 (Huang et al., 2025) 表明，该架构促成了性质上全新的工作流，而不仅仅是更快的现有工作流：约 27% 的任务是原本不会被尝试的工作。其创造者将该系统描述为“一个 Unix 实用工具，而非传统产品”，由“有用、可理解且可扩展”的最小构件搭建而成 (Cherny and Wu, 2025)。该架构投资于确定性的基础设施（上下文管理、工具路由、恢复），而不是决策脚手架（显式规划器或状态图），其前提是：能力日益增强的模型从丰富的操作环境中获益，多于从限制其选择的框架中获益。

**情境适应性（Contextual Adaptability）。** 系统契合用户的具体情境（其项目、工具、约定与技能水平），且这种关系随时间改善。扩展架构（`CLAUDE.md`、技能、MCP、

钩子（hook）、插件（plugin））在多个上下文开销层级上提供了可配置性（第 6、7 节）。纵向数据（McCain et al., 2026）显示，人机（human-agent）关系会随时间演化：自动批准率从不足 50 次会话时的约 20% 上升到 750 次会话时的 40% 以上。这种模式被描述为"由模型、用户和产品共同建构"的自主性，意味着系统是为信任的演化轨迹而非固定的信任状态而设计的。MCP 被捐赠给 Linux 基金会的 Agentic AI Foundation（The Linux Foundation, 2025），这体现了该价值的生态维度。

### 2.2 设计原则

这些价值通过十三条设计原则得以落地，每条原则回答一个生产级编程代理必须解决的重复出现的问题。表 1 汇总了这些原则；后续各节（第 3 节至第 9 节）将逐条追踪它们在具体实现选择中的体现。

**表 1** 设计原则、所服务的价值，以及各自回答的设计空间问题。

| 原则 | 所服务的价值 | 设计问题 | 章节 |

### 2.3 从价值到架构

每一项价值都经由其原则追溯到具体的架构决策：

- 人类决策权威促成了拒绝优先评估、渐进式信任谱系、仅追加（append-only）状态（可审计的历史）、外部化可编程策略，以及价值高于规则（第 5 至第 7 节及第 9 节）。
- 安全、保障与隐私促成了纵深防御、拒绝优先的默认值、按可逆性加权的评估、外部化策略，以及隔离的子代理边界（第 5 节和第 8 节）。
- 可靠执行促成了将上下文视为稀缺资源、仅追加的持久状态、优雅恢复、隔离的子代理边界，以及纵深防御（第 4 节及第 7 至第 9 节）。
- 能力放大促成了最小化脚手架、可组合扩展性、按可逆性加权的风险、上下文管理，以及优雅恢复（第 4 至第 6 节）。
- 语境适应性促成了透明的基于文件的记忆、可组合扩展性、渐进式信任谱系，以及外部化可编程策略（第 5 至第 7 节）。

这些映射也揭示了该架构没有做什么：它没有对模型的推理施加显式的规划图，没有提供单一统一的扩展机制，也没有在恢复会话时复原所有与会话范围内的信任相关的状态。这些"缺席"与上述原则集合是一致的。

### 2.4 一个横切问题：开发者的长期能力

以上五项价值描述了该架构被设计来服务的内容。本文还提出第六个问题：该架构是否有助于开发者保持长期的理解力与能力。这一关切是真实的：Anthropic 自身对 132 名工程师与研究者的研究（Huang et al., 2025）记录了一种"监督悖论"，即对 AI 的过度依赖有可能会使监督 AI 所需的技能退化；而独立研究（Shen and Tamkin, 2026）发现，在 AI 辅助条件下，开发者在理解力测试中的得分低 17%。然而，这一关切在该架构中、以及在 Anthropic 所声明的设计价值中，并未作为设计驱动力得到显著体现。因此，我们不把它当作同等并列的价值，而将其视为一个横切关切：这是一个在第 12 节中横跨全部五项价值加以追问的问题——短期的能力放大是否以长期的人类理解力、代码库的一致性和开发者培养链路为代价。

## 3 架构总览

构建一个生产级编程代理需要回答若干反复出现的设计问题：推理应当位于何处，需要多少个执行引擎，采取何种安全姿态，以及把什么资源视为有约束力的限制。Claude Code 的架构可以被读作对这些问题的某一组回答。在实现层面，该系统有七个组件，由一条主数据流连接：用户通过若干接口之一提交提示词，提示词汇入一个共享的代理循环。代理循环组装上下文、调用 Claude 模型、接收可能包含工具调用（tool use）请求的响应、把这些请求路由通过权限系统，并将获准的动作分派给与执行环境交互的具体工具。在整个过程中，状态与持久化机制记录对话转录、管理会话身份，并支持恢复（resume）、分叉（fork）和回退（rewind）操作。

### 3.1 设计问题与贯穿案例

本描述围绕四个在生产级编程代理中反复出现的设计问题来组织，每个问题都为表 1 中识别出的一条或多条设计原则提供依据。此处先逐一介绍每个问题，并给出 Claude Code 的答案、对可能的替代方案的说明，然后在第 4 至第 9 节中逐步展开论证。

**推理发生在哪里？** 在 Claude Code 中，模型对做什么进行推理；执行框架（harness）负责执行动作。模型在其响应中发出 `tool_use` 块，执行框架解析它们、检查权限、将其分派给工具实现，并收集结果（`query.ts`）。模型从不直接访问文件系统、运行 shell 命令或发起网络请求。这种分离具有安全上的后果：由于推理与强制执行位于不同的代码路径，一个被攻陷或被对抗性操纵的模型无法覆盖在执行框架中实现的沙箱、权限检查或拒绝优先规则。模型与外部世界之间唯一的接口是结构化的 `tool_use` 协议，执行框架会在执行前对其加以校验。社区对抽取出的源代码的分析估计，Claude Code 的代码库中只有约 1.6% 构成 AI 决策逻辑，其余 98.4% 是运维基础设施，这一比例说明核心的代理推理层有多么薄。替代性设计则在脚手架侧的推理上投入更多：Devin 维护显式的规划与任务跟踪结构，而 LangGraph（LangChain, Inc., 2024）通过开发者定义的状态图来路由控制流。

**需要多少个执行引擎？** Claude Code 使用单个 `queryLoop()` 函数，无论用户是通过交互式终端、无头 CLI 调用、Agent SDK 还是 IDE 集成进行交互，该函数都照常执行（`query.ts`）。只有渲染与用户交互层存在差异。其他系统使用针对特定模式的引擎：例如，IDE 集成可能走与 CLI 工具不同的代码路径，以统一性换取针对特定界面的优化。

**默认的安全姿态是什么？** Claude Code 的默认安全姿态是拒绝优先并升级至人类：拒绝规则覆盖询问规则，询问规则覆盖允许规则，未被识别的动作会被升级给用户，而不是被静默允许（`permissions.ts`）。多个彼此独立的安全层（权限规则、`PreToolUse` 钩子、启用时的自动模式分类器，以及可选的 shell 沙箱）被叠放起来，因此任何一层都可以阻止某个动作（第 5 节）。这把表 1 中的"拒绝优先并升级至人类"与"纵深防御与分层机制"两条原则结合起来。替代方案则把信任边界移到别处：SWE-Agent 与 OpenHands（Yang et al., 2024; Wang et al., 2024b）依赖基于容器的隔离来容纳任意执行，而 Aider（Gauthier, 2024）把基于 git 的回滚作为其主要安全网。

**什么是有约束力的资源限制？** 在 Claude Code 中，上下文窗口（较早的模型为 200K，Claude 4.6 系列为 1M）是有约束力的资源限制。每次模型调用前都会执行五种不同的上下文缩减策略（`query.ts`），此外还有其他若干子系统决策（指令的按需加载（lazy loading）、延迟加载的工具模式、仅返回摘要的子代理）用于限制上下文消耗（第 7 节）。之所以存在这条五层流水线，是因为没有任何单一的上下文压缩（compaction）策略能够应对所有类型的上下文压力。预算削减针对溢出尺寸限制的单个工具输出。Snip 处理时间上的深度。Microcompact 对缓存开销作出反应。Context collapse 管理极长的历史。Auto-compact 则作为最后手段执行语义压缩。

> [图 2]

**图 2** 运行时回合流程，展示单个代理回合的端到端执行：用户提示经上下文组装进入，模型被调用，工具请求通过权限闸门，工具结果反馈回循环，上下文压缩（compaction）管理上下文压力。

每一层都在不同的成本收益权衡下运作，更早、更便宜的层先于更昂贵的层运行。替代架构则把其他资源视作主要瓶颈，例如计算预算（限制模型调用或工具调用的次数）或工作记忆（维护一个显式的暂存区，而不是依赖对话历史）。

### 3.2 高层系统结构

七组件模型（图 1）直接对应到源文件：

1. 用户（User）：提交提示、批准权限、审阅输出。
2. 接口（Interfaces）：交互式 CLI、无头 CLI（`claude -p`）、Agent SDK，以及 IDE/Desktop/Browser。所有界面都汇入同一个循环。
3. 代理循环（Agent loop）：模型调用、工具分派与结果收集的迭代周期，在 `query.ts` 中实现为 `queryLoop()` 异步生成器。
4. 权限系统（Permission system）：拒绝优先（deny-first）的规则评估（`permissions.ts`）、自动模式的机器学习分类器，以及基于钩子（hook）的拦截（`types/hooks.ts`）。
5. 工具（Tools）：最多 54 个内置工具（19 个无条件启用，35 个取决于功能开关和用户类型），通过 `assembleToolPool()`（`tools.ts`）组装，并与 MCP 提供的工具合并。插件通过 MCP 服务器以及技能/命令注册表间接做出贡献。
6. 状态与持久化（State & persistence）：主要是仅追加（append-only）的 JSONL 会话记录（`sessionStorage.ts`）、全局提示历史（`history.ts`），以及子代理侧链文件。
7. 执行环境（Execution environment）：带可选沙箱的 shell 执行（`shouldUseSandbox.ts`）、文件系统操作、网页抓取、MCP 服务器连接以及远程执行。

> [图 3]

**图 3** 扩展的分层架构，展示五个子系统层：表层（交互式 CLI、无头 CLI、Agent SDK、IDE/Desktop/Browser、UI/渲染器）、核心层（代理循环、上下文压缩管线）、安全/行动层（权限系统，含自动模式分类器、钩子管线、可扩展性、内置工具、MCP 工具、shell 沙箱、子代理派生）、状态层（上下文组装、运行时状态、会话持久化、CLAUDE.md + 记忆、侧链记录）以及后端层（执行后端、外部资源）。

数据流沿一条从左到右的主轴展开：用户通过某个接口提交请求，请求随即进入代理循环。循环向权限系统提出动作；获准的动作到达工具，工具与执行环境交互，并把 `tool_result` 消息返回循环。状态与持久化位于循环旁边，记录会话记录并加载先前的会话数据。

应用入口点 `main()`（位于 `main.tsx`）初始化安全设置（包括用于防止 Windows PATH 劫持的 `NoDefaultCurrentDirectoryInExePath`），注册用于优雅关停的信号处理器，并分派到相应的执行模式。

### 3.3 分层子系统分解

五层分解（图 3）把七组件模型扩展为粒度更细的视图，将每一层映射到具体的源码目录。

**表层（入口点与渲染）。**

`src/entrypoints/` 目录包含各条启动路径，其中包括带有 `coreTypes.ts`、`controlSchemas.ts` 和 `coreSchemas.ts` 的 SDK 入口。`src/screens/` 目录组合出全屏布局，`src/components/` 则通过 ink 框架提供终端 UI 构件。交互式 CLI 启动一个带实时流式输出、权限对话框和进度指示器的终端 UI。无头 CLI（`claude -p`）创建 `QueryEngine` 实例——它是对共享查询路径（第 3.4 节）的一层薄会话封装——用于单次处理。Agent SDK 通过异步生成器发出带类型的事件。

**核心层（代理循环、上下文压缩管线）。**

`queryLoop()` 异步生成器（`query.ts`）实现迭代式代理循环，消费来自状态层已组装好的上下文，并把工具请求分派给安全/行动层。在每次模型调用之前，由五个顺序执行的重塑器（shaper）组成的压缩管线（`query.ts:365-453`）管理上下文压力：预算缩减、剪裁（snip）、微压缩（microcompact）、上下文折叠（context collapse）和自动压缩（auto-compact）（第 4.3 节和第 7.3 节）。

**安全/行动层（权限系统、钩子、可扩展性、工具、沙箱、子代理）。**

权限系统（`permissions.ts`）实现拒绝优先的规则评估，支持多达七种权限模式（若把仅内部使用的 bubble 和受功能开关控制的 auto 也算入）（`types/permissions.ts`），并集成了一个自动模式的机器学习分类器（`yoloClassifier.ts`），它对工具安全性提供两阶段的快速过滤与思维链评估（第 5 节）。一条跨越 27 种事件类型的钩子管线（`coreTypes.ts`；输出模式见 `types/hooks.ts`）可以阻断、改写或标注工具请求；其中 5 种与安全相关，其余 22 种服务于生命周期与编排目的（第 6 节）。可扩展性子系统允许插件（plugin）和技能（skill）向运行时注册工具与钩子。通过 `assembleToolPool()`（`tools.ts`）完成的工具池组装会合并内置工具与 MCP 提供的工具。获准的 shell 命令会经过 shell 沙箱（`shouldUseSandbox.ts`），它独立于权限系统限制文件系统与网络访问。通过 `AgentTool`（`AgentTool.tsx`、`runAgent.ts`）进行的子代理（subagent）派生与所有其他工具一样，经由同一个 `buildTool()` 工厂分派，带着隔离的上下文窗口重新进入 `queryLoop()`，并且只向父级返回一份摘要（第 8 节）。

**状态层（上下文组装、运行时状态、持久化、记忆、侧链）。**

上下文组装是一个带记忆化（memoized）的状态加载器，而非路由枢纽：`getSystemContext()`（`context.ts`）计算会话级系统上下文，其中包含 git 状态；`getUserContext()`（`context.ts`）加载 CLAUDE.md 层级结构和当前日期。两者都被缓存以便复用：系统上下文被追加到系统提示之后，而用户上下文则作为一条用户上下文消息加入。`src/state/` 目录管理运行时应用状态。会话记录以近乎仅追加的 JSONL 文件存储在项目特定路径下（`sessionStorage.ts`）。CLAUDE.md + 记忆子系统提供四级指令层级（`claudemd.ts`），从受管设置一直到目录特定的文件，此外还有 Claude 在对话过程中写入的自动记忆条目（第 7.2 节）。侧链记录（`sessionStorage.ts:247`）把每个子代理的对话存入单独的文件，从而避免子代理内容撑大父级上下文（第 8.3 节）。全局提示历史维护在 `history.jsonl` 中（`history.ts`）。恢复（resume）与分叉（fork）操作从会话记录中重建会话状态（`conversationRecovery.ts`）。

**后端层（执行后端、外部资源）。**

带可选沙箱的 shell 命令执行（`BashTool.tsx`、`PowerShellTool.tsx`）、远程执行支持（`src/remote/`）、跨多种传输变体（包括 stdio、SSE、HTTP、WebSocket、SDK 以及 IDE 专用适配器）的 MCP 服务器连接（`services/mcp/client.ts`），以及 `src/tools/` 中 42 个工具子目录实现的具体工具逻辑。

### 3.4 QueryEngine：一处澄清

`QueryEngine.ts` 中的类文档写道：“QueryEngine 拥有一次对话的查询生命周期与会话状态。它把核心逻辑从 `ask()` 中抽取为一个独立类，可供无头/SDK 路径以及（在未来的阶段）REPL 共同使用。” 该类是非交互式界面的一层会话封装，而不是引擎本身。其构造函数接受一个 `QueryEngineConfig`，其中包含初始消息、一个中止控制器、一个文件状态缓存以及其他按对话划分的状态。其 `submitMessage()` 方法是一个异步生成器，负责编排单个回合。共享的查询路径位于 `query()`（`query.ts`）中，它包装了一个内部的 `queryLoop()`；`QueryEngine` 委托给 `query()`。

这一区分在架构上很重要：交互式 CLI 也调用 `query()`，从而完全绕过 `QueryEngine`。共享的代码路径是循环函数，而不是引擎类。

### 3.5 权限与安全层

“默认安全”（safety-by-default）原则通过七个相互独立的层来实现。一个请求必须穿过所有适用的层，而任何单独一层都可以将其阻断：

1. 工具预过滤（`tools.ts`）：被整体拒绝的工具会在任何调用发生之前就从模型的视野中移除，从而防止模型尝试调用它们。
2. 拒绝优先的规则评估（`permissions.ts`）：拒绝规则始终优先于允许规则，即使允许规则更为具体。
3. 权限模式约束（`types/permissions.ts`）：当前激活的模式决定了对不匹配任何显式规则的请求的基线处理方式。
4. 自动模式分类器：在自动模式（auto mode）下，基于机器学习的分类器可以评估在规则评估和快速路径检查之后仍需批准的请求；在自动模式激活期间，那些会绕过它的被选中的允许规则（例如 `Bash(*)`）会被搁置。

5. Shell 沙箱（`shouldUseSandbox.ts`）：已获批准的 shell 命令仍可能在限制文件系统与网络访问的沙箱内执行。
6. 恢复会话时不还原权限（`conversationRecovery.ts`）：会话作用域的权限不会写入会话记录（transcript），因此在新进程中恢复的会话启动时并不带有这些权限。
7. 基于钩子的拦截（`types/hooks.ts`）：`PreToolUse` 钩子可以修改权限决策；`PermissionRequest` 钩子可以与用户对话框并行地（或在协调器模式下先于它）异步给出决策。

这些层次将在第 5 节中详述。

### 3.6 上下文作为瓶颈：超越上下文压缩

除了五层上下文压缩管线（详见第 7 节）之外，还有若干其他子系统的设计决策反映了"上下文即瓶颈"这一约束：

- `CLAUDE.md` 按需加载（lazy loading）：基础的 `CLAUDE.md` 层级在会话启动时加载，但额外的嵌套目录指令文件与条件规则只有在代理读取那些目录中的文件时才加载，从而避免未使用的指令占用上下文。
- 延迟加载的工具模式（tool schema）：当启用 `ToolSearch` 时，部分工具在初始上下文中只包含其名称；完整的模式按需加载。
- 子代理仅返回摘要：子代理只向父代理返回摘要文本，而不返回其完整的对话历史（第 8 节）。
- 单条工具结果预算：单条工具结果被限制在可配置的大小内，防止某个冗长的输出占用不成比例的上下文。

## 4 轮次执行：代理式查询循环（Agentic Query Loop）

当用户提交"修复 `auth.test.ts` 中失败的测试"时，该输入进入一个响应式循环（reactive loop），这是编码代理可能的多种编排模式之一。本节考察 Claude Code 选择简单 `while` 循环架构的理由，并端到端地追踪该循环的一个轮次，以此说明表 1 中的三条设计原则：最小脚手架配以最大化的运行时执行框架、上下文作为稀缺资源并加以渐进式管理、以及优雅恢复与韧性。

### 4.1 查询管线

每个轮次都遵循固定的顺序（图 2，`query.ts`）：

1. 设置解析。`queryLoop()` 函数解构出不可变参数，包括系统提示（system prompt）、用户上下文、权限回调与模型配置。
2. 可变状态初始化。单一的 `State` 对象保存跨迭代的所有可变状态，包括消息、工具上下文、压缩追踪与恢复计数器。该循环的七个继续点（"continue sites"）各自以整对象赋值的方式覆写该对象，而不是逐个字段地修改。
3. 上下文装配。函数 `getMessagesAfterCompactBoundary()` 从最近的压缩边界向后取回消息，确保被压缩的内容由其摘要而非原始消息来代表。
4. 模型调用前的上下文整形器（context shaper）。五个整形器依次执行（第 4.3 节）。
5. 模型调用。一个 `for await` 循环遍历 `deps.callModel()`，流式接收模型的响应，并传入装配好的消息（前置了用户上下文）、完整的系统提示、思考（thinking）配置、可用工具集、中止信号（abort signal）、当前模型规格，以及包括快速模式设置、努力值（effort value）与备用模型在内的其他选项。
6. 工具调用分派。如果响应中包含 `tool_use` 块，它们会流向工具编排层（第 4.2 节）。
7. 权限门。每个工具请求都要经过权限系统（第 5 节）。
8. 工具执行与结果收集。工具结果以 `tool_result` 消息的形式加入对话，循环继续。
9. 停止条件。如果响应中不含 `tool_use` 块（仅文本），则该轮次结束。

`queryLoop()` 函数被定义为 `AsyncGenerator`，在其推进过程中依次产出 `StreamEvent`、`RequestStartEvent`、`Message`、`TombstoneMessage` 与 `ToolUseSummaryMessage` 事件。这种基于生成器的设计使得可以向 UI 层流式输出，同时在循环内部保持单一同步控制流。

Claude Code 的响应式循环遵循 ReAct 模式（Yao et al., 2022）：模型生成推理与工具调用，执行框架执行动作，结果再反馈给下一次迭代。其他编排模式包括显式的基于图的路由（LangChain, Inc., 2024），其中控制流被定义为带类型的边（typed edge）构成的状态机；以及树搜索方法（Zhou et al., 2023），在提交之前探索多条动作轨迹。Anthropic 自己的文档（Schluntz and Zhang, 2024）指出了五种可组合的工作流模式（提示链、路由、并行化、编排器-工作者、评估器-优化器），Claude Code 主要使用其中的编排器-工作者（orchestrator-workers）模式来实现子代理委派（第 8 节），同时保持核心循环的响应式特征。响应式设计以搜索的完备性换取简洁性与延迟：每个轮次都提交到一条动作序列，而不进行回溯。

### 4.2 工具分派与流式执行

当模型响应包含 `tool_use` 块时，系统会在两条执行路径之间选择。主路径使用 `StreamingToolExecutor`，它在工具从模型响应中流式传入时就开始执行，从而降低多工具响应的延迟。回退路径使用 `toolOrchestration.ts` 中的 `runTools()`，它遍历由 `partitionToolCalls()` 生成的分区。两条路径都将工具分类为并发安全（concurrent-safe）或独占（exclusive）。只读操作可以并行执行，而诸如 shell 命令这类修改状态的操作则被串行化。

`StreamingToolExecutor`（`StreamingToolExecutor.ts`）通过两种协调机制管理并发执行：

- 同级中止控制器（sibling abort controller）。当任一 Bash 工具出错时触发，立即终止其他仍在进行中的子进程，而不是让它们运行至完成。
- 进度可用信号（progress-available signal）。当有新输出就绪时唤醒 `getRemainingResults()` 消费者。

结果会被缓冲，以确保不会有结果先于某个仍在运行的、更早的非并发安全工具被发出；并行运行的并发安全工具的结果则在其完成时发出。这种"并发读、串行写"的执行模型介于完全串行分派与更激进的推测式方法之间，例如 PASTE（Sui et al., 2026），后者在模型仍在生成时就推测性地预先执行预测的未来工具调用，通过推测来隐藏工具延迟。

工具结果收集阶段会遍历来自流式执行器或批量 `runTools()` 异步生成器的更新。两者都是异步可迭代对象，由同一个 `for await` 循环消费；区别在于工具执行是在模型结束流式输出之前就开始（流式），还是在划分为并发安全分组之后才开始（批量）。每个更新可能携带一个工具结果、一个附件或一个进度事件。有一项特殊的检查用于检测 `hook_stopped_continuation` 附件：如果某个 `PostToolUse` 钩子表示该轮次不应继续，则设置 `shouldPreventContinuation` 标志。结果会经由 `normalizeMessagesForAPI()` 针对 Anthropic API 进行规范化，过滤后只保留用户类型的消息。

### 4.3 模型调用前的上下文整形器

五个上下文整形器在每次模型调用之前于 `query.ts` 中依次执行，各自作用于 `messagesForQuery` 数组。五个整形器按顺序运行，较早的步骤施加较轻的削减，较晚的步骤才施加范围更大的压缩。

预算削减（Budget reduction）。（`applyToolResultBudget()`）。对工具结果施加单条消息的大小限制，将过大的输出替换为内容引用。豁免工具（即 `maxResultSizeChars` 不为有限值的工具）保留其完整输出。对于代理与会话查询来源，内容替换会被持久化，以便在恢复时重建。预算削减排在 microcompact 之前运行，因为 microcompact 完全依据 `tool_use_id` 操作，从不检查内容；两者可以干净地组合。

Snip。（`snipCompactIfNeeded()`，由 `HISTORY_SNIP` 控制开关）。一种轻量裁剪，移除较早的历史片段，返回 `{messages, tokensFreed, boundaryMessage}`。`snipTokensFreed` 值会被传递给自动压缩（auto-compact），因为主 token 计数器是从最近一条助手消息的 `usage` 字段推导上下文大小的，而该消息在 snip 之后仍然保留着其 snip 之前的 `input_tokens`；因此，除非显式传递，snip 节省的 token 对计数器而言是不可见的。

Microcompact。细粒度压缩，总是运行一条基于时间的路径，并可选地运行一条缓存感知（cache-aware）路径（由 `CACHED_MICROCOMPACT` 控制开关）。启用缓存路径时，边界消息会被推迟到 API 响应之后，以便使用真实的 `cache_deleted_input_tokens` 而非估计值。返回 `{messages, compactionInfo}`，其中 `compactionInfo` 可能包含 `pendingCacheEdits`。

上下文折叠（Context collapse）。由 `CONTEXT_COLLAPSE` 控制开关。一种对对话历史的读取时投影（read-time projection）。源码注释解释道："不会产出任何东西；折叠视图是对 REPL 完整历史的读取时投影。摘要消息存放在折叠存储中，而不是 REPL 数组中。这正是折叠能够跨轮次持久化的原因。"与其他整形器不同，上下文折叠不会改变 REPL 所存储的历史；它通过 `applyCollapsesIfNeeded()` 用投影视图替换 `messagesForQuery` 数组，因此模型看到的是折叠后的版本，而完整历史仍可用于重建。

自动压缩（Auto-compact）。第五个整形器，通过 `compact.ts` 中的 `compactConversation()` 触发一次完整的、由模型生成的摘要。该函数执行 `PreCompact` 钩子，使用 `getCompactPrompt()` 创建摘要请求，并调用模型生成压缩后的摘要。结果送入 `buildPostCompactMessages()`（`compact.ts`）。只有在前面四个整形器全部运行之后上下文仍超过压力阈值时，自动压缩才会触发。

### 4.4 恢复机制

查询循环针对边界情况实现了若干恢复机制：

- 最大输出 token 升级：当响应触及输出 token 上限时，系统可以在受 GrowthBook 标志控制、且不存在已有覆盖值或环境变量上限的情况下，以升级后的上限重试。每个轮次最多允许三次恢复尝试（`MAX_OUTPUT_TOKENS_RECOVERY_LIMIT = 3`）。
- 响应式压缩（由 `REACTIVE_COMPACT` 控制开关）：在出现 prompt-too-long 或媒体过大的错误之后，循环可以尝试响应式压缩，并在恢复成功时重试该请求。`hasAttemptedReactiveCompact` 标志确保这一动作在每个轮次中最多触发一次。
- Prompt-too-long 处理：如果 API 返回 `prompt_too_long` 错误，循环会先尝试上下文折叠的溢出恢复与响应式压缩。只有在这些尝试都失败之后，才以 `reason: 'prompt_too_long'` 终止。
- 流式回退：`onStreamingFallback` 回调处理流式 API 的问题，使循环能够以不同的策略重试。
- 备用模型：`fallbackModel` 参数支持在主模型失败时切换到替代模型。

### 4.5 停止条件

多种条件可以终止循环：

1. 无工具调用：模型只产生文本内容（主要的停止条件）。
2. 达到最大轮次：达到可配置的 `maxTurns` 上限。
3. 上下文溢出：API 返回 `prompt_too_long`。
4. 钩子干预：某个 `PostToolUse` 钩子设置了 `hook_stopped_continuation`。
5. 显式中止：`abortController` 信号触发。

轮次管线决定了工具请求如何被编排与恢复。下一节考察决定每个请求是否被允许执行的那道门。

## 5 工具授权与控制边界

生产级编程代理采用不同的安全架构：分层策略执行、操作系统级沙箱，或基于版本控制的回滚。Claude Code 结合了前两者，实现了表 1 中的四项设计原则：拒绝优先并升级至人工、渐进式信任谱系、以分层机制实现纵深防御，以及以可逆性为权重的风险评估。

> [图 4]

**图 4** 权限门控概览与设计原则。

| 原则 | 描述 |
| --- | --- |
| 渐进式信任（Progressive Trust） | 代理一开始只拥有最低限度的自主权；用户通过批准工具调用来扩展它，这些批准会成为永久规则。 |
| 拒绝优先、默认询问（Deny-First, Ask-by-Default） | 即使处于更宽松的模式下，拒绝规则也始终优先。在默认与手动审批模式中，未匹配任何规则且带有风险的操作会询问用户，而不是静默运行；可选的自动模式会将许多此类审查交由分类器中介的检查处理。 |
| 可组合策略（Composable Policy） | 三种机制共同塑造策略：声明式规则、全局信任模式，以及可编程钩子，三者均可独立配置。 |

当 Claude 决定执行某个工具时（例如通过 `BashTool` 运行 `npm test` 以复现 auth 测试失败），该请求会进入图 4 所示的权限管线。除绕过模式外，工具调用都要经过权限系统。在默认的交互姿态下，超出只读访问范围的操作会请求批准，而不是静默运行；而更宽松的模式会用有范围的自动批准、拒绝或分类器中介的审查来取代部分提示。这一默认设置源于一种有文献记录的行为模式：Anthropic 的自动模式分析（Hughes, 2026）发现，用户会批准约 93% 的权限提示，这表明审批疲劳使得交互式确认在行为层面无法作为唯一的安全机制可靠发挥作用。由于用户会习惯性地不加仔细审查就批准，系统必须在人的警觉性之外独立维持安全。这促使了架构上的承诺：拒绝优先的评估、全局拒绝预过滤，以及沙箱，作为独立于用户注意力的分层机制运行。

### 5.1 权限模式与规则评估

类型定义中共存在七种权限模式（`types/permissions.ts` 中有 5 种外部模式；`auto` 按条件添加；`bubble` 位于类型联合中）：

1. `plan`：模型必须制定计划；只有在用户批准后才继续执行。
2. `default`：标准交互式使用。大多数操作需要用户批准。
3. `acceptEdits`：工作目录内的编辑以及某些文件系统 shell 命令（`mkdir`、`rmdir`、`touch`、`rm`、`mv`、`cp`、`sed`）会被自动批准；其他 shell 命令需要批准。
4. `auto`：基于机器学习的分类器评估未通过快速路径检查的请求（由 `TRANSCRIPT_CLASSIFIER` 控制）。
5. `dontAsk`：提示被抑制，原本会触发提示的操作会被自动拒绝；显式的允许与拒绝规则仍然适用。
6. `bypassPermissions`：跳过大多数权限提示，但安全关键检查与不受绕过影响的规则仍然适用。
7. `bubble`：仅内部使用的模式，用于将子代理的权限升级传递到父终端。

五种对外可见的模式（`acceptEdits`、`bypassPermissions`、`default`、`dontAsk`、`plan`）定义在 `EXTERNAL_PERMISSION_MODES` 数组中。`auto` 模式仅当 `TRANSCRIPT_CLASSIFIER` 功能标志处于活动状态时才被有条件地包含。`bubble` 模式存在于类型联合中，但不在任何模式数组内；它在内部用于子代理权限升级（第 8 节）。

权限规则按拒绝优先的顺序评估（`permissions.ts`）。`toolMatchesRule()` 函数首先检查拒绝规则：拒绝规则始终优先于允许规则，即使允许规则更为具体。宽泛的拒绝（“拒绝所有 shell 命令”）不能被狭窄的允许（“允许 `npm test`”）覆盖。该规则系统支持工具级匹配（按工具名）和内容级匹配（匹配特定的工具输入模式，例如 `Bash(prefix:npm)`）。

这七种模式构成一个渐进的自主性谱系，从 `plan`（用户在执行前批准所有计划）经过 `default` 与 `acceptEdits` 直到 `bypassPermissions`（最少提示）。这一梯度反映了一种反复出现的设计张力：随着自主性提高，系统必须从交互式批准转向自动化安全检查。其他代理系统以不同方式解决这一张力。SWE-Agent 与 OpenHands（Yang et al., 2024; Wang et al., 2024b）使用 Docker 容器隔离，对整个执行环境进行沙箱化，而不是逐一评估单个工具调用。Aider（Gauthier, 2024）依赖 Git 作为安全网，通过版本控制使所有变更都可逆。Claude Code 的方法是在可选的 shell 沙箱之上（第 5.4 节）叠加多种策略执行机制，以简洁性换取对单个操作的细粒度控制。

### 5.2 授权管线

完整的授权管线经过若干阶段：

**预过滤。** 在任何工具请求进入运行时评估之前，`filterToolsByDenyRules()`（`tools.ts`）会在组装工具池时，将全局被拒绝的工具从模型视野中完全剔除。文档指出：“使用与运行时权限检查相同的匹配器，因此像 `mcp__server` 这样的 MCP 服务器前缀规则会在模型看到它们之前就剥离该服务器的所有工具。”这防止模型尝试调用被禁止的工具，从而不会在这些工具上浪费调用。

**`PreToolUse` 钩子。** 已注册的钩子会作为权限管线的一部分触发。`PreToolUse` 钩子可返回 `permissionDecision` 以拒绝或询问，或返回 `updatedInput` 以修改工具的输入参数（`types/hooks.ts`）。钩子的允许不会绕过后续基于规则的拒绝或安全检查。在交互路径中，用户对话框会先入队，钩子异步运行；协调器及类似的后台代理路径则会先等待自动化检查完成再显示对话框。

**规则评估。** 拒绝优先的规则引擎评估该请求。MCP 工具按其完全限定名 `mcp__server__tool` 进行匹配，服务器级规则会匹配该服务器的所有工具。

**权限处理器。** `useCanUseTool.tsx` 中的处理器根据运行时上下文分支为四条路径之一：

1. 协调器（Coordinator）：用于多代理协调模式。在回退到用户交互之前，尝试自动化解决（分类器、钩子、规则）。
2. 集群工作节点（Swarm worker）：处理多代理集群中的工作节点代理，并带有自己的解决逻辑。
3. 推测式分类器（Speculative classifier）：当 `BASH_CLASSIFIER` 启用且工具为 `BashTool` 时，推测式分类器会让预先启动的分类结果与超时竞速。如果分类器以高置信度返回，工具会立即获批而无需用户交互。
4. 交互式（Interactive）：回退路径。通过终端 UI 呈现标准的用户批准对话框。

在协调器及某些后台路径中，会先尝试自动化解决，再进行用户交互。在标准交互路径中，对话框可以先出现，同时钩子或分类器检查并行继续。当分类器或拒绝规则阻止某项操作时，系统会把拒绝视为一种路由信号，而不是硬性停止：模型会收到拒绝理由，修改其方法，并在下一轮循环迭代中尝试更安全的替代方案。`PermissionDenied` 钩子事件（第 6 节）使外部代码能够以编程方式观察并响应这些拒绝。这种面向恢复的设计意味着，权限执行是在塑造代理的行为，而不仅仅是将其中止。

### 5.3 自动模式分类器与钩子生命周期

自动模式分类器（`yoloClassifier.ts`）在启用时参与权限决策。当 `TRANSCRIPT_CLASSIFIER` 启用时，分类器加载三个提示资源：

- 一个基础系统提示。
- 一个外部权限模板。
- 对于 Anthropic 内部用户，一个单独的内部模板。

分类器会对照对话记录与权限模板评估拟议的工具调用，产生允许、拒绝或请求人工批准的结果。`isUsingExternalPermissions()` 函数检查 `USER_TYPE` 与 `forceExternalPermissions` 配置标志，以选择适当的模板。

在源码中定义的 27 个钩子事件（`coreTypes.ts`）中，有五个直接参与权限流程，每个都有特定的经 Zod 校验的输出 schema（`types/hooks.ts`）：

- `PreToolUse`：可返回 `permissionDecision`（拒绝或询问，但允许不会绕过后续检查）、`permissionDecisionReason` 以及 `updatedInput`（修改参数）。
- `PostToolUse`：可注入 `additionalContext`，并且对于 MCP 工具，可返回 `updatedMCPToolOutput` 以在结果进入上下文之前修改它们。
- `PostToolUseFailure`：可注入 `additionalContext`，提供针对错误的指导。
- `PermissionDenied`：可在自动模式拒绝后提供重试指导。
- `PermissionRequest`：可返回允许或拒绝的决定。在协调器及类似路径中，这可以在用户对话框之前解决。在标准交互路径中，它也可以与对话框并行运行。

对于非 MCP 工具，`tool_result` 会在 `PostToolUse` 钩子触发之前发出。对于 MCP 工具，结果会延迟到后置钩子运行完毕之后，从而使 `updatedMCPToolOutput` 得以生效。

### 5.4 Shell 沙箱

Shell 沙箱为 Bash 与 PowerShell 命令提供额外一层保护（`shouldUseSandbox.ts`）。`shouldUseSandbox()` 函数检查沙箱是否全局启用、该调用是否选择退出，以及命令是否匹配任何排除模式。当沙箱处于活动状态时，它提供独立于应用层权限模型的文件系统与网络隔离。<sup>3</sup> 一条命令可以被权限批准但仍被沙箱化，也可以被权限拒绝因而永远到不了沙箱检查。这两个系统运行在不同轴线上：授权与隔离。

分层安全架构建立在一个独立性假设之上：如果某一层失效，其他层会捕获违规。然而，若干层共享共同的性能约束。安全研究人员（Adversa.ai, 2026）记录到，包含超过 50 个子命令的命令会回退为单一的通用批准提示，而不是执行逐子命令的拒绝规则检查，因为逐子命令解析会导致 UI 卡死。这一例子表明，当纵深防御的各层共享失效模式时，其效果可能下降，这是安全与性能之间的结构性张力，第 12.3 节将进一步分析。

权限管线决定工具请求是否执行。下一节考察是什么决定了哪些工具首先存在：组装模型行动面的可扩展性架构。

## 6 可扩展性：MCP、插件、技能与钩子

```python
# Claude Code 代理循环的一轮
while not stopped:
    # a 组装（assemble）：构建模型所看到的内容
    context = assemble(
        system_prompt,        # 指令头部
        tool_schemas,         # 可调用工具的签名
        history,              # 先前轮次的消息
        hook_additions,       # 由钩子推入的内容
    )
    # b 模型（model）：选择下一个动作
    action = model(context, tools)          # 扁平工具池
    if action.is_text_only():
        stopped = run_stop_hooks(action)    # 可否决
        continue
    # c 执行（execute）：授权并运行工具调用
    action, hook_decision = run_pre_tool_hooks(action)
    if not permitted(action, hook_decision):
        continue
    result = execute(action)                # 工具在此运行
    result = run_post_tool_hooks(result)    # 变更/注解
    history.append(action, result)
```

| `SessionStart` 钩子 | 在会话开始时一次性注入上下文 |

**b `model()`：模型所能触及的内容**

### 6.1 四种扩展机制

这些机制实现在不同的源码目录中（图 5），服务于不同的集成模式：

**MCP 服务器。** Model Context Protocol 是主要的外部工具集成路径。MCP 服务器可从多个作用域配置：项目、用户、本地和企业，并在运行时合并额外的插件服务器与 claude.ai 服务器（`services/mcp/config.ts`）。MCP 客户端（`services/mcp/client.ts`）支持多种传输类型：`stdio`、`SSE`、`HTTP`、`WebSocket`、`SDK`，以及 IDE 专用变体（`sse-ide`、`ws-ide`）和一个内部的 `claudeai-proxy`。每个已连接的服务器都以 `MCPTool` 对象的形式贡献工具定义。专门的内置工具 `ListMcpResourcesTool` 和 `ReadMcpResourceTool` 提供对 MCP 资源的访问。

**插件。** 插件承担双重角色：它们既是打包格式，也是分发机制。`PluginManifestSchema`（`utils/plugins/schemas.ts`）接受十种组件类型：命令、代理、技能、钩子、MCP 服务器、LSP 服务器、输出风格、通道（channel）、设置和用户配置。插件加载器（`utils/plugins/pluginLoader.ts`）校验清单，并把每个组件路由到相应的注册表：命令与技能通过 `SkillTool` 元工具呈现，代理出现在由 `AgentTool` 消费的定义中，钩子并入钩子注册表，MCP 与 LSP 服务器折叠进各自的标准配置，输出风格则修改响应格式。因此，单个插件包可以同时以多种组件类型扩展 Claude Code，这使插件成为第三方扩展的主要分发载体。

**技能。** 每个技能由一个带 YAML frontmatter 的 `SKILL.md` 文件定义。`parseSkillFrontmatterFields()` 函数（`loadSkillsDir.ts`）解析 15+ 个字段，包括显示名称、描述、允许的工具（授予该技能对额外工具的访问权）、参数提示、模型覆盖、执行上下文（`'fork'` 表示隔离执行）、关联的代理定义、effort 级别和 shell 配置。技能可以定义自己的钩子，这些钩子在调用时动态注册。内置技能在启动时注册到内存中。被调用时，`SkillTool` 元工具会把技能的指令注入上下文。

**钩子。** 源码定义了 27 个钩子事件，涵盖工具授权（`PreToolUse`、`PostToolUse`、`PostToolUseFailure`、`PermissionRequest`、`PermissionDenied`）、会话生命周期（`SessionStart`、`SessionEnd`、`Setup`、`Stop`、`StopFailure`）、用户交互（`UserPromptSubmit`、`Elicitation`、`ElicitationResult`）、子代理协调（`SubagentStart`、`SubagentStop`、`TeammateIdle`、`TaskCreated`、`TaskCompleted`）、上下文管理（`PreCompact`、`PostCompact`、`InstructionsLoaded`、`ConfigChange`）、工作区事件（`CwdChanged`、`FileChanged`、`WorktreeCreate`、`WorktreeRemove`）以及通知（`coreTypes.ts`、`coreSchemas.ts`）。其中 15 个具有事件特定的输出模式（output schema），其丰富字段支持权限决策、上下文注入、输入修改、MCP 结果转换和重试控制（`types/hooks.ts`）。通过设置和插件配置的持久化钩子命令使用四种命令类型：shell 命令（`type: command`）、LLM 提示钩子（`type: prompt`）、HTTP 钩子（`type: http`）和代理式校验钩子（`type: agent`）（`schemas/hooks.ts`）。运行时还额外支持不可持久化的回调钩子（`type: callback`），供 SDK 和内部埋点使用（`types/hooks.ts`）。钩子来源包括启动时的 `settings.json`、插件和托管策略；技能钩子在调用时动态注册（`utils/hooks.ts`）。五个工具授权事件在第 5.3 节详述。

### 6.2 工具池装配

位于 `tools.ts` 的 `assembleToolPool()` 函数在源码注释中被描述为"把内置工具与 MCP 工具结合的唯一事实来源"。装配遵循五步流水线：

1. **基础工具枚举。** `getAllBaseTools()`（`tools.ts`）返回最多 54 个工具的数组：其中 19 个始终包含（如 `BashTool`、`FileReadTool`、`AgentTool`、`SkillTool`），另外 35 个依据功能开关、环境变量和用户类型有条件地包含。Anthropic 内部用户会获得额外的内部工具。Worktree 模式启用 `EnterWorktreeTool` 和 `ExitWorktreeTool`。代理集群（agent swarm）启用团队工具。当 Bun 二进制中内置的搜索工具可用时，专门的 `GlobTool` 和 `GrepTool` 会被省略。
2. **模式过滤。** `getTools()`（`tools.ts`）施加模式特定的过滤。在 `CLAUDE_CODE_SIMPLE` 模式下，只有 `Bash`、`Read` 和 `Edit` 可用（或在 REPL 分支中为 `REPLTool`；如适用再加协调器工具）。每个工具的 `isEnabled()` 方法会被调用，以做运行时可用性检查。
3. **拒绝规则预过滤。** `filterToolsByDenyRules()`（`tools.ts`）在任何调用发生之前，把被整体拒绝的工具从模型的视野中剥离。
4. **MCP 工具集成。** 来自 `appState.mcp.tools` 的 MCP 工具先按拒绝规则过滤，再与内置工具合并。
5. **去重。** 工具按名称去重，内置工具优先于 MCP 工具。

`REPL.tsx`（通过 `useMergedTools` 钩子）和 `AgentTool.tsx`（在构建 worker 工具集时）都会调用该函数，从而确保所有执行路径上的装配一致。在请求时，延迟工具（deferred tool）可以被隐藏于模型的上下文之外，直到通过 `ToolSearch` 显式查询（`tools.ts`）。

基于代理的扩展（通过 `.claude/agents/*.md` 和插件贡献的代理自定义代理定义）在第 8 节讨论，因为代理与上述四种机制有根本不同：它们创建新的、隔离的上下文窗口，而不是扩展当前的上下文窗口。

### 6.3 为什么是四种机制？

既然每增加一种扩展机制都会扩大开发者必须学习的面，一个自然的问题是：为什么 Claude Code 使用四种不同的机制，而不是合并成一两种。答案在于这样一个观察：不同种类的可扩展性对上下文窗口施加的成本不同，而单一机制无法覆盖从零上下文的生命周期钩子到模式繁重的工具服务器这整个范围，除非把不必要的权衡强加给扩展作者。

**表 2** 每种扩展机制独特提供的能力。上下文成本指该机制激活时占用的有限上下文窗口的多少。

| 机制 | 独特能力 | 上下文成本 | 插入点 |
| --- | --- | --- | --- |
| MCP 服务器 | 外部服务集成（多传输） | 工具模式加载后较高 | `model()`：工具池 |
| 插件 | 多组件打包 + 分发 | 中等（视情况而异） | 全部三个点 |
| 技能 | 领域特定指令 + 元工具调用 | 被调用前较低 | `assemble()`：上下文注入 |
| 钩子 | 生命周期拦截 + 事件驱动自动化 | 默认零 | `execute()`：工具前/后 |

如表 2 所总结，每种机制都以部署复杂度换取不同种类的可扩展性。MCP 服务器提供运行时工具集成（模型获得新的可调用工具），代价是服务器管理开销以及工具模式消耗的上下文预算——这些模式默认只在需要某个工具时才加载。技能以最小的上下文成本塑造代理的思考方式（而不只是它拥有哪些工具），因为在技能被调用之前，只有 frontmatter 中的描述留在提示中。钩子提供横切的生命周期控制（阻止、改写或注解工具调用），默认不占用上下文，不过钩子可以选择注入额外上下文。插件把其他三种机制的任意组合打包成可分发的包，充当打包与分发层，而不是一种独立的运行时原语。这种渐进的上下文成本排序（钩子为零，技能在调用前较低，插件中等，MCP 较高）意味着廉价的扩展可以广泛铺开而不耗尽上下文窗口，而昂贵的扩展则留给那些确实需要新工具面的场景。

有些代理框架只提供单一扩展机制，通常是仅面向工具的 API，所有定制都以额外的可调用工具形式到达。另一些则采用两层结构，把工具与配置或指令注入分开。Claude Code 的四种机制方案可以容纳更广泛的扩展模式，从零上下文的事件处理器到完整的外部服务集成，但它也提高了开发者为某个集成任务决定用哪种机制时的学习曲线。

## 7 上下文构建与记忆

代理如何管理其上下文窗口、如何持久化用户指令，是一个核心设计选择，不同系统在基于文件的透明性、数据库支持的检索以及不透明的学习表示之间做选择。这里的设计选择落实了表 1 中的两条原则：把上下文视为稀缺资源并渐进管理，以及透明的、基于文件的配置与记忆。

在运行示例进行到这一步时，任务已经积累了状态：最初的请求、`npm test` 权限判定的结果、第 6 节装配的工具池，以及到目前为止收集到的任何文件读取或命令输出。本节要问的是：在下次模型调用之前，这些不断增长的状态如何被装入 Claude Code 有限的上下文窗口。

在模型被调用之前，代理循环会从工具池（第 6 节）、`CLAUDE.md` 文件、自动记忆（auto memory）和对话历史装配出上下文窗口。以下各小节涵盖装配顺序、`CLAUDE.md` 层级以及多步上下文压缩（compaction）流水线。

### 7.1 上下文窗口组装

上下文窗口（图 6）由以下来源组装而成，其中一些在初始组装时加入，另一些则在轮次进行中较晚注入：

1. 系统提示，其中并入输出风格修改以及任何 `--append-system-prompt` 标志的内容。
2. 通过 `getSystemContext()`（`context.ts`）获取的环境信息：git 状态（在远程模式下或禁用 git 指令时跳过），以及针对内部构建的可选破坏缓存注入（由 `BREAK_CACHE_COMMAND` 控制）。每会话记忆化（memoized）一次。
3. 通过 `getUserContext()`（`context.ts`）获取的 CLAUDE.md 层级：四级指令文件层级（第 7.2 节）。同样经过记忆化。
4. 路径作用域规则：条件性的、按目录匹配的规则，当代理在匹配的目录中读取文件时才按需加载。
5. 自动记忆：异步预取的在上下文中相关的记忆条目。
6. 工具元数据：技能（skill）描述、MCP 工具名称，以及延迟加载的工具定义（按需通过 ToolSearch）。
7. 对话历史：向前携带，受上下文压缩（compaction）约束。
8. 工具结果：文件读取、命令输出、子代理摘要。
9. 压缩摘要：替换较早的历史片段。

`query.ts` 中的系统提示组装通过 `asSystemPrompt(appendSystemContext(systemPrompt, systemContext))()` 将系统上下文与基础提示合并。用户上下文（CLAUDE.md 与日期）通过 `prependUserContext()` 前置到消息数组中。这种分离意味着 CLAUDE.md 内容在 API 请求中所处的结构位置不同于系统提示，从而可能影响模型的注意力模式。

若干上下文来源在主窗口构建完成之后才被较晚注入：相关记忆预取（`query.ts`）、MCP 指令增量（仅新增或变更的服务器指令）、代理列表增量，以及后台代理任务通知。因此上下文窗口在组装时并非静态，而是可能在轮次进行中增长。

### 7.2 CLAUDE.md 层级与自动记忆

有一条设计原则塑造了记忆系统：存储的上下文应当可由用户检视与编辑。CLAUDE.md 文件是纯文本 Markdown，而不是结构化配置或不透明的数据库条目。这一透明性选择以表达力换取可审计性：用户可以直接检视和编辑自己所控制的记忆文件，项目级记忆也可以与代码库一同纳入版本控制（Anthropic, 2026i; MindStudio Team, 2026）。其他记忆架构则体现了这种权衡。检索增强方法使用基于嵌入的查找来呈现相关的先前上下文，获得了灵活性，却牺牲了可检视性：用户无法轻易看到或编辑检索系统认为相关的内容。数据库支撑的记忆提供结构化查询，但需要额外的基础设施，且对版本控制不透明。Claude Code 基于文件的方法使这些记忆表面可读可编辑，尽管其他上下文来源仍通过系统提示、工具、钩子（hook）、MCP 服务器和运行时状态进入。该系统不使用嵌入或向量相似度索引进行记忆检索；相反，它用基于 LLM 的记忆文件头部扫描，按需选出至多五个相关文件，以文件为粒度而非条目粒度呈现它们。基于嵌入的系统可以更有选择性地检索单个条目，代价是可检视性以及维护索引所需的基础设施。

CLAUDE.md 文件遵循多级加载层级。源码头文件（`claudemd.ts`）定义了四种记忆类型：

1. 托管记忆（managed memory，例如 Linux 上的 `/etc/claude-code/CLAUDE.md`）：面向所有用户的操作系统级策略。
2. 用户记忆（user memory，`~/.claude/CLAUDE.md`）：私有的全局指令。
3. 项目记忆（project memory，项目根目录中的 `CLAUDE.md`、`.claude/CLAUDE.md` 以及 `.claude/rules/*.md`）：签入代码库的指令。
4. 本地记忆（local memory，项目根目录中的 `CLAUDE.local.md`）：被 gitignore 忽略，用于私有的项目专属指令。

文件发现从当前目录向上遍历至根目录，在每个目录中检查所有项目记忆与本地记忆文件。越靠近当前目录的文件优先级越高（加载越晚）。文件按“优先级逆序”加载：后加载的文件获得更多模型注意力。对于从根目录到 CWD 的各目录，`.claude/rules/*.md` 中的无条件规则在启动时即被立即加载。对于 CWD 之下的嵌套目录，即便是无条件规则也要等到代理在匹配目录中读取文件时才按需加载。这意味着模型的指令集可以随着代码库新部分被探索而在对话过程中演化。

CLAUDE.md 内容是作为用户上下文（一条用户消息）投递的，而不是作为系统提示内容投递（`context.ts`）。这一架构选择有重要含义：由于 CLAUDE.md 内容是以对话上下文而非系统级指令的形式投递，模型对这些指令的遵从是概率性的而非有保证的。以拒绝优先（deny-first）顺序评估的权限规则（第 5 节）提供了确定性的执行层。这在指导（CLAUDE.md，概率性）与执行（权限规则，确定性）之间形成了有意的分离。相关函数调用 `setCachedClaudeMdContent()` 将已加载内容缓存给自动模式分类器，以避免 CLAUDE.md 加载器与权限系统之间出现循环导入。

记忆文件支持 `@include` 指令，用于模块化指令集（`claudemd.ts` 中的 `processMemoryFile()`）。语法变体包括 `@path`、`@./relative`、`@~/home` 和 `@/absolute`。该指令仅在叶子文本节点中生效（代码块内不生效）。在实现中，发起包含的文件先被推入，被包含的文件随后追加在其后，循环引用通过跟踪已处理路径来防止，不存在的文件则被静默忽略。

### 7.3 上下文压缩流水线

五层压缩流水线（第 4.3 节）通过渐进式压缩实现“上下文即瓶颈”原则（`query.ts`）。Claude Code 并不采用单一策略，而是依次施加五个层，每一层都更具侵略性（其中三层由构建期特性标志控制，预算削减由一个运行时标志控制，而自动压缩可由用户配置）。这种渐进式方法与更简单的替代方案形成对比，例如单遍截断（丢弃最旧的消息）或单次摘要步骤。渐进式设计反映了一种惰性降级原则：先施加干扰最小的压缩，只有当更廉价的策略被证明不足时才升级。这种方法的代价是复杂性。五个相互作用的压缩层，其中若干由特性标志控制，所产生的行为对用户而言难以完全预测。自动压缩会在转录记录中产生可见摘要，微压缩（microcompact）会发出边界标记，而上下文坍缩（context collapse）则在用户不可见的情况下运行。更简单的单遍方法牺牲信息，但更容易被理解。

1. 预算削减（运行时标志）：单个工具结果的大小上限。
2. 剪切（Snip，`HISTORY_SNIP`）：对较旧历史的轻量裁剪。
3. 微压缩（Microcompact，`CACHED_MICROCOMPACT`）：细粒度的缓存感知压缩。
4. 上下文坍缩（Context collapse，`CONTEXT_COLLAPSE`）：读取时对历史做虚拟投影。
5. 自动压缩（Auto-compact，默认启用，可禁用）：由模型生成的完整摘要。

`buildPostCompactMessages()` 函数（`compact.ts`）返回如下压缩后输出结构：`[boundaryMarker, ...summaryMessages, ...messagesToKeep, ...attachments, ...hookResults]`。边界标记通过 `annotateBoundaryWithPreservedSegment()` 标注保留片段元数据，记录 `headUuid`、`anchorUuid` 和 `tailUuid`，以支持读取时的链修补（chain patching）。这种大体上仅追加（append-only）的设计意味着压缩从不修改或删除先前写入的转录行；它只追加新的边界事件与摘要事件。

压缩函数 `compactConversation()`（`compact.ts`）包含若干设计选择。压缩前钩子最先触发，从而允许钩子注入自定义指令。一个 GrowthBook 特性标志控制压缩路径是否复用主对话的提示缓存（一处代码注释记录了 2026 年 1 月的一次实验：“false 路径的缓存未命中率为 98%，耗费约 0.76% 的机群 cache_creation”）。压缩之后，附件构建器会从实时应用状态重新声明运行时状态（计划、技能与异步代理），因为压缩丢弃的是先前的附件消息，而不是底层状态。

当系统把工作委派给子代理（subagent）、而每个子代理都在自己受限的上下文窗口中运行时，上下文隔离变得更加关键。

## 8 子代理委派与编排

多代理编排是编码代理的一个关键设计维度，其选择涵盖父子层级结构、基于对等的对话框架（Wu et al., 2024），以及图结构的工作流引擎（LangChain, Inc., 2024）。Claude Code 的委派架构实现了表 1 中“隔离的子代理边界”原则，并同时体现了“拒绝优先并辅以人工升级”（权限覆盖）与“按可逆性加权风险评估”（子代理工具限制）的若干方面。

当 Claude 判定修复认证测试需要先探索认证模块的结构时，它可以将这一探索委派给子代理。委派机制是 Agent 工具（`AgentTool.tsx`），`Task` 作为遗留别名保留。模型以结构化输入调用 Agent，其中包括委派提示、可选的子代理类型，以及用于隔离模式、权限覆盖和工作目录的配置。

### 8.1 代理工具与委派标准

Agent 工具的输入模式（图 7）使用受特性标志控制的字段，当其背后的特性被禁用时会省略相应的可选参数。`isolation` 字段为内部用户提供 `['worktree', 'remote']`，为外部用户提供 `['worktree']`，在构建时确定。`cwd` 字段由特性标志控制。当后台任务被禁用或启用 fork-subagent 模式时，`run_in_background` 字段被省略。

Claude Code 依据特性标志与入口点，提供至多六种内置子代理类型：

- `Explore`：主要面向读取/搜索的调查，写入与编辑工具在其拒绝清单（deny-list）中。
- `Plan`：创建结构化计划；执行则经由标准权限模型推进。
- **General-purpose**：能力广泛，在明确请求时使用（注：省略 type 可能转而路由到 fork-subagent 路径，该路径复用父会话的对话上下文，而不对其做隔离）。
- **Claude Code Guide**：入职引导与文档协助，带有自己的 `permissionMode` 覆盖。
- **Verification**：运行校验检查（测试套件、lint）。
- **Statusline-setup**：专用于终端状态栏配置。

> [图 7]

**图 7** 子代理隔离与委派架构。Agent 工具分派到内置子代理（Explore、Plan、general-purpose）或自定义子代理，每个子代理都在隔离的上下文中运行，拥有重建的权限上下文和独立的工具集。Agent 工具沿三个轴分派：路由（teammate）、隔离（remote、worktree）和生命周期（async、sync）。

除内置子代理之外，用户通过 `.claude/agents/*.md` 文件定义自定义子代理，插件则通过 `loadPluginAgents.ts` 提供代理定义。每个文件的 Markdown 正文充当该代理的系统提示，YAML frontmatter 则指定配置字段，包括 `description`、`tools`（允许列表）、`disallowedTools`、`model`、`effort`、`permissionMode`、`mcpServers`、`hooks`、`maxTurns`、`skills`、memory scope、background 标志和 isolation 模式。JSON 格式的代理定义支持相同的字段，并额外支持把 `prompt` 作为显式字段（`loadAgentsDir.ts`）。这意味着自定义代理可以是一个完整配置、彼此隔离的子系统，拥有自己的工具、模型、权限、钩子（hook）、memory scope 和隔离模式。AgentTool 与 SkillTool 一同位于基础工具池中，作为分派到这些定义的元工具（meta-tool），但两者有本质区别：SkillTool 通常把指令注入当前上下文窗口（另有一个需显式启用的 `context: fork` 模式，它通过同一套 `runAgent()` 机制生成一个隔离子代理），而 AgentTool 总是生成一个新的、隔离的代理。其代价是，大多数子代理调用都需要一个自包含的提示，因为默认路径不继承父会话的对话历史（fork-subagent 路径是例外）。基于对话的框架共享完整的转录历史，避免了这一成本，但随着代理数量增长，会面临上下文爆炸的风险。

### 8.2 隔离架构

子代理隔离支持多种模式（`AgentTool.tsx`）：

- Worktree：创建一个临时 git worktree，使子代理拥有自己的一份仓库副本，可以在其中修改而不影响父级的工作树。
- Remote（仅内部）：在远程 Claude Code Remote 环境中启动，始终在后台运行。
- In-process（默认）：与父级共享文件系统，但在隔离的对话上下文中运行。

子代理的权限覆盖逻辑（`runAgent.ts`）涉及若干具体规则。当子代理定义了 `permissionMode` 时，该覆盖会被应用，除非父级已处于 `bypassPermissions`、`acceptEdits` 或 auto 模式，因为这些模式始终优先，它们代表着用户就安全性与自主性之间的权衡做出的明确决定。对于异步代理，系统通过一条级联规则判断是否避免弹出提示：先看显式的 `canShowPermissionPrompts`，再看 bubble 模式（始终显示，因为它们会升级到父终端），最后是默认值（同步代理显示提示，异步代理不显示）。能够显示提示的后台代理会设置 `awaitAutomatedChecksBeforeDialog: true`，确保分类器和钩子在打断用户之前完成解析。

这些隔离模式占据设计空间中的不同位置。基于容器的隔离（SWE-Agent 和 OpenHands 采用（Yang et al., 2024; Wang et al., 2024b））提供更强的资源边界，但需要容器基础设施。仅上下文隔离（AutoGen 等基于对话的框架采用（Wu et al., 2024））共享文件系统但分离对话历史。Claude Code 基于 worktree 的隔离在不引入容器编排的前提下提供了工作区级别的文件系统隔离，借助的是 Git 的内置机制。

当向 `runAgent()` 显式提供 `allowedTools` 时（`runAgent.ts`），会应用两层权限作用域模型。来自 `--allowedTools` 的 SDK 级权限被保留：“来自 SDK 使用方、应作用于所有代理的显式权限。”但会话级规则会被替换为子代理声明的 `allowedTools`。当未提供 `allowedTools` 时（常见的 AgentTool 路径），父级的会话级规则被继承，不做替换。

### 8.3 侧链转录

每个子代理都把自己的转录写为单独的 `.jsonl` 文件，并附带一个 `.meta.json` 元数据文件（`sessionStorage.ts`、`runAgent.ts`）。这种侧链（sidechain）设计意味着子代理的历史会被保留下来用于调试与审计，但不会使父级会话文件膨胀。只有子代理的最终回复文本和元数据会返回父对话上下文；子代理的完整历史从不进入父级的上下文窗口，从而遵循“上下文即瓶颈”原则。

仅返回摘要的模型是一种刻意的上下文节约选择：在代理之间共享完整转录历史的基于对话的框架，随着代理数量增长会面临上下文爆炸的风险。即便是隔离上下文的并行也带来可观成本。在 plan 模式下，Claude Code 的 agent teams 消耗的 token 约为标准会话的 7 倍（Anthropic, 2025b），这使得当子代理同样处于隔离上下文时，仅返回摘要变得更加关键。

对于 agent teams 中的多实例协调，执行框架（harness）使用文件锁而非消息代理或分布式协调服务（Anthropic, 2025b）。每个 teammate 都有自己的 inbox JSON 文件（`utils/teammateMailbox.ts`）；任务分配及其他代理间消息在按 inbox 加锁的锁文件（`utils/lockfile.ts`）保护下被推入接收方的 inbox，文件存储在可预测的文件系统路径上。这以吞吐量换取了两项特性：零依赖部署（无需外部基础设施）和完全可调试性（任何代理的状态都可以通过读取纯文本 JSON 文件来检查）。

## 9 会话持久化与恢复

编码代理中的会话持久化涉及在仅追加日志、结构化数据库、基于检查点的快照和无状态架构之间做出设计选择，它们在可审计性、查询能力和部署复杂度上各有不同的权衡。Claude Code 的持久化设计实现了表 1 中的仅追加持久状态原则。会话作用域权限仅存在于内存中，不会被序列化到转录，因此用 `--resume` 启动的新进程会根据 CLI 参数和磁盘设置重建权限上下文；重建后的上下文不认识的任何请求都会回退到拒绝优先（deny-first）提示。

当 auth-test 任务推进到本节时，会话中已包含原始提示、工具调用与结果、压缩边界，以及探索认证模块所产生的子代理摘要（第 8 节）。本节要问的是：这些产物中哪些被持久记录，以及在不再沿用会话旧有权限授予的情况下，日后可以恢复出什么。

**图 8** 会话持久化与上下文压缩。该图将实时会话状态（上下文窗口、压缩）与持久化存储（会话转录、`history.jsonl`、子代理侧链、检查点）区分开来。转录可恢复消息，但不恢复会话作用域权限。

| --- | --- |
| 对话比上下文更长寿 | 一次会话的有用寿命不能被模型的上下文窗口所限制。磁盘上的转录记录了持久的会话事件，因此压缩可以回收实时视图而不终结对话。 |
| 对话会超出单一路径 | 会话不应被困在单一线性轨迹上。仅追加的转录让用户可以回退、恢复或分叉到新的分支，而不丢失先前的工作。 |

Claude Code 的持久化机制会在事件发生时把对话（消息、工具结果和压缩边界）写入磁盘。

### 9.1 转录模型

会话转录以大部分仅追加（append-only）的 JSONL 文件形式存储在项目特定路径下（显式清理导致的重写是例外）（图 8）。`getTranscriptPath()` 函数（`sessionStorage.ts`）将其计算为 `` join(projectDir, `${getSessionId()}.jsonl`) ``，其中 `projectDir` 先通过检查 `getSessionProjectDir()`（在恢复/分支时由 `switchSession()` 设置）来确定，若不存在则回退到 `getProjectDir(getOriginalCwd())()`。

三条持久化通道独立运作：

1. 会话转录：包括 user、assistant、attachment 和 system 消息在内的对话记录，外加压缩及其他元数据事件。按项目作用域，每个会话一个文件。
2. 全局提示历史：仅包含用户提示，存储在 Claude 配置主目录下的 `history.jsonl` 中（`history.ts`）。`makeHistoryReader()` 生成器通过 `readLinesReverse()` 以逆序产出条目，支持上箭头与 `ctrl+r` 导航。
3. 子代理侧链：每个子代理单独的 `.jsonl` + `.meta.json` 文件（第 8.3 节）。

会话转录除简单消息外还存储若干类事件，包括压缩标记、文件历史快照、归属快照和内容替换记录。仅追加的 JSONL 格式是刻意之选，它偏向可审计性与简洁性，而非查询能力。每个记录的事件都是人类可读、可纳入版本控制、无需专门工具即可检查的。以数据库为后端的替代方案能对会话历史实现更丰富的查询，但会引入部署依赖并降低透明度。

会话身份系统把 `sessionId` 与 `sessionProjectDir` 配对，二者在恢复或分支时一同设置。转录路径必须使用消息写入时处于活动状态的同一个项目目录，以免钩子（hook）在错误的目录中查找。

### 9.2 恢复、分叉，以及不恢复权限

`--resume` 标志通过重放转录来重建对话（`conversationRecovery.ts`）。分叉（Fork）从既有会话创建新会话（`commands/branch/branch.ts`）。然而，转录并不记录会话作用域权限。用 `--resume` 恢复会启动一个不携带这些权限的新进程，因此用户必须重新授予；而在运行中的会话内部恢复或分叉则保留已授予的权限。这是一种刻意偏向安全保守的设计选择：信任决策不随转录传递。从转录中恢复先前授予的权限会带来便利，但存在把过时信任决策带入已变化上下文的风险。该架构选择在新进程中重新授予，而非隐式持久化，并接受由此产生的用户摩擦。

`compact_boundary` 标记经过精心设计，以便与持久化协同工作。`annotateBoundaryWithPreservedSegment()` 函数（位于 `compact.ts`）在边界事件中记录 `headUuid`、`anchorUuid` 与 `tailUuid`。这些 UUID 使会话加载器能够在读取时修补消息链：被保留的消息在磁盘上保持其原有的 `parentUuids`，加载器则借助边界元数据将它们正确连接起来。这种「以追加为主」（mostly-append）的设计意味着上下文压缩（compaction）不会修改或删除此前已写入的转录文本行。Claude Code 中的「检查点」（checkpoints）是用于 `--rewind-files` 的文件历史检查点，存放于 `~/.claude/file-history/<sessionId>/`。它们是用于回退文件系统改动的文件级快照，而并非通用的检查点存储。

前文各节记录了 Claude Code 对一系列反复出现的设计问题所给出的回答。下一节将把 Claude Code 的设计选择与两个在架构上相互独立的 AI 代理系统进行对照。

## 10 对比分析：Claude Code、OpenClaw 与 Hermes Agent

前文各节记录了 Claude Code 就循环架构、安全性、可扩展性、上下文管理、任务委派与持久化等反复出现的设计问题所给出的回答。为了把这些发现置于更广阔的代理设计空间之中，本节将 Claude Code 与两个独立的开源 AI 代理系统进行比较，这两个系统从根本不同的起点出发，回答了许多相同的设计问题。

OpenClaw 是一个本地优先（local-first）的 WebSocket 网关，把各类消息界面（WhatsApp、Telegram、Slack、Discord、Signal 等）连接到内嵌的代理运行时，并在 macOS、iOS 与 Android 上配有伴随应用（Steinberger and OpenClaw Contributors, 2026）。Hermes Agent 是单个 Python 进程，其角色由启动它时所使用的入口点决定，它拥有一个持久化层，并以众多界面面向同一个运行时（Nous Research, 2026）。4 Hermes 发行版暴露三个控制台脚本：用于 CLI 与网关控制器的 `hermes`、用于批处理运行的 `hermes-agent`，以及用于 Agent Client Protocol 适配器的 `hermes-acp`，后者让外部 IDE 能够像 Hermes 自己的网关托管其他代理那样托管 Hermes。Claude Code 是绑定于单一仓库会话的 CLI 编码执行框架（coding harness），而 OpenClaw 是面向多渠道个人助理的常驻控制平面（control plane），Hermes 则是一个进程，其角色与界面集合由启动它的入口点决定。三个系统占据代理设计空间的不同区域。这一比较的价值在于展示：当部署情境发生变化时，同样的反复出现的问题如何产生不同的架构回答。

4 基于源码对 Hermes 的阅读揭示出两处项目自身文档与实现脱节的情形：`SECURITY.md` 记录的审批模式分类为 on/auto/off，而 `tools/approval.py:721-750` 返回的是 manual/smart/off；`SECURITY.md` 与 `AGENTS.md` 都描述委派深度默认为二，而 `tools/delegate_tool.py:128` 设置 `MAX_DEPTH = 1`。我们引用源码而非文档。

### 10.1 六个对比维度

表 3 汇总了六个维度上的比较。每个维度对应一个三个系统都必须回答的设计问题。超出这六个维度的 Hermes 能力将在 10.2 节单独讨论。

**系统范围与部署模型。** Claude Code 作为临时的 CLI 进程运行，绑定于单一仓库。每个会话随终端开始并结束。OpenClaw 作为常驻守护进程运行（默认端口 18789，仅回环），拥有全部消息界面连接，并通过类型化的 WebSocket 协议协调客户端、工具与设备节点。Hermes Agent 作为单个长期存活的 Python 进程运行，其角色由启动时所用的入口点固定；其网关子命令通过两层适配器体系驱动消息界面（`gateway/platforms/` 下的内置适配器，加上 `plugins/platforms/` 下针对 Google Chat、IRC 与 Teams 的插件层），并把会话状态与多代理看板（multi-agent-board）状态持久化到两个磁盘上的 SQLite 文件（`state.db` 与 `kanban.db`），而不是持久化到类型化的 WebSocket 协议。这使得 Hermes 在信任拓扑上更接近 OpenClaw 而非 Claude Code，但在进程拓扑上更接近 Claude Code 而非 OpenClaw；关于把代理中介（broker）放在何处的设计问题，在 Hermes 中的回答是根本没有中介。这些系统范围上的差异是比较中最根本的架构分歧：它们决定了其他每一个设计问题如何被提出。三个系统之间还存在一种组合关系：OpenClaw 可以通过其 ACP（Agent Client Protocol）集成把 Claude Code、OpenAI Codex 与 Gemini CLI 作为外部编码执行框架来托管，而 Hermes Agent 同时处在 ACP 宿主/访客（host/guest）分工的两侧——其网关托管平台适配器与工具服务器，而其 `hermes-acp` 适配器让外部 IDE 托管 Hermes，从而使这些系统可以相互堆叠，而不只是彼此替代。

**信任模型与安全架构。** 三个系统应对不同的威胁模型。Claude Code 假设不可信的模型运行在可信开发者的机器上：拒绝优先的权限系统（第 5 节）对每次工具调用进行评估，ML 分类器提供自动化安全评估，七种权限模式构成渐进的自主性谱系。OpenClaw 假设每个网关实例只有一个可信操作者。其安全架构从身份与访问控制（DM 配对码、发送方白名单、网关认证）入手，而不是从逐动作的安全分类入手。工具策略对每个代理使用可配置的允许/拒绝列表，而不是集中式分类器。沙箱是可选择启用的功能，支持多种后端（Docker、SSH 或 OpenShell）和可配置范围（按代理、按会话或共享）；启用非主模式（non-main mode）时可以把所有非主会话放入沙箱，不过沙箱默认并不启用。OpenClaw 的安全文档明确指出，共享网关上的对抗性多租户隔离不是受支持的安全边界。Hermes Agent 采取第三种立场。工具授权集中在一个文件（`tools/approval.py`）中，暴露三种模式（manual、smart、off）以及无条件的 `HARDLINE_PATTERNS` 底线，无论处于何种模式都会拦截 `rm -rf /`、`mkfs`、对块设备的裸 `dd`、fork 炸弹以及系统关机命令（Tier B）。smart 模式会运行辅助 LLM 风险评估；源码内的一处注释把 OpenAI Codex 的 smart approvals 列为设计灵感。由于 Hermes 运行在众多界面之上，同一审批流程被渲染四次：CLI 提示，Telegram、Discord 与 QQBot 上的网关审批键盘，面向 IDE 客户端的 ACP `request_permission` 往返，以及用于无人值守运行的仅 cron 模式。与 Claude Code 的七模式分类和由 ML 分类器驱动的 auto 模式相比，Hermes 的模式分类更小，但具有相同的多层结构：无条件安全底线、默认交互式提示、可选的辅助 LLM「smart」路径。架构上的回答相同，只是界面数量不同。三者之间的差异反映了信任边界所在的位置：Claude Code 把它置于模型与执行环境之间，OpenClaw 把它置于网关周界，Hermes 则介于两者之间，像 Claude Code 一样采用逐动作审批，但像 OpenClaw 一样通过众多界面呈现。

**代理运行时与工具编排。** 三个系统都实现了代理循环（agent loop），但循环在各自架构中所处的位置不同。在 Claude Code 中，`queryLoop()` 异步生成器（第 4 节）是系统的中心：所有界面都汇入其中，它直接管理上下文组装、模型调用、工具分派与恢复。在 OpenClaw 中，代理运行时是内嵌的 pi-coding-agent 核心（来自 pi-mono 项目、由 OpenClaw 集成的外部 SDK），位于更大的网关分派层之内。网关的 agent RPC 校验参数、解析会话并立即返回；随后内嵌运行器执行代理循环，同时通过网关协议回发生命周期事件与流事件。运行通过按会话的队列和可选的全局通道（global lane）串行化，防止在多渠道界面之间出现工具与会话竞争。在 Hermes Agent 中，循环是 `AIAgent.run_conversation`（`run_agent.py`）内部的同步 while 循环，受迭代次数（默认 90）和单独的迭代预算约束；预算耗尽时，一次剥离工具调用的摘要调用让代理给出收尾消息，而不是在思路中途终止（Tier B）；每次迭代发送由 `model_tools.get_tool_definitions()` 收集的工具 schema，并把所有工具调用路由到 `model_tools.handle_function_call`，`tools/*.py` 中的工具文件在导入时自行注册，因此新增一个工具只需一次 `registry.register()` 调用；单条助手消息返回多个工具调用时会并行执行，并以串行执行作为回退。三个系统都遵循 ReAct 模式（Yao et al., 2022）：OpenClaw 的循环是控制平面之内的一个组件，而非控制平面本身；Hermes 的循环在运行时层面与 Claude Code 的循环对等，但实现形态不同——它是同步 Python 循环加线程管理的并发，而不是会 yield 的异步生成器。

**扩展架构。** Claude Code 的四种扩展机制（MCP、插件、技能、钩子）按上下文成本组织（第 6 节）：钩子（hook）消耗零上下文，技能（skill）消耗低上下文，MCP 服务器一旦加载其工具 schema 就消耗高上下文。这四者都扩展单个代理的上下文窗口与工具面。OpenClaw 使用清单优先（manifest-first）的插件系统，具有四个架构层（发现、启用、运行时加载、界面消费）和十二种能力类型，包括文本推理、语音、媒体理解、图像/音乐/视频生成、Web 搜索与消息渠道。插件把能力注册到中央注册表；网关读取注册表以暴露工具、渠道、提供方设置、钩子、HTTP 路由、CLI 命令与服务。OpenClaw 还拥有独立的技能层，具有多种来源（工作区、项目级、个人、托管、内置与额外目录，其中工作区技能优先级最高），外加一个公共注册表（ClawHub），并通过内置的 `openclaw mcp` 命令（服务器与出站客户端注册表）支持 MCP。Hermes Agent 则提供五个扩展面，相较 Claude

Code 的四个 Tier B 扩展面：三个与 Claude Code 处于同一层级（`plugins/<name>/` 下带生命周期钩子（hook）的通用插件、`skills/` 下的捆绑技能（skill），以及在 `config.yaml` 中配置的 MCP 服务器），另有两个扩展面沿不同轴线延伸（`plugins/memory/<name>/` 下的可插拔记忆提供者，以及 `plugins/model-providers/<name>/` 下的可插拔模型提供者），它们让 Hermes 得以替换后端，而不是拦截事件。Hermes 中的钩子既可以是进程内的 Python 回调，也可以是配置驱动的外部 shell 命令，二者都通过同一个钩子管理器分发。当 Hermes 启动 stdio MCP 服务器时，子进程的环境在启动前会被限制在一个很小的系统变量允许列表内，并且 `npx`/`uvx` 包名会对照 OSV 恶意软件数据库进行筛查。三者的架构差异在于扩展作用于何处：Claude Code 的扩展修改单个代理的行动面，OpenClaw 的插件把网关的能力面扩展到所有代理，而 Hermes 的扩展则在类 Claude Code 的按代理能力面之上增加第二条轴线，就地替换整个记忆与模型提供者后端，而不是围绕它们拦截事件。

**记忆、上下文与知识管理。**
三个系统都使用透明的、基于文件的记忆，而不是不透明的数据库。Claude Code 加载四级 `CLAUDE.md` 层级，并通过五层上下文压缩（compaction）流水线来管理上下文压力（第 7 节）。记忆检索使用基于 LLM 的文件头部扫描。OpenClaw 在会话开始时把工作区引导文件注入系统提示：五个核心文件（`AGENTS.md`、`SOUL.md`、`TOOLS.md`、`IDENTITY.md`、`USER.md`），外加按条件注入的 `BOOTSTRAP.md`、`HEARTBEAT.md` 和 `MEMORY.md`，过大的文件会被截断。另外，记忆系统管理三类文件：用于长期持久事实的 `MEMORY.md`、带日期戳的每日笔记（`memory/YYYY-MM-DD.md`），以及可选的、用于 dreaming 清扫摘要的 `DREAMS.md`。配置了嵌入（embedding）提供者后，记忆搜索使用结合向量相似度与关键词匹配的混合检索。一个实验性的 dreaming 系统执行后台整合，对候选项打分，只把合格条目从短期回忆提升到长期记忆。在压缩之前，OpenClaw 会自动提醒代理把重要笔记保存到记忆文件，以防上下文丢失。Hermes 的压缩是一个带 token 预算尾部保护的辅助 LLM 摘要器，前面还有一个工具输出修剪阶段；摘要会被加上一段很长的“仅供参考”前言，告诉代理这次压缩属于背景上下文、不是新指令，并且持久记忆（`MEMORY.md`、`USER.md`）仍然具有权威性（Tier B）。Claude Code 的 `CLAUDE.md` 层级是固定的、压缩有五层，而 Hermes 的压缩层数更少，却增加了上下文文件的注入前扫描：`AGENTS.md`、`.cursorrules` 和 `SOUL.md` 等文件会对照一份注入模式列表和不可见 Unicode 字符进行检查，任何命中都会用 `[BLOCKED: ...]` 标记替换该文件的内容。三者都共享同一条设计承诺——记忆对用户可见、可编辑——但对同一个上下文管理问题给出了不同答案：Claude Code 投资于渐进式上下文压缩（五层，且具备缓存感知）；OpenClaw 投资于结构化的长期记忆提升（dreaming、每日笔记、记忆搜索）加上可插拔的压缩提供者和会话修剪，尽管其压缩流水线不如 Claude Code 的五层体系那样渐进；Hermes 投资于注入前内容扫描，以及在提示层面把持久记忆与已压缩历史隔离开，而不是更深的压缩栈。

**多代理架构与路由。**
这一维度揭示了最鲜明的架构差异。Claude Code 的多代理模型是任务委派：父代理派生（spawn）子代理（Explore、Plan、通用型以及自定义类型），它们在隔离的上下文窗口中运行、工具集受限，并且只返回摘要式结果（第 8 节）。工作树（worktree）隔离提供了文件系统层面的分离。OpenClaw 区分了两类不同的问题。第一，多代理路由：单个网关可以承载多个完全隔离的代理，每个代理都有自己的工作区、认证配置、会话存储和模型配置，并通过确定性绑定规则路由到特定频道或发送者。第二，子代理委派：在单个代理内部，可以派生后台运行，嵌套深度可配置（最大 5，默认 1，建议 2），在受支持的频道上可使用绑定到线程的会话，并且可按深度配置工具策略。OpenClaw 的项目愿景明确拒绝把代理层级框架作为默认架构。Hermes Agent 则沿另一条不同的接缝切分这个问题。逐轮委派通过 `delegate_task` 工具进行，它在线程池中派生子 `AIAgent` 实例；父代理阻塞等待子代理返回摘要，并发默认上限为三个子代理，深度上限为一（被钳制在 [1, 3] 区间内），叶子子代理默认不能自行再委派（嵌套委派需通过 orchestrator 子代理和更高的派生深度设置显式开启），并且子代理始终在禁用持久记忆的情况下运行，因此它们无法读写父代理的笔记（Tier B）。除逐轮委派之外，v0.13 的 Kanban 子系统是一个由 SQLite 支持的工作队列，多个 Hermes worker 配置（profile）在此认领、发送心跳并完成任务，具备过期认领回收机制，以及在连续两次尝试失败后自动阻塞（`hermes_cli/kanban_db.py:2703`）。三者的区别之所以重要，是因为 Claude Code 的子代理是单个用户编程会话内的从属工作者，OpenClaw 的多代理路由创建的是真正独立的代理实例，通过不同频道服务不同用户或目的，而 Hermes 把严格的逐轮委派默认值与一个独立的 Kanban 层结合起来，让多个代理进程在一块持久共享的看板上协作——这是 Claude Code 和 OpenClaw 没有以同样形式提出的问题。

### 10.2 Hermes Agent：对比表之外的能力

Hermes 的会话持久化使用单个 WAL 模式的 SQLite 数据库，对所有会话消息提供全文检索，并用父会话链记录由压缩触发的分裂（Tier B）。Claude Code 按项目把会话持久化到 JSONL 文件（第 9 节），而 Hermes 的选择开箱即提供跨会话搜索和并发读取支持。当网关在对话中途重启时，会话会在下一条消息到达时自动恢复，这由对话记录时间戳的新鲜度逻辑驱动，默认窗口为一小时。内置的 cron 调度器和 webhook 订阅系统让代理可以按计划表达式或外部 HTTP 事件无人值守地运行；cron 会话运行时禁用持久记忆，并带有一个默认 600 秒的可配置不活动超时。该发行版还包含一个后台“curator”循环，它审查代理创建技能、归档陈旧技能，且从不删除，并且只作用于带有代理来源标记的技能，因此捆绑技能和从 hub 安装的技能不在其范围内。这些能力都无法干净地映射到主表所用的六个对比维度上，这正是它们在此以 Hermes 专属附录的形式出现、而不是作为表 3 中单元格的原因。OpenClaw 的独特能力（扩展架构下的 ClawHub 插件注册表，以及记忆与上下文下的 dreaming 记忆子系统）已经占据了这六个维度中的单元格，因此不需要平行的附录。本小节中的 Hermes 增补源于其持久进程的适用范围，这是 Hermes 与 OpenClaw 共享、而 Claude Code 的按会话 CLI 模式不具备的一种部署上下文属性。

### 10.3 对比揭示了什么

这一对比引出关于 AI 代理系统设计空间的三点观察。

第一，第 3.1 节提出的那些反复出现的设计问题（推理位于何处、采取何种安全姿态、如何管理上下文、如何组织可扩展性）同样适用于编程代理之外。OpenClaw 从多频道个人助理而非受仓库约束的编程工具这一出发点来回答其中每一个问题，Hermes Agent 则从单进程、多界面的部署形态而非 CLI 执行框架或多频道网关来回答它们。问题是稳定的；答案随三个系统的部署上下文而变化。

第二，这些系统在若干维度上做出了不同的押注。Claude Code 投资于渐进的逐动作安全评估；OpenClaw 投资于边界层面的身份与访问控制；Hermes 处于两者之间，既有像 Claude Code 那样的逐动作审批，又像 OpenClaw 那样通过许多界面呈现。Claude Code 把代理循环（agent loop）视为架构中心；OpenClaw 把网关控制平面视为中心，并把代理循环作为一个组件嵌入其中；Hermes 的循环在运行时层面与 Claude Code 的循环对等，占据相同的架构位置，而不是坐在网关分发层内部。Claude Code 的扩展修改单个上下文窗口；OpenClaw 的插件扩展共享的网关能力面；Hermes 在类 Claude Code 的按代理能力面之上增加第二条轴线，就地替换记忆与模型后端，而不是拦截事件。这些差异并非任意：它们源于三个系统不同的信任模型和部署拓扑。

第三，三个系统之间的组合关系具有架构意义。OpenClaw 可以通过 ACP 把 Claude Code 作为外部编程执行框架来承载，而 Hermes Agent 同时处在宿主/访客二分法的两侧：其网关承载平台适配器和工具服务器，其 `hermes-acp` 适配器又让外部 IDE 承载 Hermes。这些系统是可组合的，而不是互相排斥的替代品，这表明 AI 代理的设计空间不是扁平分类法，而是分层分类法，网关层系统与任务层执行框架可以在多个位置上组合。

## 11 相关工作

### 11.1 编程代理分类

AI 编程工具可以按其所支持的自主行动程度来组织（表 4）。GitHub Copilot（Chen et al., 2021）等行内补全工具在编辑器内建议代码片段，但不采取自主行动。包括 Cursor 和 Windsurf 在内的对话集成产品增加了会话式交互和多文件编辑，但仍与 IDE 环境耦合。代理式 CLI 工具，包括 Claude Code、OpenAI 的 Codex CLI 和 Aider（Gauthier, 2024），从命令行运行，可以在单个请求内自主执行 shell 命令、读写文件并对输出反复迭代。Devin、SWE-Agent（Yang et al., 2024）和 OpenHands（Wang et al., 2024b）等完全自主系统追求最少的人工监督，通常运行在沙箱化的云环境中。

Claude Code 与更高自主性的代理共享一些特性（自动模式分类器、后台代理执行、远程环境），但默认保留交互式审批。SWE-Bench（Jimenez et al., 2023）和 HumanEval（Chen et al., 2021）等评测基准推动了学术界对编程代理的大部分关注。本文从源代码层面考察 Claude Code 的内部架构。

### 11.2 代理架构模式

Claude Code 的核心循环遵循 ReAct 模式（Yao et al., 2022）：模型生成推理与工具调用，执行框架（harness）执行动作，结果再反馈到下一次迭代。Toolformer（Schick et al., 2023）证明了语言模型可以学会使用工具。Claude Code 使用多达 54 个内置工具和一套分层权限系统。更广阔的设计空间已被若干综述勾勒。Weng（2023）提出了如今已成标准的规划、记忆与工具调用三分法，Wang et al.（2024a）梳理了早期的自主代理工作。Xu（2026）围绕三个反复出现的权衡（自主性 vs. 可控性、延迟 vs. 准确性、能力 vs. 可靠性）来组织这一领域，而这些权衡贯穿于我们的分析之中；Hu et al.（2024）则把代理设计本身视为在组件、算法和评估函数上的搜索问题。本文刻画的是该空间中的一个具体点。

一篇关于“代码作为代理执行框架”的最新综述把代码不仅视为模型输出，也视为推理、行动、环境建模和基于执行的验证的基底（Ning et al., 2026）。这一框架与本文关注模型周围的执行框架、而非仅关注基准分数相一致。

**近期的运行时机制。**
近期的综述和系统明确提出了若干执行框架选择。Graph Engineering 将任务依赖、代理通信和执行状态分离（Feng et al., 2026），Self-Evolving Coding Agents 综述则按目标、时机和反馈来源来组织持久性变更（Zhou et al., 2026）。LoopsBench 和 LoopArena 评估前置条件、保留的回归检查以及控制器决定检查或停止的方式如何塑造编程循环（Li et al., 2026; Wang et al., 2026a），Symphony 把问题调度与编程代理自身的循环分离（OpenAI, 2026b）。在恢复方面，Resume Means Resume 对照其声称的语义测试工作流框架的检查点与恢复行为（Khan, 2026），Temporal 的 Deep Agents 集成把每次模型调用和 I/O 工具调用作为 Temporal activity 运行，而控制循环在工作流内部重放（Temporal Technologies, 2026）。Living-Harness 在回合之间更新情景记忆和状态图，而模型和工具保持固定（Du et al., 2026）。Graphiti 和 Cognee 把实体关系存储在知识图谱中（Zep, 2026; Cognee, 2026）。APPA 在工具结果进入代理上下文之前对其进行校验，把调用工具的权限与接纳其返回数据区分开来（Kravchenko et al., 2026）。在协议层面，

从业者文献已经收敛到少数几种反复出现的模式，而 Claude Code 的架构正是这些模式的实例。Anthropic 自己的《Building Effective Agents》（Schluntz and Zhang, 2024）区分了代理与工作流，并主张采用简单的可组合模式，而非重型框架。Martin（2026）综合了在生产系统中观察到的七种模式，包括赋予代理文件系统与 shell 访问能力作为通用行动层，以及按需发现操作，而不是预先加载所有工具 schema。Chase（2025）观察到，Claude Code 的规划工具“基本上是一个空操作（no-op）”，其价值在于让代理保持在正轨上，而不是执行任何外部计算。Wang（2025）认为，权威（authority）是学术框架最常遗漏的要素，并称信任是生产级代理设计中“最被忽视的要素”，而第 5 节的权限分析试图弥合这一缺口。Huyen（2025）让复合错误（compound-error）的担忧变得具体：在每步 95% 准确率下，一个 100 步的任务只有 0.6% 的时间能够成功，这促成了我们在第 4 节和第 5 节追踪的逐步验证模式。OpenAI 在其关于 harness 工程的写作中也提出了类似观点，将 harness 本身的设计视为一项核心工程任务（OpenAI, 2026a）。最近还出现了一个名为循环工程（loop engineering）的新概念：开发者不再每一轮都提示代理，而是构建一个循环，由它发现工作、分配工作、检查结果并决定下一步做什么，所用构件正是本文记录的同一批原语，例如技能（skill）、MCP 服务器和子代理（Osmani, 2026）。它让单个开发者能够以自主方式指挥多得多的工作，并引起了关注，包括 Claude Code 团队自身的关注，不过减少人逐轮的参与也加剧了第 14 节将重新讨论的长期开发者能力担忧。

**上下文管理。** 表 5 给出了上下文管理方法的设计空间分类。Claude Code 的五层上下文压缩（compaction）流水线在升级之前，会在不同粒度上应用多种策略，并带有缓存感知压缩和读取时虚拟视图（virtual-view-on-read）语义。Zhang et al. (2025a) 刻画了该设计所缓解的两种失效模式（摘要丢失领域细节，以及迭代式上下文重写造成的细节损失），并转而提出将上下文视为一本随时间累积策略的“演进式手册（evolving playbook）”。Claude Code 的做法与这一框架一致，因为 CLAUDE.md 层级累积结构化指令，而不是反复对它们做摘要。Hu et al. (2025) 区分了上下文工程（context engineering）与代理记忆（agent memory）：上下文工程处理瞬时的组装，而记忆涵盖持久的事实知识与经验痕迹。Claude Code 的架构以同样的方式将二者分离，把上下文压缩流水线与基于文件的记忆层级配对使用。

**安全与权限。** 生产级编码代理采用的安全架构沿三条轴线变化：批准模型（逐动作提示、分类器介导的自动化，或不做提示而做事后审查）、隔离边界（操作系统级容器、文件系统沙箱、权限受限的工具池，或没有隔离），以及恢复机制（版本控制回滚、会话级权限重置，或基于检查点的回退）。SWE-Agent 和 OpenHands（Yang et al., 2024; Wang et al., 2024b）主要依赖 Docker 容器隔离，提供环境级沙箱，约束代理的所有动作。Codex CLI 支持沙箱模式和针对 shell 命令的批准策略。OpenCode 和 Cline 也提供工具批准控制（Anomaly, 2026; Cline, 2026）。Aider（Gauthier, 2024）以 Git 作为其主要安全机制，使所有更改都可通过版本控制回滚。Claude Code 结合了逐动作的拒绝优先（deny-first）规则、用于自动批准的基于机器学习的分类器、可选的 shell 沙箱，以及会话级的权限不恢复机制，分层使用多种机制，而不是依赖单一隔离边界。

沙箱相关的报告让这一边界变得具体。E2B 和 OpenSandbox 通过 API 暴露隔离的执行环境（E2B, 2026; OpenSandbox, 2026）。OpenAI 关于 Windows 沙箱的讨论描述了将写访问限定在工作目录和配置的可写根目录内，并对这些根目录内选定的只读路径设置显式拒绝规则（OpenAI, 2026c）。Cursor 的云代理报告补充了同一问题的云端侧面：网络策略、机密信息脱敏（secret redaction）和凭据管理成为代理环境的一部分（Ma, 2026）。这些细节使安全边界成为一种执行边界，而不只是批准提示。

**协议与可扩展性。** Claude Code 用作其主要外部工具集成方式的 Model Context Protocol 已成为事实标准，拥有可观的生态和相应的攻击面。Hou et al. (2025) 编目了 26 个主要目录中数千个社区开发的 MCP 服务器，并将 MCP 特有的威胁归入四类攻击者和十六种场景，包括工具投毒（tool poisoning）、rug pull 和跨服务器遮蔽（cross-server shadowing）。第 5 节分析的权限与拒绝规则机制，以及第 6.2 节中的预过滤步骤，可以看作该综述所呼吁的缓解措施的运行时侧面。同样的观点也适用于更高层的工具设计。NSA 的指南将 MCP 安全视为一个生命周期问题，横跨协议设计、运行时调度、与外部服务的集成以及长期监控（National Security Agency, 2026）。一份关于代理优先工具设计的提案主张，面向代理的 API 应提供搜索、解析、预览、执行、验证和恢复等阶段，而不仅仅是面向人类的 CRUD 端点（Pan, 2026）。按此理解，MCP 服务器、插件（plugin）、技能、SDK 以及代理间协议构成了一条工具供应链：它们扩展了代理能做的事，但也需要身份、允许列表、版本管理、审计日志和撤销机制。

**软件架构。** 分层架构模式（Garlan et al., 1993）为我们的五层分解提供了借鉴。基于角色的访问控制模型（Sandhu et al., 2002）为权限模式系统提供了理论。浏览器沙箱（Reis and Gribble, 2009）是一种类似的逐进程隔离方法。多代理系统理论（Wooldridge, 2009）有助于解释子代理委派。

**定位。** 以往关于编码代理的工作聚焦于基准测试（代理解决任务的能力如何）、框架（如何组合代理）和产品（用户能做什么）。本文贡献的是对一个生产级编码代理的、基于源码的设计空间分析，使用源码级分析和架构比较来揭示设计选择与权衡。它借鉴了软件架构案例研究的传统（Garlan et al., 1993），但将其应用于基于 LLM 的代理：系统地识别设计问题、梳理备选方案，并将 Claude Code 的选择与 OpenClaw 和 Hermes Agent 的选择进行对比，后两者是运行于不同部署情境的两个独立 AI 代理系统。

## 12 讨论

前文各节的分析记录了 Claude Code 如何回答关于循环架构、安全姿态、可扩展性、上下文管理、委派和持久化的反复出现的设计问题。每个答案都反映了设计空间中的一个位置，该空间存在真实的备选方案和可度量的权衡。本节考察这些答案放在一起阅读时揭示了什么：它们所反映的设计哲学（12.1 节）、它们造成的价值张力（12.2 节）、它们带来的架构权衡（12.3 节）、它们产生的经验性预测（12.4 节），以及在各子系统间反复出现的横切承诺（12.7 节）。2.1 节的五价值框架组织本节的结构。

### 12.1 设计哲学

第 2 节引入的价值观和设计原则预示了一种在运营基础设施而非决策脚手架（decision scaffolding）上投入的架构。实现证实了这一点：第 3 至第 9 节记录的架构绝大多数是确定性基础设施（权限闸门、工具路由、上下文管理、恢复逻辑），LLM 仅作为无状态的补全端点被调用。据估计，约 1.6% 的代码库构成决策逻辑，其余 98.4% 是运营性的执行框架。这一比例并非偶然。

第 2.2 节记录的设计原则支撑了这一做法：执行框架创造让模型能够做出良好决策的条件，而不是约束模型的选择。

这一设计与代理工程中的主流模式相反：在主流模式中，LangGraph 等框架让模型输出经过带有类型化边的显式图节点，Devin 等系统则将多步规划器与厚重的运营基础设施配对。Claude Code 反其道而行，在丰富的运营执行框架内给予模型最大的决策自由度。工程复杂性存在不是为了约束模型的决策，而是为了促成这些决策。这种分层架构——模型负责推理，执行框架负责强制执行——提出了一个问题：代理式编码工具是否正在向类操作系统的抽象收敛，其中核心循环充当内核，其余一切构成操作系统。

随着前沿模型在编码任务上的实际能力趋于接近，这一设计获得了额外意义：周围运营执行框架的质量成为主要差异化因素，从而验证了一种在基础设施而非决策脚手架上投入的架构。对于代理构建者而言，其含义是：在上下文管理、安全分层和恢复机制等确定性基础设施上投入，可能比围绕能力日益增强的模型添加规划脚手架带来更大的可靠性收益。最近的原生运行时（native-runtime）基准测试为这一原本属于推理性的主张提供了直接的经验支持：保持模型固定、仅改变周围的执行框架，可使单个模型在长时程任务上的得分变化多达 18 分，测试的执行框架中包括 Claude Code 和 OpenClaw（Ding et al., 2026）。

（Tier C）随着模型能力变得更强，对于像 Fable 5 这样能够自行阅读代码库并修复问题的模型，执行框架是否仍然需要？执行框架服务于 2.1 节的五项价值，其中只有一项——能力放大（Capability Amplification）——主要关乎模型有多强。在这一价值内部，更强模型所影响的部分是决策脚手架，例如某些框架包裹在模型周围、用以引导和约束其走向解决方案的规划与控制逻辑。在模型本已很强的领域，例如代码和数学，它能自行得到成功的解，因此这种引导和约束就不那么必要了。其余四项价值主要并不关乎模型有多强，因此服务于它们的执行框架依然存在。可靠执行（Reliable Execution）是部分例外：更强的模型能更准确地理解请求，并更好地修正自己的错误。但上下文窗口仍然有限，会话仍会恢复，模型仍然倾向于每次运行都以不同方式重建同样的东西，因此上下文管理和恢复仍然必要。安全、安保与隐私（Safety, Security, and Privacy）完全不依赖于能力。拒绝优先规则、沙箱、自动模式分类器和审计日志与以往同样重要，而更强的模型风险更大，而不是更安全：Fable 5 本身在风险较高的领域就受到安全分类器的限制（Anthropic, 2026d）。人类决策权（Human Decision Authority）关乎人的决定权，而非模型的能力，因此批准、中断和 transcript 仍保有它们的作用。情境适应性（Contextual Adaptability）类似：强模型仍然是通用模型，没有见过你的代码，因此 CLAUDE.md、技能和 MCP 仍然能让它适配你的项目。约束全部五项价值的 token 经济学也不会放宽，因为更好的模型并不会让 token 免费。

研究甚至在最强的模型上也证实了这一点：仅执行框架的选择就使 Fable 5 的功能通过率和安全通过率变化 10 个百分点或更多（Compagna, 2026）。执行框架并不会随着模型能力增长而变得无用；改变的只是决策脚手架，而且只在模型本已很强的部分，至于执行框架所做的其他一切，其重要性一如既往。

综合来看，前面各节表明，生产级编码代理面临着反复出现的设计选择：推理相对于执行框架位于何处、迭代循环如何组织、默认采用何种安全姿态、扩展面如何划分、上下文如何组装与压缩、子代理如何委派与编排，以及会话如何跨越边界持久化。Claude Code 对这些问题的回答构成了一个连贯的设计点，它在丰富的运营执行框架内赋予模型自主性。

| 价值组合 | 张力 | 证据 |
| --- | --- | --- |

### 12.2 价值张力

第 2.1 节识别出的五种价值会产生张力：追求其中一种价值会约束另一种价值（表 6）。这些张力并非设计失败；它们是同时追求多种价值所导致的结构性后果。我们只报告支持证据最强的那些张力，而非完整的组合集合。

另一个独立的问题是，短期收益是否会削弱开发者的长期能力（第 2.4 节）。一项针对 16 名资深开发者、涵盖 246 项任务的随机对照试验（Becker et al., 2025）发现，AI 工具使开发者慢了 19%，尽管他们主观感受到 20% 的提升。一项针对 807 个代码仓库中 Cursor 采用情况的因果分析（He et al., 2025）发现，代码复杂度上升了 40.7%。一项针对 54 名参与者的脑电图（EEG）研究（Kosmyna et al., 2025）发现，LLM 使用者表现出减弱的神经连接性，且这种减弱在移除 AI 之后仍然持续。研究者提出了用于测量 AI 辅助编程中认知卸载（cognitive offloading）的协议，其动因是担心使用 AI 的学生会在不理解底层逻辑的情况下产出应用（Aiersilan, 2026）。这些发现，加上 2023 年至 2024 年间初级技术岗位招聘下降 25%（Rak, 2025），表明能力放大与长期可持续性之间的张力不仅涉及个体生产力，还延伸至更广泛的开发者人才管道。这些证据为长期能力问题提供了动因，但并未专门针对 Claude Code 的架构。它与依赖有界上下文、工具调用循环和本地生成决策的代理系统最为相关。

### 12.3 架构权衡

表 6 中的张力在四个方面表现为具体的架构权衡。上文记录的长期可持续性关切，在第 12.4 节的经验性预测中浮现出来。

**安全 vs. 自治。** 权限模式（五种始终存在，外加分类器特性开关启用时的 auto，以及内部的 bubble 模式）构成一条梯度：从 plan（用户批准所有计划），经 default、acceptEdits、auto（ML 分类器），直到 bypassPermissions（跳过大多数提示，但安全关键检查仍然保留）。这一递进代表一条单调递减的安全梯度，同时自治性递增。不从对话记录（transcript）中恢复会话范围的权限，反映了一种刻意偏向安全的取舍：新进程启动时不带旧会话的授权。

安全—自治梯度不仅由架构设计塑造，也由用户行为塑造。Anthropic 的自动模式分析（Hughes, 2026）发现，用户批准了约 93% 的权限提示，这表明审批疲劳使交互式确认在行为上变得不可靠。纵向使用数据（McCain et al., 2026）显示，自动批准率从会话数少于 50 时的约 20% 上升到 750 次会话时的 40% 以上，同时会话时长也大幅增加。这些模式表明，用户并非通过审慎的模式选择来穿行于这条梯度，而是通过逐渐习惯化。沙箱化将权限提示的频率降低了约 84%（Dworken and Weller-Davies, 2025），从而把问题重新界定为人因问题：面对不可靠的人类批准，架构层面的应对是减少人必须做出的决策数量。

更根本地说，第 5 节描述的纵深防御（defense-in-depth）架构建立在一条独立性假设之上：如果某一安全层失效，其他层会拦截违规行为。但 Claude Code 的各安全层共享共同的性能与经济约束。自动模式分类器是一次单独的 LLM 调用，具有直接的 token 成本。`bashSecurity.ts` 模块执行基于 AST 的顺序检查，会产生解析延迟。拒绝优先（deny-first）规则求值作用于命令结构。当性能压力推动削减这些成本时，各层可能会同时降级。安全研究者（Adversa.ai, 2026）记录到，包含超过 50 个子命令的命令会回退为单一的通用批准提示，而不再执行逐子命令的拒绝规则检查，因为逐子命令解析会导致 UI 冻结——这表明当独立性假设被违反时，纵深防御就会失效。

这一张力是结构性的。任何使用模型本身进行安全评估的基于 LLM 的代理系统都会面对它。相关的评估标准不是任何单个层能否被绕过，而是必须有多少个相互独立的层同时失效，以及它们是否共享失效模式。

**对抗条件下的权限模型。** 独立的安全研究为权限架构提供了经验验证，具体而言，它揭示了一种图 4 未能捕捉的时间顺序属性。两个经独立验证的漏洞在信任建立之前的初始化顺序上共享同一根因：在较早的版本中，项目初始化期间执行的代码（MCP 服务器连接以及设置环境变量的应用）在用户接受交互式信任对话框之前就已运行<sup>5</sup>。那个信任建立之前的执行窗口落在拒绝优先求值流水线（`permissions.ts`）之外，形成了一个在结构上享有特权的阶段，此时第 5 节记录的安全保障尚未生效。在所分析的快照中，标准的交互式启动路径要求在接受信任之后，才执行钩子（hook）、连接项目 MCP 服务器，并应用超出安全允许列表范围的项目级设置环境变量（`hooks.ts`、`main.tsx`、`managedEnv.ts`）。

这一模式表明，权限流水线描绘的是安全检查的空间顺序，却没有捕捉时间维度：具体而言，即在会话初始化过程中每个机制何时变为有效。修补之前的初始化序列（先执行 MCP 服务器，再接受信任，最后执行权限强制）制造了一个窗口，在这个窗口中，可扩展性架构（第 6 节）先于安全架构（第 5 节）完全介入而运作。这一发现通过增加一个安全维度，细化了可扩展性与简单性之间的张力：可扩展性制造攻击面，不仅通过组合复杂性，也通过初始化顺序。

**上下文效率 vs. 透明性。** 五层上下文压缩（compaction）流水线实现了有效的上下文管理，但压缩对用户而言基本上不可见。当预算削减（budget reduction）用一条引用替换冗长的工具输出时，当上下文坍缩（context collapse）用摘要替换消息时（源码中将其描述为"对 REPL 完整历史的一次读取时投影"），或者当剪裁（snip）修剪较早的历史时，用户没有简便方法来检查究竟丢失了什么。微压缩（microcompact）的缓存感知行为进一步增加了不透明度，因为压缩决策会以用户不可见的方式受到提示缓存的影响。关于基于摘要的压缩的外部研究记录了除不透明性之外的另外两项成本，而这些是源码层面的视角所无法呈现的：摘要步骤是一次阻塞性的推理停顿，而且它是非确定性的，在相同输入下，保留的内容会随运行而变化（Cim et al., 2026）。

[^5]: 这两个信任建立之前顺序问题对应的漏洞是 CVE-2025-59536（CVSS 8.7）和 CVE-2026-21852（CVSS 5.3）（Donenfeld and Vanunu, 2026），由 Check Point Research 发现。CVE-2025-54794 和 CVE-2025-54795（Beber, 2025）则分别利用了权限流水线其他位置的路径校验与命令解析缺陷。这四个漏洞都在披露后数周内被修补。

**简单性 vs. 可扩展性。** 四种扩展机制实现了丰富的定制能力，但也制造了组合式的交互。一个插件（plugin）贡献了一个修改工具输入的 PreToolUse 钩子。自动模式分类器读取缓存的 `CLAUDE.md` 内容。路径范围规则（path-scoped rules）在读取新目录时按需加载，可能改变对话中途的分类器行为。权限处理器的四个分支在多个点上与钩子流水线交互。这些横切关注点制造出难以从任何单一配置文件预测的涌现行为。

### 12.4 经验性预测与早期信号

本文记录的架构属性产生了关于代码质量结果的可检验预测，而这些预测无法仅从源代码推导出来。有界上下文窗口（第 7 节）使代理无法同时保持对完整代码库的感知：五层压缩流水线保留了有用信息，但在每个阶段都引入有损压缩。因此，从架构上可以预测，代理生成的代码将比在完整代码库可见性下产出的代码表现出更高的模式重复率和约定违背率。子代理隔离（第 8 节）——每个子代理在各自的上下文窗口中运行，并拥有独立组装的工具池——加剧了这一效应：并行代理可能各自独立地重新实现其他地方已经存在的解决方案。第 12.1 节的设计理念信任模型能够做出良好的局部决策，但当模型缺乏全局上下文时，良好的局部决策可能产生糟糕的全局结果。

关于架构相似工具的已发表经验性研究提供了与这些预测相一致的数据。一项针对 807 个代码仓库中 Cursor 采用情况的因果分析（He et al., 2025）发现，代码复杂度出现了统计上显著的上升，最初的速度尖峰到第三个月时回落至基线。复杂度上升与未来开发速度成比例下降相关联，这表明短期收益可能被后续维护成本所抵消<sup>6</sup>。一项对 6,275 个代码仓库中 304,000 次 AI 撰写提交的大规模审计（Liu et al., 2026）发现了可度量的技术债务，其中约四分之一的 AI 引入问题一直存续到最新修订版，而与安全相关的问题存续比例显著更高。尽管这些研究针对的是相邻系统，但其架构上的相似之处（有界上下文、工具调用循环、本地生成决策）使它们成为本文所分析设计的相关参照点。一项在 Claude Code 自身上运行的受控最小配对研究更精确地定位了这些效应可被测量的位置：代码整洁度没有改变任务通过率，但更整洁的输入使 token 使用量减少 7% 到 8%，文件重访次数减少 34%（Trivedi and Schmitt, 2026），这表明执行框架（harness）对上下文的处理最明显地体现在运行足迹（成本与导航）上，而非原始成功率上。

Claude Code 的上下文管理流水线正是为缓解这些效应而设计的：渐进式压缩保留最近、最相关的上下文；缓存感知的压缩避免在压缩过程中使提示缓存失效；读取时投影为重建保留完整历史，同时向模型呈现压缩后的视图；子代理摘要隔离则防止探索性噪音在父上下文中累积。这些机制是否足以克服有界上下文的结构性限制，是一个可直接测量的经验性问题，本文的源码层面分析无法解决。

[^6]: 复杂度 +40.7%（p < 0.001），第一个月速度尖峰为 +281%，到第三个月恢复至基线性能。

### 12.5 局限性

除附录中描述的方法论局限之外，还有若干分析层面的约束。记忆化的上下文组装函数（`getSystemContext()` 与 `getUserContext()` 都在 `context.ts` 中使用 lodash memoize）意味着 git 状态和 `CLAUDE.md` 内容是被缓存的，而不是在每一轮重新计算。对话期间的动态变化可能不会立即反映出来，不过压缩可以清除缓存，而按需加载的路径范围规则提供了一种部分的对冲机制。

特性开关（feature flag）造成了构建时差异。在 `TRANSCRIPT_CLASSIFIER` 为 false 的构建中，整个自动模式分类器都被剔除。受特性开关控制的模块使用动态 `require()` 而非静态 `import`（例如用于上下文坍缩的 `query.ts`），因为 `feature()` 由于 `bun:bundle` 的 tree-shaking 约束只能在 `if`/三元条件中工作。不同的构建目标可能产出功能上不同的应用。

### 12.6 新兴方向

实现中的若干方面与更宏观的设计问题相关。更长的上下文窗口会减轻上下文压缩（compaction）的压力，有可能简化这种分级流水线。多模态工具（截图、图表、UI 预览）会扩展工具面，并带来新的上下文挑战。Claude Code Desktop 已经朝这个方向迈进：在其 Browser 面板中，Claude 通过截取屏幕截图、检查页面元素以及与运行中的应用交互来核查 UI 变更（Anthropic, 2026c）。对权限性质的形式化验证（例如证明拒绝规则始终优先、沙箱化命令无法逃逸隔离，或恢复的会话无法继承过期权限）将提供更强的安全保障。

**架构解耦（Architectural decoupling）。** 本文分析的这种紧耦合本地架构只是已经在演化的一条谱系上的一个点。Anthropic 自己的 Managed Agents 工作（Martin et al., 2026）描述了将代理的各个组件（会话、执行框架、沙箱）虚拟化，使得"每一个都成为对其他组件做很少假设的接口，并且每一个都可以独立失败或被替换"，并明确类比操作系统如何将硬件虚拟化为进程与文件。Harness Design 一文（Rajasekaran, 2026）从不同角度提出了类似观点，认为更好的模型会移动有用执行框架组合的空间，而不是消除这一空间。因此，本文记录的这一架构应被理解为一个协同演化系统的快照，而非固定的最优解。

云代理的报告让这一点变得具体，而不必依赖操作系统的类比。Cursor 将代理循环（agent loop）、机器状态与对话状态分离，并把 VM 检查点、网络策略、密钥处理与凭据管理视为代理产品的一部分（Ma, 2026）。LangChain 的 Managed Deep Agents 采取了类似做法，把持久线程、检查点、流式传输、上下文、可观测性与人机协同（human-in-the-loop）工作流放入托管运行时（LangChain, 2026c）。Google 的 Antigravity 向人们提供计划、截图与录屏等产物，用以核查代理的工作（Google, 2025）。DeepSeek Harness 通过插件配置使运行时组件（包括代理循环与会话日志）可替换（DeepSeek-AI, 2026）。因此，真正有用的设计问题是运行时归属：哪一层拥有循环、状态、沙箱、策略与恢复路径？

**适配模型与执行框架。** 自动化适配可以改变执行框架、模型，或两者兼改。Yang et al.（2026b）保持模型权重不变，利用失败轨迹来修订指令、工具、钩子与上下文管理。Yu et al.（2026）更进一步：一个专家模型在较小模型自己的轨迹中纠正失败的回合，这些纠正成为该模型的微调数据，随后再用演化后的执行框架进行评估。

**记忆作为一等子系统。** Hu et al.（2025）的记忆综述认为，代理记忆正在成为一种独立的认知基底，而不再只是上下文窗口管理的副产品，并把自动化记忆管理、RL 驱动的记忆以及可信记忆（隐私、可解释性与幻觉鲁棒性）列为开放前沿。Claude Code 目前暴露了事实层（`CLAUDE.md`、自动记忆）与工作层（对话窗口）。经验层（从过往会话中学到的、经过自动策展的策略手册的累积）是自然的下一步，而上下文工程文献（Zhang et al., 2025a）已开始为这种累积提供机制。

Context Hub 让这条边界变得可见。LangSmith Context Hub 把 `AGENTS.md` 文件、技能、策略、示例及相关打包内容视为可版本化、可评审的产物，并用标签支持跨环境部署（LangChain, 2026a）。这与 Claude Code 的文件层级是不同的设计点，但指向同一个问题：上下文需要一个生命周期，而不仅仅是一个 token 预算。技能带来了相关的维护问题，因为对一个技能的更新可能影响其他技能。Yang et al.（2026a）用图结构表示技能之间的依赖、联合使用与冲突，一并修订相关技能，并通过重放相关案例来检查每一次组合变更。

**可观测性与静默失败。** 行业调研表明，已部署代理的主导失败模式不是崩溃，而是静默的错误。Bessemer 的 2026 年基础设施报告（Wade et al., 2026）估计"78% 的 AI 失败是不可见的"，而 LangChain 针对 1,340 名受访者的代理工程现状调查（LangChain, 2026d）把质量而非成本列为生产使用的首要障碍，并发现可观测性（采用率接近 89%）与离线评估（52.4%）之间存在巨大差距。本文分析的架构让运维者可以看到工具调用、钩子与会话记录。弥合评估差距很可能需要额外的脚手架（生成器—评估器分离、冲刺合同，以及 Rajasekaran (2026) 中所讨论的那类事后检查），而不仅仅是模型改进。

OpenAI 的代理改进循环让这一点变得可操作：轨迹与反馈变成评估，由此产生的证据变成针对执行框架变更的 Codex 交接（Pasfield, 2026）。在这个循环中，遥测之所以重要，是因为它会转化为可复用的测试或具体的变更请求。

**治理。** 随着代理变得更加自主，更广泛的治理趋势将约束设计空间。《International AI Safety Report》（Bengio et al., 2026）警告称，"AI 代理带来更高的风险，因为它们自主行动，使人类更难在失败造成伤害之前进行干预"，而 MIT 的 AI Agent Index（Staufer et al., 2026）发现，被索引的代理系统中只有 13.3% 发布了针对代理的安全卡。新兴的监管努力，包括 EU AI Act 以及围绕 AI 生成代码不断演化的版权争论，可能对日志记录、透明度、风险管理与人类监督施加外部约束，从而塑造编码代理架构的演化方式。

**主动式架构。** 由特性开关控制的 KAIROS 系统展示了这一架构如何可能超越反应式的工具调用（tool use）。KAIROS 实现了一个持久的后台代理，带有基于 tick 的心跳：当没有待处理的用户消息时，系统会注入周期性的 `<tick>` 提示，由模型决定是行动还是休眠。该设计回应了一项关于主动式 AI 助手的研究中记录到的张力：任务完成率提高了 12 到 18%，但在高频率下用户偏好下降（Chen et al., 2025）。KAIROS 试图通过终端焦点感知（当用户离开时最大化自主行动，当用户在场时增加协作）以及通过 `SleepTool` 实现的经济性节流（每次唤醒都消耗一次 API 调用，而提示缓存会在五分钟无活动后过期，从而使休眠/唤醒成为一种显式的成本优化）来解决这一问题。这种把主动性同时绑定到用户在场与 token 经济性上的做法值得注意，尽管无法确认 KAIROS 是否在生产构建中处于活跃状态。

### 12.7 反复出现的设计选择

把六项子系统分析合起来阅读，会发现三个贯穿性的设计承诺，它们在原本相互独立的组件中反复出现。

**分级分层而非单一机制。** 安全、上下文管理与可扩展性都采用由独立机制组成的分级栈，而不是单一集成方案。权限架构分层了第 3.5 节列举的七个独立阶段：工具预过滤、拒绝优先（deny-first）的规则评估、权限模式约束、自动模式分类器、shell 沙箱、不从会话记录恢复会话权限，以及钩子（hook）拦截。上下文管理分层了五个上下文压缩阶段、按需加载（lazy loading）的 `CLAUDE.md` 文件、延迟加载的工具 schema，以及仅返回摘要的子代理（subagent）。可扩展性在不同上下文成本下分层了四种机制（MCP 服务器、插件、技能与钩子）（第 6 节）。在每种情况下，设计都以简单性和可调试性换取纵深防御，并接受层与层之间的交互可能产生难以从任何单一配置预测的涌现行为。第 10 节中 OpenClaw 与 Hermes Agent 的对比表明，分级分层在部署情境迥异的系统中反复出现，这说明分层模式反映的是共同的设计问题，而不是 Claude Code 特有的实现选择。

**优先可审计性而非查询能力的仅追加（append-only）设计。** 会话记录是仅追加的 JSONL 文件，并在读取时进行链式修补。会话级权限不存储在会话记录中。上下文压缩对完整历史应用读取时的投影，而非破坏性编辑。这一承诺之所以反复出现，是因为它保留了在不修改既有已写入状态的前提下恢复、分叉与审计会话的能力。代价是更丰富的结构化查询（"显示跨会话中所有修改了文件 X 的工具调用"）需要事后重建，而不是直接查找。

**确定性执行框架中的模型判断。** 在所有子系统中，该架构信任模型在丰富的确定性执行框架中的判断，而不是约束其选择。估计的 1.6% 决策逻辑占比从数量上体现了这一点：执行框架创造各种条件（工具路由、权限执行、上下文组装、恢复逻辑），使模型能够做出良好决策。分层权限在代理边界之间保持安全不变量，`assembleToolPool()` 将内置工具与 MCP 工具合并为单一统一接口，但模型对调用哪些工具以及以何种顺序调用保留完全的自主空间。其代价是，当有限的上下文妨碍全局感知时，良好的局部决策可能产生糟糕的全局结果，正如第 12.4 节的经验性预测所记录的那样。

## 13 未来方向

第 12 节把第 3 至 9 节记录的架构解读为一个连贯的设计点，并揭示了该设计点所蕴含的张力、权衡与近端方向。本节走出架构本身，记录六个开放问题——第 12.6 节已部分点明它们，而不断增长的外部文献已将其锐化到可以具体陈述的程度。这些问题覆盖本文的五价值框架（第 2.1 节）以及第 2.4 节引入的长期开发者能力问题。它们分别涉及对 Authority 层级（第 13.5 节）的治理约束、Safety 一侧的可观测性—评估鸿沟（第 13.1 节）、Reliability 一侧的跨会话持久化（第 13.2 节）、Capability 前沿的四个扩展（第 13.3 节）、作为 Reliable Execution 独立轴线的视界扩展（第 13.4 节），以及被重新表述为设计问题的长期开发者能力（第 13.6 节）。与第 12.6 节的框架一致，每个问题都以"是否/如何/哪一个"（whether/how/which）的形式提出。当所引来源给出了具体的机制选择时，本文就点名这些选择，否则保持开放。

### 13.1 静默失败与可观测性—评估鸿沟

第 12.6 节报告的可观测性—评估鸿沟可能反映了缺失的工具层、执行框架内部缺失的评估接口，或是模型能力的天花板。该处的来源并未对此作出裁决。因此，该段提到的静默错误失败模式应当如何被显性化，对执行框架而言是一个架构问题，而不是对模型而言的能力问题。近期的经验研究在多个分辨率上刻画了这一鸿沟。Cemri et al.（2025）编目了十四种失败模式，涵盖系统设计问题、代理间错位与任务验证。Pathak et al.（2025）专门为轨迹中的异常检测构建了代理轨迹基准。Yao et al.（2024）通过 `passk` 指标揭示了跨试验一致性差距，即全部 k 次独立试验都成功的概率。Kapoor et al.（2024）认为当前的代理基准缺乏留出集与成本控制，限制了可观测性实际能够诊断的范围。

会自我更新的执行框架同样需要公平比较。Wang et al.（2026b）在匹配的反馈与推理预算下，把执行框架演化与对任务解的搜索进行比较，Le et al.（2026）则用被排除在训练之外的执行框架来测试经过训练的模型。

对照第 4 节与第 5 节分析的权限流水线与工具编排层，仍有两个架构问题悬而未决。第一，本文从 Rajasekaran（2026）引用的脚手架（生成器—评估器分离、冲刺合同、事后检查，其基础是 Madaan et al. (2023) 的自我精炼模式）应当位于执行框架内部（例如作为第 6 节记录的 27 个钩子事件之外的额外钩子事件），还是作为独立的评估层位于其外部，所引来源并未给出定论。第二，第 6 节现有的钩子流水线能否在其当前上下文成本范围内承载这类脚手架，是另一个开放问题。关于弥合这一差距"很可能需要额外的脚手架……而不仅仅是模型改进"（第 12.6 节）的观察，把待完成的工作定位在执行框架层。

### 13.2 持久化：记忆与纵向的同事关系

代理状态与人机工作关系是否应当跨会话持久化，以及以何种形式持久化，本文目前在两个不同层面上处理。第 7 节记录了四级 `CLAUDE.md` 层级与自动记忆。第 9 节记录了以仅追加为主的 JSONL 会话记录，并有显式的清理重写；会话级权限不存储在其中。这两层之间应当放什么，是一个开放的设计问题：那种既不是静态指令、也不是单次会话记录的持久状态。第 12.6 节已引用的 Hu et al.（2025）与 Zhang et al.（2025a）为一个累积层提供了动机。Packer et al.（2023）把 LLM 重新表述为带有分页记忆的操作系统。Chhikara et al.

（2025）构建了一个面向生产、可在重启后存活的记忆存储，而 Xu et al. (2025) 提出了一种研究性的代理记忆设计。Wang et al. (2024c) 捕获可复用的过程性轨迹。Shinn et al. (2023) 通过跨多次尝试的言语强化来累积自我反思轨迹。Zhang et al. (2025b) 与 Huang et al. (2026) 的综述梳理了候选机制。

MemGym 使记忆问题更加具体。它评估的是在工具调用对话、深度研究、编程和计算机使用中动态形成记忆的能力，而不只是聊天中个人事实的留存（Xu et al., 2026）。这把问题从“笔记应该存放在哪里？”转变为“哪一种被记住的状态能帮助代理持续正确地工作？”

持久记忆还需要一种从有害条目中恢复的方法。MemSecBench 检验存储的信息是否会影响后续动作，以及修复过程是否能让指定的有效记忆保持完好（Chen et al., 2026）。

同样的持久性问题在人的一侧也会反复出现。第 12.6 节已经引用了 Huang et al. (2025) 与 McCain et al. (2026) 关于纵向自主性的证据。Dell'Acqua et al. (2025) 针对 776 名 Procter & Gamble 专业人士的实地实验，连同关于 Copilot 推广的纵向与组织研究（Stray et al., 2025）以及 AI 团队协作轨迹研究（Xiao et al., 2025），报告了随着协作不断累积，人机工作动态所发生的变化。Wang et al. (2023) 展示了一个具身代理，它跨任务累积技能库。Mollick (2024) 将人机工作关系界定为共同智能（co-intelligence）。单一基底能否同时承载用户的个人指令层级与共享的组织上下文，同时保持第 7 节所记录的 `CLAUDE.md` 那种基于文件的透明性，是一个开放的架构问题。会话范围的权限如何与这样的基底交互，同时又不重新引入第 9 节作为刻意安全选择而关闭的恢复（resume）复原问题，则是另一个开放问题。Claude Code 的 Projects beta 是朝这一方向迈出的一个产品步骤：独立的云会话向一个共享的项目记忆增添内容并从中取用，从而在不同会话之间传递决策（Anthropic, 2026l）。OpenClaw 的记忆子系统（dreaming、每日笔记、混合检索）与 Hermes Agent 采用 WAL 模式、支持全文搜索的 SQLite 会话存储——两者分别记录在第 10 节与第 10.2 节——为持久基底如何居于静态指令层级与单一会话对话记录之间提供了两个具体的参照点。

### 13.3 执行框架边界演化：代理在何处、何时、对什么、与谁行动

第 12.6 节引用了 Rajasekaran (2026) 的论点：更好的模型会改变有用执行框架组合的空间，而不是消除这一空间。这种移动究竟最明显地体现在执行框架于何处运行、于何时行动、对什么行动，还是与谁协调，第 3 至第 9 节的源码层面分析并未给出答案。这四个方面各自都有活跃的研究文献，而本文只是顺带触及。

**何处。** Martin et al. (2026) 的 Managed Agents 将会话、执行框架与沙箱虚拟化为可独立替换的接口。这延伸了 Packer et al. (2023) 应用于上下文窗口管理、并由 Karpathy (2023) 更广泛普及的虚拟内存类比。Khattab et al. (2023) 将执行框架本身视为一种编译目标。

**何时。** 第 12.6 节已经引入 KAIROS 作为受特性开关控制的示例，其动因是 Chen et al. (2025) 报告的 +12% 到 +18% 的任务通过率提升，以及仅在高频 Persistent Suggest 变体上出现的显著偏好惩罚（47% 对 80% 到 90%）。Claude Code 的 routines 使用更简单的触发方式：当配置的日程、API 调用或 GitHub 事件触发时，它们会启动一个新的云会话（Anthropic, 2026m），而 KAIROS 则唤醒一个后台代理，让它在每个 tick 自行决定是否行动。Liu et al. (2025)、Pu et al. (2025) 与 Lee et al. (2025) 在编程与环境界面（ambient-interface）场景中扩展了主动性设计空间。Pasternak et al. (2025) 与 Sun et al. (2025) 提出了旨在打磨这一能力的基准与训练范式，Deng et al. (2025) 则综述了更广泛的文献。

**对什么。** 视觉—语言—动作（VLA）工作将执行框架扩展到文本工具返回值之外。Brohan et al. (2023) 与 Black et al. (2024) 训练执行物理动作的 VLA 策略，Ahn et al. (2022) 则将计划建立在机器人的可供性（affordance）之上。Figure AI (2025) 与 Bjorck et al. (2025) 等行业系统将类似想法推进到人形机器人控制中。这些系统以一种成本不对称性面对可逆性加权风险原则（表 1），而该原则只是点明了这种不对称，并未对非文本动作加以量化。

**与谁。** 角色分化的多代理系统（Hong et al. (2023)、Li et al. (2023)、Chen et al. (2023)、Qian et al. (2024)）将具有不同职责的代理组合起来。多代理辩论（Du et al., 2024; Liang et al., 2024）与图结构工作流（Zhuge et al., 2024）探索了第 8 节父代理/子代理模式的替代方案。Guo et al. (2024) 综述了这一领域。

单一执行框架架构能否覆盖全部四种扩展，还是 Rajasekaran (2026) 所描述的“执行框架组合”将会分化为专门化的技术栈，是一个开放的设计问题。何时扩展直接延续了表 6 中能力与适应性之间的张力。与谁扩展部分映射到能力与可靠性之间的张力，但提出了表 6 本身并未覆盖的跨代理一致性问题。何处扩展与对什么扩展提出了本文当前子系统边界未能覆盖的进一步问题：当执行框架组件成为托管服务时，会附带哪些治理义务（第 13.5 节），以及可逆性加权风险（表 1）如何从文本效果扩展到物理效果。这些扩展如何跨多个轴组合，而不是在任一单个轴内组合，并非本文的单子系统分析所能解决。

### 13.4 时间视野扩展：从会话到科学项目

第 2.1 节将可靠执行定义为涵盖“单轮正确性与长视野可靠性”。当自主工作延伸到单个会话之外时，第 3 节、第 4 节以及第 7 至第 9 节所记录的架构如何继续支持长视野可靠性，是一个开放问题。它的主要单位是轮次、会话和子代理。越来越多的文献针对这一情形。Lu et al. (2024) 提出了一个端到端的自主研究流水线，可产出论文草稿。Beel et al. (2025) 在 SIGIR Forum 上对该流水线做了独立评估，刻画了“自主研究”目前能交付什么以及在何处不足。Gottweis et al. (2025) 开发了一个多代理假设生成系统，其运行以天而非轮次为尺度，Novikov et al. (2025) 则在以往需要人类专家数周的时间尺度上开展算法发现。Kwa 等人的 METR 研究测量了前沿代理在固定可靠性下能够成功完成的任务时长，为这一扩展问题提供了经验框架。

Quantitative Goal Persistence 基准指出了一个更窄的失败模式：代理可以做出合理的局部工具调用，却在验证器确认足够多的有效工作单元之前就停了下来（Cai et al., 2026）。对于长视野编程代理而言，进展需要一个外部定义的“完成”概念，而不只是一段流畅的最终消息。SWE Refactor Bench 将同样的思路应用于仓库迁移：它将迁移要求与固定行为测试分开检查，因此不完整的迁移与破坏所需行为的迁移会表现为不同的失败（Hong et al., 2026）。

对照本文的分析，长视野部署检验的是：当会话组合成多会话项目时，第 7 节的上下文管理流水线、第 8 节的返回最后一条助手文本的策略，以及第 9 节的仅追加（append-only）持久化是否仍然足够。第 12.4 节已将此界定为“一个可直接测量的经验性问题”，源码层面分析无法解决。时间视野扩展以周为尺度重述了这一问题：究竟是执行框架层本身就能弥合差距，还是需要一个跨会话的记忆基底（第 13.2 节），抑或视野尺度的工作需要超越会话、子代理与记忆的协调原语，并非本文以会话为范围的分析所能定论。

（Tier A）在此分析的 v2.1.88 快照之后的一项进展使这一问题变得具体。Claude Code v2.1.154 引入了动态工作流（dynamic workflows）：模型编写一段 JavaScript 编排脚本，由后台运行时执行，向大量子代理分发任务（每次运行上限为一千个），同时中间结果存放在模型上下文窗口之外的脚本变量中，而不是流经上下文窗口（Anthropic, 2026n）。它与 Claude Opus 4.8 一同发布（Anthropic, 2026k），恰恰是一种超越本文所分析的会话、子代理与记忆单位的协调原语：它把编排逻辑本身移出了对话，将“上下文是稀缺资源”与“隔离子代理边界”这两条原则（表 1）从单个子代理扩展到编排层。编排即代码（orchestration-as-code）是否会成为主导的长视野原语，以及它的 token 成本与减少的人工中途监督如何与其可靠性收益相权衡，是本文以会话为范围的分析无法定论的开放问题。

### 13.5 规模化治理与监督

新兴的 AI 监管为第 2.1 节所记录的、实现 Anthropic、运营者与用户之间权威层级的架构增加了一项外部约束。在这一外部约束下，编程代理架构应当提供哪些日志记录、透明性与人工监督能力，仍然是一个开放的设计问题。欧盟委员会的 GPAI 行为准则（European Commission, 2025a）与实施指南（European Commission, 2025b）展示了通用目的 AI 治理如何朝着对文档、风险管理、透明性与监督提出更明确期望的方向演进。MIT AI Agent Index（Staufer et al., 2026）与国际 AI 安全报告（Bengio et al., 2026）——第 12.6 节已引用——为这一约束的披露与监督方面提供了动因。Bartz 诉 Anthropic 案的裁决（bar, 2025）在训练数据来源方面增加了一项输入侧约束，这不同于新兴案件另行处理的、关于 AI 生成代码的输出侧版权问题。OECD 关于 AI 治理框架的报告（OECD, 2025）与 Nannini et al. (2026) 对代理提供方合规义务的早期分析，勾勒了面向监管者的接口可能是什么样子，但并未规定具体细节。

（Tier A）监管也可以作用于模型的可用性，而不只是作用于架构必须披露什么。2026 年 6 月，一项美国出口管制命令禁止外国国民使用 Anthropic 的 Fable 5 与 Mythos 5 模型，而在发布后数日内，Anthropic 就为全球所有用户禁用了这两个模型（Anthropic, 2026e）。Anthropic 报告称管制于 6 月 30 日解除；Fable 5 于 7 月 1 日面向全球用户恢复，而 Mythos 5 的访问权限仅对一组美国组织恢复（Anthropic, 2026f）。此类政府政策可以直接决定这样的模型何时、对谁可用。

代理安全基准也将安全对象从文本转移到环境状态。Boiling the Frog 评估多轮工作区编辑在渐进式攻击下是否会变得不安全（Bisconti et al., 2026）。这对编程代理很重要，因为风险对象可能是被修改的仓库，而不是最终答案文本。

对照第 5 节所分析的权限流水线来审视，当前架构的两项属性在这一约束下仍处于开放状态。第一，本文所记录的拒绝优先（deny-first）求值可通过会话对话记录进行内部审计（第 9 节），并且 Claude Code 可以通过 OpenTelemetry 导出工具权限决策事件（Anthropic, 2026j）。在 GPAI 行为准则（European Commission, 2025a）等新兴框架下，这些记录如何支持外部审计，仍是一个开放问题。第二，本文与确定性护栏搭配的“价值高于规则”（values-over-rules）原则，是否容许合规审查可能要求的那种显式规则表述，是另一个开放问题。这两项属性都位于执行框架而非模型之中，而未来的架构可能正需要在此处暴露新的接口。

### 13.6 长期开发者能力

第 2.4 节将长期开发者能力作为一项横切问题引入，而不是将其视为与其他设计价值并列的价值。第 12.2 节与第 12.4 节以外部的证据扩展了这一问题，包括主观感受与实测生产力之间的差异、理解力的丧失、复杂度的累积、技术债务的持续存在、神经连接性的持续改变，以及早期职业招聘的下降。实践者的说法也是如此：回顾自己转向代理驱动编程的经历时，Karpathy (2026) 警告说，“你可以外包你的思考，但你不能外包你的理解。”第 14 节随后转向：“未来的系统可以将这一可持续性缺口视为一等设计问题，而不是下游的评估指标。”这一转向是否可能，以及一等对待会需要哪些架构机制，是本节所记录的最后一个开放问题。

这也与过程监督相关联。人—LLM 协作规划研究认为，用户需要过程层面的控制，而不只是结果层面的审查，并按模式、范围和编辑层级来组织引导（He et al., 2026）。对编程代理而言，类似的问题是：在工作仍在展开的过程中，用户能够检查并改变什么。

两个子问题将测量差距与设计差距区分开来。第一，激发这一问题的经验性主张是否能在会话粒度上被测量。现有引用覆盖从会话到数月不等的尺度（Becker et al. (2025) 的 16 名开发者随机对照试验、Shen and Tamkin (2026) 的理解力测试比较、Kosmyna et al. (2025) 的 EEG 研究、He et al. (2025) 对 807 个仓库的因果分析、Liu et al. (2026) 对 304,000 次提交的审计、Rak (2025) 的招聘数据系列），但第 3、4、7 节所记录的执行框架

并未暴露任何针对理解程度或约定漂移的按会话信号。关于程序员交互模式（Barke et al., 2023）与 AI 引发的代码安全性回归（Perry et al., 2023）的相关工作勾勒出了会话粒度的度量，Aiersilan（2026）则提出了一套会话级认知卸载探针的协议。其次，一旦这类度量存在，架构能否对其作出响应（例如把生成器—评估器分离（Rajasekaran, 2026）的类似思路应用于人类环路、保理解的界面（comprehension-preserving surfaces），或尚未命名的机制），正是第 14 节提出的设计缺口问题。本文对哪一类机制更合适不持立场。它同样没有判定：此处记录的这套执行框架（harness）是否是采取该行动的恰当场所，而不是 IDE、组织或人类开发环路。第 11 节梳理的相关工作与第 14 节的可持续性转向，标示出本文把这一问题留在了何处。

## 14 结论

本文表明，生产级编程代理可以被理解为对一组反复出现的设计问题的回答：推理相对于执行框架（harness）位于何处，执行、安全、可扩展性、上下文、委派与持久化如何组织，以及这些选择编码了哪些权衡。Claude Code 在这一设计空间中占据了一个清晰的设计点。它赋予模型广泛的本地自主权，同时用一套密集的确定性执行框架将其包围，用于权限控制、工具路由、上下文压缩（compaction）、可扩展性与会话恢复。若通过第 2 节识别出的五项价值与十三条设计原则来解读，这些选择是自洽的而非临时拼凑的：系统始终如一地优先考虑人类决策权、安全性、可靠执行、能力放大与上下文适应性。

与 OpenClaw 和 Hermes Agent 的比较表明，相同的设计问题会在不同的代理系统中反复出现，但会产生不同的答案。Claude Code 把投入放在 CLI 执行框架内逐动作的安全分类与渐进式上下文压缩上，OpenClaw 则把投入放在多通道网关内的边界级访问控制与结构化长期记忆上，而 Hermes Agent 从单一进程出发、在众多界面上提供逐动作审批，并具备可插拔的记忆与模型后端。三个系统通过 ACP 在多个位置上组合：OpenClaw 可以通过 ACP 将 Claude Code 作为外部执行框架来托管，而 Hermes Agent 则同时处在宿主/访客划分的两侧。因此，对代理构建者而言，最具影响的开放问题不是如何增加更多自主权，而是如何随时间推移保持人类能力。

综合来看，第 2.4 节提出的长期能力问题、第 12 节的分析以及第 13 节梳理的开放问题表明，该架构提供的、能够显式保持长期人类理解、代码库一致性或开发者流水线的机制是有限的。未来的系统可以把这一可持续性缺口当作一等设计问题来处理，而不是把它当作下游的评估指标。

### 证据基础与方法

本附录记录了本研究的证据来源、分析程序和局限。

#### 证据基础与证据层级

本文的论断建立在三个证据层级上：

- **Tier A（产品文档）**：取自 Anthropic 官方文档和工程出版物的论断。这些材料确立了产品意图，但可能不反映内部实现。
- **Tier B（代码验证）**：引用提取出的 TypeScript 代码库（v2.1.88，取自公开可得的 npm 包提取物）中具体文件和函数的论断。这是最强的证据层级。
- **Tier C（重构推断）**：源自社区分析、OpenClaw 或 Hermes Agent 结构比较，或从代码模式推断的论断。这些论断以带保留的措辞表述。

源语料包含约 1,884 个文件，总计约 512K 行 TypeScript，取自提交 `53faa8b216` 的 `original-source-code/src` 目录。OpenClaw 和 Hermes Agent 被用作比较参照点，而非基准真相标准。所分析的快照分别为提交 `462d8e3bc0` 和 `f1f42a7b9f`。

#### 设计空间分析程序

设计问题通过考察每个子系统中反复出现的选择点来识别，这些选择点在其它生产级代理中存在替代设计。Claude Code 对每个问题的回答都追溯到具体的源文件和函数实现（Tier B 证据）。五值框架（人类决策权威、安全性、保障与隐私、可靠执行、能力放大、上下文适应性）从官方文档和创作者陈述中识别（Tier A），然后通过十三项设计原则追溯到架构决策。长期能力保持被单独作为一个横切问题处理，而不是作为一种设计价值，因为它在架构或 Anthropic 所陈述的价值观中并未显著体现为设计驱动力（第 2.4 节）。Token 经济学作为横切约束，同时约束全部五个价值，揭示了各个子系统的选择在共享资源压力下如何相互作用。

#### 局限性

- **静态快照。** 分析反映一个版本（v2.1.88）。特性开关（例如 `TRANSCRIPT_CLASSIFIER`、`CONTEXT_COLLAPSE`）造成构建期可变性。不同的构建目标可能产生功能上不同的应用。
- **逆向工程的认识论。** 源代码揭示已实现的结构、控制流、依赖关系和特性门控。它无法确认设计意图、已启用的生产标志、运行时普遍性或未发布行为。
- **单一系统分析。** 发现描述的是 Claude Code 的设计空间，而不是编码代理的全部设计空间。概括是有边界的。
- **比较系统快照。** OpenClaw 和 Hermes Agent 的分析各自反映特定的开发状态，可能不代表其当前能力。

#### 条件性工具可用性

`getAllBaseTools()` 函数（`tools.ts`）根据模式、构建、环境和特性开关构造不同的工具集（表 8）。在简单模式下，模型可能只看到 3 个工具（`Bash`、`Read`、`Edit`），而在启用全部特性的完整内部构建中，最多可看到 54 个工具（19 个无条件工具加 35 个条件工具）。

**表 8** 条件性工具可用性分类。

| 类别 | 示例 |
| --- | --- |
| 始终包含 | `AgentTool`、`BashTool`、`FileReadTool`、`FileEditTool`、`FileWriteTool`、`SkillTool`、`WebFetchTool`、`WebSearchTool` |
| 环境 | `GlobTool`/`GrepTool`（除非为嵌入式）、`ConfigTool`（仅 ant）、`PowerShellTool`（Windows） |

#### 跨文件依赖

导入图包含以下依赖结构。`QueryEngine.ts` 将回合执行委托给 `query.ts`。`query.ts` 从 `services/tools/`（`StreamingToolExecutor`、`runTools`）和 `services/compact/`（`autoCompact`、`buildPostCompactMessages`）导入。`QueryEngine.ts` 从 `memdir/` 导入记忆和提示组装。代码显式避免循环导入：提取 `types/permissions.ts` 以打破导入循环，而 `context.ts` 中的 `setCachedClaudeMdContent()` 避免了经由 permissions/filesystem 路径的循环。
