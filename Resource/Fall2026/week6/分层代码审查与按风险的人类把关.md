我们此前提过：Claude Code 里大约 90% 的代码是 Claude 写的。那么在这种体量下如何做代码审查？到底谁在读代码？代码出错了怎么办？

本文描述 Claude Code 团队的代码审查流程，以及我们如何改进它。6 月到 9 月间，合并进 Claude Code 代码库的 pull request 数量翻了一倍以上，而不得不回滚的 PR 占比下降了超过 40%。

我们并没有停止代码审查。相反，我们把大部分「阅读」自动化了，并调优流程以节约人类时间与精力；同时也大力投资，让回滚错误变得更快、更容易。

## 重新思考代码审查的目标

有了 agent 写代码，改动量迅速上升。我们的 monorepo 里，从 5 月大约每天合并 2,500 次改动，到今年 9 月超过 [30,000](https://www.anthropic.com/engineering/redesigning-source-control)。

虽然 Claude Code 不在该 monorepo 里，压力同样很大。以这种速度推进时，逐行人工审查会越来越难，甚至不可能。

**代码审查有两个目的：**

1. 在上线前发现并纠正缺陷
2. 形成对代码库的共享理解

本文主要谈第一个目标，文末会回到第二个。

我们把「有没有人读过代码？」看成对「这次改动可能出什么问题、该用哪种自动化或人工检查来抓住它？」的不精确度量。

这个问题也改变了审查的时机。传统上，审查是事后闸门：代码写完、PR 开了，再等人来看。我们则把审查嵌进工作流，更像写作时持续开着的拼写检查。

多数改动在请人看之前，至少已经过 Claude 审查并修正过一轮。这样我们先抓住常规缺陷，把人类注意力留给更高层的考量。

## 人类时间与注意力

我们想把人类时间与注意力留给只有人能处理的事，同时用足够的自动化覆盖其余部分。即便以当前节奏，人仍有大量工作，团队几乎每天都在碰到新挑战。

因此人类时间是双边成本：既要算人做审查的时间，也要算人修「烂代码引入的缺陷」的时间。若只减少前者而不减少后者，并没有真正节省人类时间。

所以目标是：Claude Code 相关仓库（CLI、桌面与 Web、移动端）里，多数 PR 最多只需一个人在环（可以是作者本人）就能合并，且回滚与事故率不上升。

我们用「每个 PR 的人类批准数中位数（及 95 分位）」「人类评论数」「PR 等人的时长」跟踪人类时间；用回滚率与事故率作护栏——若这些上升，说明只是把人类时间挪了地方，并未真正减少。

## 一次改动要走过怎样的旅程？

无论来自工程师笔记本，还是 Slack 里的 Claude 会话，典型改动都会经过多层审查。

我们有六层检查，再加上回滚机制兜住漏网问题。

*[图略：FIG B: Layers, not one gate]*

每层抓住一些、漏掉另一些。很少有缺陷能穿过全部层；若仍漏了，还有回滚。

**1. PR 前验证（Pre-PR verification）**

多数审查发生在创建 PR 之前。我们要求 Claude 做可运行的事：跑测试、构建，或把截图与设计对比。不是口头说「做完了」，而是出示结果。然后由子 agent 在全新上下文里再审一遍 diff。这两招都写在我们的[最佳实践指南](https://code.claude.com/docs/en/best-practices)里。

开 PR 前，许多人还会跑一批内部 skills——猎 bug、缩 diff、端到端验证、对照设计规范检查 UI 改动等。

Claude Code 创建者 Boris Cherny 认为，给 Claude 配上[验证流程](https://x.com/bcherny/status/2007179861115511237)大概是提升产出质量的最大关键。

他估计验证流程能把 Claude 输出质量提升两到三倍。

不同领域的验证差别很大：有时只是一条 bash；有时是整套测试；有时是在浏览器或手机模拟器里测应用。

若自动化审查反复标出同一问题，我们在源头修——改 skill、加 lint 规则，或更新文档，例如：

`CLAUDE.md` —— 给 Claude 的项目说明（技术栈、约定、目标与非目标）。Claude Code 每次审查都会拉入此文件，大型代码库里我们保持简短，并在此引用其余文档。若代码违反其中约定，或更新导致文件过时，审查器会标出。

`REVIEW.md` —— 代码所有者告诉审查器「自己这块什么重要」。我们会单独核验审查器是否真的遵循。好的写法简短，并聚焦：定义项目失败态（文档不得撒谎；配置不得误路由）；限制吹毛求疵；定义忽略路径；要求文件+行号引用而非猜文件名；要求顶层摘要含数量，并明确写「无问题」。

**2. 每个 PR 上的 AI 审查**

每个人类审查之前，每个 PR 都会先收到 Claude 审查。

diff 会对照整个代码库以及作者声明的意图分析，检查：改动是否真解决了问题；是否融入更大系统；是否破坏代码库其他部分。

审 bug 修复时，bot 会尝试找根因。

我们的公开产品 [Code Review for Claude Code](https://code.claude.com/docs/en/code-review) 已对所有 Team 与 Enterprise 客户开放。本地还有更轻的 `/code-review`。

研究预览发布以来，内部 PR 收到实质性审查评论的比例从 16% 升到 54%。超过 1,000 行的 PR 多数能检出问题；较小 PR 多数返回干净结果。管理员可为仓库配置 Quick / Standard / Deep。漏掉单个 bug 的代价高于审查时间时，用 Deep。

发现（findings）在给人看之前，会再经多个 agent 把关：

- 多个 agent 并行猎 bug
- 单独投票判定有效或假阳性，只确认票数够的发现
- 仅风格／诊断／清理类发现会被滤掉（上线前在我们自己的 PR 上做过 A/B）

剩余发现以行内评论呈现，按严重度排序，并标为：Important、Nit、Pre-existing（避免因 PR 未引入的旧 bug 不公地惩罚作者）。

所有发现都必须处理——修好，或带理由关闭讨论。很多时候 agent 会在夜间修好，作者回来时 PR 已又过一轮审查。

**3. 可阻断合并的安全审查**

我们还跑自动化安全审查。只要还有未关闭发现（来自代码审查或安全审查），PR 就不能合并。作者可修复，或用简短理由关闭（处理假阳性的方式）。

后续 commit 修好问题后，发现会自动关闭。可用开源 security review GitHub Action 或 `/security-review` 配置同样机制。

**4. 可阻断的自动化检查**

标准检查：lint、类型检查、全平台测试、构建。（我们另文写过如何扩展 CI。）典型 CLI PR 在任何人看之前可能已跑几十项检查。PR 模板会问如何测试、如何回滚。Claude 可代答，但作者有责任审过。

**5. 按风险缩放的人类批准**

有的改动风险高于另一些（例如文档修复 vs 自动更新器），因此审查级别不同。

*[图略：FIG C]*

分级由**改动**决定，而非作者。分类器按改动定风险；另一分类器判断即使档位未要求，是否仍需额外批准。有些路径永远需要额外批准——所有者标为敏感的任何内容，以及任何 CI workflow 文件。

只有仓库受信名单上的作者能享受放宽要求，通常是拥有该仓库的团队。其他人需要第二人批准。Agent 批准不算人类批准。自动化审查可放行低风险改动，但不能在「需要人」时代替人。

改动作者对其负责：若 agent 开了 PR，agent 操作者始终算作必要审查者之一。批准只对一次 commit 有效。若出现不可信的新 commit（例如 agent 推了东西，或有人手动解决合并冲突），必须重新批准。

**6. 合并队列、特性开关与分阶段放量**

合并队列确保在把改动打到 main 上再跑完全部检查，避免两个各自成功的 PR 合并后弄坏 main。新功能通常放在特性开关后，先给 Anthropic 员工。因为我们重度自用，常比用户更早发现回归。

公开发布时先走 latest 通道，stable 随后。

**7. 快速反馈与回滚**

总会有坏合并漏网。这是最后一道防线，重点是尽快识别。特性开关后的改动可不部署就关掉。

Claude Code 有每周 on-call；事故复盘会回溯哪一层本该抓住问题。发现坏合并仍靠作者与 on-call，再加上回滚与事故看板。我们还没有按这些指标自动调高批准要求的断路器，但在减少合并中人类干预的路上，这是我们在看的方向。

有人指出减速、少产出其实能提高准确率——多半是因为总工作量下降了。我们的优先项是提升「快速识别并纠正问题」的能力。

## 如何让审查器变得更好

代码审查是持续改进的循环：

我们用事故作评测指标。团队收集导致事故的 PR、其 fix-forward 与回滚，并由懂代码库的工程师核实每个 bug 的位置与正确性。审查系统每天对照这套集合评估。

*[图略：FIG D: Our incidents are the eval]*

每起事故加入集合；对审查系统的每次改动都对照整套集合评估。

测噪声时，观察人对审查评论的反应。若容忍大量非 bug 报告，抓 bug 率很容易「变好」，因此必须约束。我们把每条评论归类为：修好了、驳回了、澄清为有意为之、或认为不重要。另外在已知干净的 PR 上跑审查系统，观察它报出会导致有害改动的频率。

公开优先级：第一，检出真实缺陷；第二，减少审查轮次。

当作者是 agent 时，处理一条审查评论更贵：人一秒就能关掉 nit；agent 处理则意味着又一次 commit、又一轮审查。

审查过程必须收敛。agent 作者与 agent 审查者可能永远循环。我们在 CLI 项目里见过一个 PR 一夜循环五十多次，只能人工叫停，否则可能无限继续。

对审查系统反复标出的内容跑 `git blame`：约 59% 从第一轮起就已存在。本质上很少发现新 bug，只是每轮多抓几个旧的。

我们还曾默认跑多轮审查（因为每轮可能抓到不同 bug），把问题加剧了。高风险改动多轮有用，但不是每个 PR 都需要。团队开始跟踪「到通过为止的轮数」以及召回，并更新重审逻辑：

- 限制轮数；三轮后请作者重新评估方案
- 初始几轮之后，重审只看新 diff
- 指明 bug 类别，让作者一次改全，而不是只改一行
- 避免重复报告已观察过的问题
- 审查 agent 也会夜间在当前代码库上跑，帮我们在历史 bug 扩散前识别它们

*[图略：FIG E: Review that converges]*

引入 Convergence 后，内部 PR 平均审查轮数下降。

## 环中之人（Humans in the loop）

让高级工程师停下手里的活去审一个常见错误，成本远高于自动化。人审仍对若干任务必不可少：

- **该不该做？** 决定是否构建、定愿景、品味与产品目标。有团队自称解决了审查瓶颈，仍对团队外改动做人审，确保「做的是对的事」。
- **审计危险代码**（计费、自动更新器、CI workflow）。
- **架构审查**，因为这些选择会定下别人遵循的约定。
- **核验证明**（测试输出、跑过的命令、截图、审查评论）。若说不清检查会漏什么，就别只求一个 👍——你需要真正的审查。
- **承担责任**。每个上线的改动都有人对结果负责，无论是谁敲的字。

## 团队上下文

代码审查向来也承担「传达代码库变化」的职责。读同事的 diff，是人们理解「改了什么、代码库怎么工作」的常见方式。若大部分阅读由机器完成，人如何学习代码库？

我们没有正式机制。团队里没人脑子里有 Claude Code 的完整心智模型，也不认为需要有。想学某一块时，就让 Claude 针对那一切片生成讲解——几分钟，而且总是最新的。

*[图略：FIG F: If machines do most of the reading, how does anyone learn the code?]*

有人会再进一步，让 Claude 生成可视化该区域、并以自己偏好风格教学的小产物。

这比逐行读琐碎 diff（比如一行文案修改）更能聚焦人类注意力——琐碎 diff 几乎教不到东西；为即将改的模块生成讲解则收获很大。

此外我们默认开放：在公开 Slack 频道工作，看着别人边做边学。

## 「你落地，你拥有」（You land it, you own it）

若你合并了小／中等改动，出了问题，一般期望通常是你自己修。之所以不会失控：

- 小改动易于审查、调试与回滚
- 几乎一切可回滚：特性开关、revert、分阶段放量可在几分钟内逆转多数错误
- 爆炸半径定标准：更昂贵的代码得到更多眼睛与验证
- 遥测与内部使用能快速暴露回归
- 不是甩锅游戏：修问题的人拥有它，因为上下文最多；事故复盘看系统
- 团队大量在公开频道共享责任：任何人能看到别人在建什么、加入讨论，或让 Claude 找缺口；反馈也来自非代码所有者。这种开放是质量能在「并非每行都过闸」时仍然高的重要原因。

## 改弦更张（Changing course）

有了 agent，开新活很便宜，但有时不该开。典型场景：频道里有人指出提议路径无效（引用既往决策或提出更好路径），作者于是关掉 PR 或改实现。

因为一开始写代码很容易，关掉 PR 也不觉得亏。关键是在讨论早期转向，而不是等 PR 定稿再发阻断评论。

## 如何落地

这套做法的多数组件，你们团队已经能拿到。

**在 pull request 之前**

- 给 agent 一份可运行检查清单，写进简短的 `CLAUDE.md`
- 用 hooks 让 agent 调用格式化与 linter
- 本地跑 `/code-review` 与 `/security-review`，或用新上下文的子 agent 审改动
- 建 `REVIEW.md`，用来跟踪反复出现的审查问题

**在每个 pull request 上**

- 强制 CI
- PR 模板加上 Testing、Risk、How to revert
- 先在一个仓库加 AI 审查器（Code Review for Claude Code 或 Claude Code GitHub Action），迭代几周 `REVIEW.md` 再推广
- 加自动化安全审查
- 要求合并前解决全部审查线程
- 按风险定严格程度：常规改动快速过；高风险区域（bug 很贵）彻底审。Code Review 有 Quick / Standard / Deep
- 限制审查轮数；几轮之后只审新 diff

**批准**

- 按**改动**而非作者定义风险级别；先严后松，有证据再放宽
- 宽松批准路径留给受信作者
- Bot 批准不能顶替必需的人类批准；有新 commit 时撤销既有批准
- 对控制 auth、计费、CI、发布流程以及安装器的代码与策略，指定人类批准者；用 CODEOWNERS 与分支保护

**合并与合并后**

- 建合并队列
- 尝试特性开关
- 先给内部用户
- 分阶段放量
- 做一键回滚机制
- 用事故与回滚日志建评测集
- 改提示词、工具或模型后重新给审查器打分
- 跟踪人类投入，以回滚率与事故率为护栏

## 走向何方

Code Review 发布时的意图是：最终批准仍由人做；产品只发发现。但在我们自己的仓库里我们走得更远：所有者决定哪些低风险改动在自动化检查通过后可自动合并。这条边界还会继续演变。

因此每当审查器漏掉什么，我们就问：模型上下文里缺了什么？然后写成 `CLAUDE.md`、skill 或新检查。目标没变：降低每次改动的人类投入，同时让回滚率不高于现在。

若你们也允许 agent 创建 pull request，请告诉我们：自动化了哪些检查、哪些仍需人、我们哪里搞错了。
