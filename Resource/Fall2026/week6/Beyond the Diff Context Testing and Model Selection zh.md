像 Nvidia、Coinbase 这样的数千家公司用 Greptile 在合并前检查改动。体量上：每天 GitHub 上超过 1% 的 PR 会经过 Greptile。

公司选 Greptile 主要有三个原因。

1. 第一，代码库上下文：Greptile 很擅长给大型代码库建索引，因此能抓住不在 diff 里、而是 diff 二阶效应的复杂缺陷。
2. 第二，Greptile 会真正跑你的代码：多数代码审查 agent 其实只是用前沿模型读代码找 bug。Greptile 会在沙箱里装依赖、起开发服务器、点来点去、模拟 API 输入、压测端点，发现纯靠「读」永远抓不到的问题。
3. 第三，我们很擅长分配推理（inference）。审查与测试的每个子任务，都会选合适体量的模型——前沿与开源都用。我们还给 agent 一套专用检查工具。这样一来，效果可以好过纯 Codex 或 Claude Code 审查，成本大约只有十分之一。

不过偶尔会有公司需求非常特殊，我们一时服务不好。这时他们会决定自建内部代码审查方案。

一旦他们这么做——我们乐意免费帮忙。我们能从过程中学到如何服务这类客户；他们则能用上我们在构建优秀审查 agent 上的经验。

今天就把其中一部分经验分享出来。这对两类人有用：

1. 在大公司工作、想自建 AI 代码审查工具的人
2. 正在为公司选型 AI 代码审查工具、想弄清它们怎么工作以便更明智决策的人

## 基本工作流

核心是：某个沙箱里跑着一个 agent。有待审 pull request 时，它接收来自 GitHub 的 webhook。可以用 Codex 或 Claude Code，也可以用 Pi、OpenCode 这类模型无关方案。它分析改动、检测缺陷，再把评论发回 GitHub。

大概一天就能搭出这个骨架。

然后你会发现几件事不对：

1. 漏掉很多 bug，而且你不知道漏了什么（很难评估和改进）
2. 对代码库和产品理解不深，尤其跨多个仓库时
3. 非常贵（单次至少 $3–5，高可达 $10–20，每个 PR 还会跑 2–3 次）
4. 一堆吹毛求疵的评论，工程师会烦
5. 每次重跑都会「新发现」一批 bug，而不是一次报全

下面逐个解决。

## 改进 1：优化提示词

最容易的是把提示词写好。可以明确要求它找特定类型的 bug，也明确要求它不要发吹毛求疵的评论。

这一步能走很远，但要评估「改完有没有变好」出奇地难。评估审查 agent 很难，因为真正的 *bug* 非常稀少。

几乎没有哪家公司的 PR 流量大到能单独把 agent 性能迭代起来。Greptile 的优势是每月有数百万 PR 经过，因此能监控改动是否提高了抓 bug 率。你可以自建一个[含多样历史缺陷 PR 的数据集](https://greptile.com/benchmarks#case-library)，对着它做 hillclimb。

## 改进 2：模型优化（model optimization）

如果公司用 Claude 写代码，审查也用 Claude 模型，会漏掉很多 bug——因为作者和审查者有相似的盲区。举例：Claude 模型引入 n+1 错误的概率大约是 GPT 的两倍，审查时漏掉它们的概率也大约是两倍。

应考虑用 Codex 模型审 Claude 写的代码，反之亦然。

如果公司只用一种编码模型，这很容易：大家都用 Claude，审查 agent 就用 GPT。

若混用多种，就得做路由／分类器，识别作者模型并翻转审查模型。

在[我们关于 model inversion 的研究](https://greptile.com/blog/model-inversion)里，这样做抓 bug 率大约提升 ~10%。数字看起来不大，但每少一个到达客户的 bug 都很重要。

Greptile 当然默认就做 model inversion。

## 改进 3：代码库上下文

即便如此，审查 agent 往往仍不懂你的代码库。这会导致假阳性评论，更糟的是完全漏掉复杂的链式缺陷。常见例子是 auth bypass：往往是无意引入的，抓住它需要对应用里鉴权机制有相当细致的理解。

审查 agent 也常常不完全理解 *意图*。有时代码完全「正确」，但做了错事，或只做了一半。

可以用两步解决：

- 建一个 MCP gateway，让它能访问文档以及 Jira、Linear 等
- 建一个代码库索引器（codebase indexer）

建索引器相当费事。一种做法是让 agent 定期爬代码库并维护某种 wiki——Greptile 大致如此。

还应跟踪回滚与事故，写入 wiki。这样审查 agent 知道过去出过什么错，避免重复。这需要与遥测栈做某种集成层。

把 wiki 注入 agent 沙箱，让它带着对代码库与产品的理解进场，从而抓住更多 bug、减少假阳性。

## 改进 4：自主测试

假设要抓 Web 应用的 UI bug，比如确保某些按钮在 iPhone 打开时不会被藏住。理论上可以把 React diff 塞进很聪明的模型，让它转一会儿再告诉你有没有 bug。更好的办法是：起开发服务器、打开浏览器，用 computer use 把每条路径点一遍，确认能工作。

好在前沿模型的 computer use 已经相当不错。你需要建设的部分是：

1. 很好的开发机，配置成能快速拉起某个 PR 分支来测
2. 代码库各部分到可测用户流程的映射

前者我们用的是大型可配置 VM，即便如此通常还需要团队的 FDE 进去帮客户把 VM 配好。

后者我们用[知识库](https://greptile.com/knowledge-base)：Greptile 跟踪代码库各部分相关的流程。你应该也能用 AI 生成这类映射。

## 改进 5：部分事情用更便宜的模型

如果上面都做了，效果会变好，但每次审查的 token 成本大概仍在 $2 到 $20。审查器往往在 PR 分支的每次 push 都跑，成本会很快累积。

好在审查与测试 PR 由一套相当稳定的子任务组成。因此可以为[每个子任务挑最合适的模型](https://greptile.com/build-vs-buy#efficiency)，相对「只用前沿模型」大幅降本，同时维持／提升效果。

举例：审查里很多 token 花在读文件上。读到的文件多数其实与本次改动无关，但模型往往读完才发现。用很轻很便宜的模型做这件事，能大幅降低读文件成本，再把更窄、信号更高的文件集交给前沿模型。

---

优秀的代码审查 agent，会把代码库上下文、测试、可靠评测，以及「每个任务用对模型」合在一起，高效地抓缺陷。
